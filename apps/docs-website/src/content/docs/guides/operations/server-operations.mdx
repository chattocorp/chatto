To operate Chatto, keep the process healthy, monitor storage growth, test your
backups, and know which tool repairs an account or a deployment.

## Operator Surfaces

| Surface | Use for |
| ------- | ------- |
| Admin UI | Members, roles, permissions, room layout, branding, event log, and system diagnostics. |
| Metrics listener | Prometheus metrics for one server process. |
| Exporter | Prometheus metrics for the full deployment, from NATS and asset storage. |
| Operator CLI | Local recovery and bootstrap over a Unix socket. |
| Backups | Disaster recovery, migration tests, and upgrade safety. |

## Check configuration

Before deployment, run the check with the same environment as the server:

```sh
chatto config check --config /etc/chatto/chatto.toml
```

The command returns a nonzero exit status for unknown or deprecated TOML keys
or `CHATTO_` environment names. It then checks decoding and normal configuration
validation. It does not start the server or contact external services. A successful
check does not test network access, credentials with a provider, or storage access.

The check includes nested tables, repeated provider tables, fixed ENV names, and
indexed provider and development bootstrap ENV names. Indexes must start at `0`
and have no gaps. Names outside `CHATTO_` are ignored. Run the check in the server
environment: development-task or test variables with that prefix are not server
configuration and are reported as unknown.

Diagnostics show key names and migration instructions, never setting values.
Syntax, decoding, and value-validation errors omit details that could contain
secrets or personal data. Check required fields and value formats in the
[configuration reference](/reference/environment-variables/) if you get a value
error.

Without `--config`, the command uses `chatto.toml` in the current directory.
If that file is absent, it checks ENV-only configuration. An explicitly selected
file must exist.

Normal startup keeps its upgrade-compatible loading policy. It still ignores
unknown TOML keys and ordinary unknown ENV names. Supported aliases still work,
but the explicit check rejects them so you can migrate before deployment:

| Old setting | Action |
| --- | --- |
| `livekit.instance_id`, `CHATTO_LIVEKIT_INSTANCE_ID` | Use `livekit.server_id`, `CHATTO_LIVEKIT_SERVER_ID`. |
| `bootstrap.instance` | Use `bootstrap.server`. |
| `bootstrap.users[].instance_role` | Use `bootstrap.users[].server_role`. |
| `CHATTO_AUTH_OIDC_*` | Use the [indexed provider variables](/reference/environment-variables/#authentication). |
| `operator_api.socket_mode`, `CHATTO_OPERATOR_API_SOCKET_MODE` | Remove the setting. The socket always uses mode `0600`. |
| `livekit.webhook_url`, `CHATTO_LIVEKIT_WEBHOOK_URL` | Remove the unused setting. Set `webhook.urls` in LiveKit. |
| `auth.providers[].provider_options` | Remove the unused setting. Use documented provider fields. |

Email OTP codes use a `30m` default in generated, omitted-setting, and ENV-only
configuration. Explicit TOML values remain valid, and
`CHATTO_AUTH_EMAIL_OTP_TTL` overrides them.

## Admin Dashboard

Owners and administrators use the admin UI for daily operations. Their
permissions control which pages they see. The **System** tab starts with a
health summary. It shows a lost broker connection, failed projections, stalled
background workers, and JetStream usage near an account limit. The other
System tabs show the details: Streams, Projections, Workers, and LiveKit. Select
a check to open its tab. A dot on a tab shows a warning or a problem.

The system pages show operational metadata, not message content. This is an
application boundary. A person who controls the process, the storage, and the
keys can read more. See [Security & Privacy](/guides/operations/security/#encryption-and-data-erasure).

### NATS Projection Consumers

Each server process creates its own NATS consumers to keep local read models.
Their names start with `projection-`. Chatto deletes them at shutdown. After a
crash, NATS removes them after five minutes without activity. Do not delete
named durable consumers, such as `chatto-asset-cleanup-v1`. They keep
unfinished background work across restarts.

## Metrics

Enable the metrics listener to let Prometheus scrape one server process:

<Tabs>
<TabItem label="TOML">

```toml
[metrics]
enabled = true
bind_address = "127.0.0.1"
port = 9090
path = "/metrics"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_METRICS_ENABLED=true
CHATTO_METRICS_BIND_ADDRESS=127.0.0.1
CHATTO_METRICS_PORT=9090
CHATTO_METRICS_PATH=/metrics
```

</TabItem>
</Tabs>

Keep the metrics listener private. Enable `metrics.pprof` only while you
profile, and only on localhost or a trusted internal network.

### Projection snapshots

Use these metrics to check snapshot restore, publication, and cleanup. The
metrics listener reports each replica separately. Counters reset on restart.

| Metric | Type | Labels |
| --- | --- | --- |
| `chatto_projection_snapshot_restore_info` | Gauge | `projection`, `source`, `reason` |
| `chatto_projection_snapshot_publications_total` | Counter | `projection`, `backend`, `result` |
| `chatto_projection_snapshot_publication_duration_seconds` | Histogram | `projection`, `backend` |
| `chatto_projection_snapshot_last_publication_timestamp_seconds` | Gauge | `projection`, `backend` |
| `chatto_projection_snapshot_cleanup_runs_total` | Counter | `backend`, `result` |
| `chatto_projection_snapshot_cleanup_deleted_objects_total` | Counter | `backend` |
| `chatto_projection_snapshot_cleanup_deleted_bytes_total` | Counter | `backend` |
| `chatto_projection_snapshot_cleanup_last_success_timestamp_seconds` | Gauge | `backend` |

The restore gauge has value `1` after initial replay completes. Its `source`
is `current`, `previous`, or `cold`. Its `reason` is `none`, `disabled`,
`missing`, `rejected`, or `unavailable`. `disabled` also applies to projections
that always use cold replay. For `previous`, the reason describes why the
current generation was not used. If both generations fail, `unavailable`
takes precedence over `rejected`, and `rejected` over `missing`.

Compare the restore result with `chatto_projection_startup_duration_seconds`
and `chatto_projection_startup_messages` for the same replica and projection.
The duration and message count describe that process's initial replay.

Publication and cleanup results are `success` or `error`. A skipped publication
or a lease held by another replica does not count as an attempt. Publication
duration includes capture, encoding, and storage work for completed attempts,
including failures. Cleanup deletion counters include work completed before a
cleanup failure. NATS uses Object Store TTL, so these cleanup metrics measure
Chatto's S3 cleanup only.

Operation metrics are absent until the first completed attempt. Success
timestamps are absent until this replica completes successful work. They do
not advance when another replica publishes or cleans up. To check the latest
observed success across replicas, take the maximum timestamp within one server
deployment. A restarted replica does not retain its previous timestamps.

For example, this query selects replicas that used cold replay because snapshot
storage was unavailable:

```promql
chatto_projection_snapshot_restore_info{source="cold",reason="unavailable"} == 1
```

## Exporter

The exporter gives metrics for the full deployment. On a single process, run
it inside `chatto run`:

```toml
[exporter]
enabled = true
bind_address = "127.0.0.1"
port = 9100
path = "/metrics"
```

With more than one replica, enable the embedded exporter on one replica only.
Alternatively, run `chatto exporter` as a separate process against external
NATS or the TCP listener of embedded NATS.

### Snapshot storage totals

For S3 storage, the exporter reports
`chatto_projection_snapshot_storage_objects` and
`chatto_projection_snapshot_storage_bytes`. Both have `backend="s3"` and a
`scope` label: `current`, `non_current`, or `all_versions`. These scopes refer
to S3 object versions, not the current and previous snapshot generations.
Object counts for `all_versions` include delete markers; markers add no bytes.

The totals cover the private snapshot namespace under the configured S3 path
prefix, including old contracts and encryption epochs. They exclude assets.
The exporter counts keys without downloading or decrypting objects. These
listings are periodic; totals can change while a listing is in progress.

`chatto_projection_snapshot_storage_refresh_success{backend="s3"}` is `1`
only when the latest inventory completed. It is `0` before the first inventory
or after a failure; snapshot totals are absent in those cases. Use
`chatto_s3_bucket_last_refresh_timestamp_seconds` and
`chatto_s3_bucket_refresh_duration_seconds` to check the shared inventory's
attempt time and duration. Reading metrics does not start an S3 listing.

## Backups

A live server must have backups:

1. Schedule encrypted backups.
2. Decide whether your backups include the encryption keys.
3. Keep backup archives away from the Chatto data directory.
4. Test a restore before you rely on a backup.
5. Set the backup retention to agree with your account deletion policy.

For a small server, the simplest reliable backup includes the keys:

```bash
chatto backup -c chatto.toml --encrypt --include-keys
```

Export the keys separately only when you want different retention and
recovery procedures for them. See [Backup & Restore](/guides/operations/backup-restore/).

## Message Search Provider

The search index contains text from decrypted messages. Keep it on a protected
local volume and do not include it in backups. Chatto rebuilds a missing index.
See [Enabling Search](/guides/operations/search/) for the configuration,
separate provider processes, and index recovery.

## Recovery And Bootstrap

Enable the operator API only when you need local recovery or trusted
automation:

```toml
[operator_api]
enabled = true
socket_path = "/tmp/chatto/operator.sock"
```

Run `chatto operator` as the same OS user as the Chatto process. In a
container, use `docker compose exec` as the `chatto` user. Use it to:

- list users when no admin session is available
- set a password for a user
- create a bootstrap user
- add a verified email address
- assign or revoke a role
- delete an account

<Aside type="danger">
  Operator socket access is root access to Chatto. Do not mount the socket
  into untrusted containers or expose it over TCP.
</Aside>

See [Operator CLI](/guides/operations/operator-cli/) for all commands.

## Upgrade Practice

<Aside type="caution" title="Upgrading from 0.4 to 0.5">
  Stop all 0.4 replicas before you start 0.5. Do not use a rolling deployment.
  Upgrade the bundled frontend at the same time. Some members must sign in
  again.
</Aside>

1. Read the release notes.
2. Make a new backup.
3. On a large server, restore a copy into a test environment and start the
   new version against it.
4. After startup, examine the system diagnostics and projection readiness.
5. Monitor logs and metrics for the first minutes.
6. If you operate bots or custom clients, read the API changes.

To operate more than one replica, see
[Horizontal Scaling](/guides/infrastructure/horizontal-scaling/).

## Community Badges

Chatto can publish [Shields.io](https://shields.io) badges with the number of
members online and registered. Use them in a README or on a website. Badges
are off by default, because they make the size and activity of your community
public.

<Tabs>
<TabItem label="TOML">

```toml
[webserver.shields]
enabled = true
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_WEBSERVER_SHIELDS_ENABLED=true
```

</TabItem>
</Tabs>

Add the badges with Markdown image syntax:

```md
![Chatto online](https://chat.example.com/.well-known/chatto/shields/online.png)
![Chatto registered](https://chat.example.com/.well-known/chatto/shields/registered.png)
```

`online.png` counts users who are Online, Away, or Do Not Disturb.
`registered.png` counts verified accounts. Chatto redirects these URLs to
Shields.io. Shields.io then reads the public JSON endpoints `online.json` and
`registered.json` from the same path on your server.

If your Markdown host does not follow image redirects, link to Shields.io
directly:

```md
![Chatto online](https://img.shields.io/endpoint?url=https%3A%2F%2Fchat.example.com%2F.well-known%2Fchatto%2Fshields%2Fonline.json)
```

You cannot change the labels or colors.
