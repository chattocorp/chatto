A **permission** controls one action, such as posting messages or managing
rooms. A **role** gives a set of permissions to many people. Each permission
setting is **Allow**, **Deny**, or **Inherit**.

## How permissions work

- **Every signed-in person has the `everyone` role.** You can also assign the
  built-in `moderator` and `admin` roles, and your own roles.
- **You set a permission at a scope.** A channel room checks Room, then Room
  group, then Server. A direct message (DM) checks Direct messages, then
  Server. **Inherit** uses the next broader setting of the same user or role.
- **The most specific setting wins for one user or role.** A room setting
  replaces the room-group and server settings of that user or role. It does not
  replace the settings of a different role.
- **A deny wins.** If the user or one of their roles denies an action, Chatto
  denies it, even when a different role allows it.
- **`everyone` is the baseline.** An allow on a user or a named role overrides
  an `everyone` deny only at the same scope or a more specific scope.
- **No setting means no access.**
- **Owners have every permission.** You cannot restrict an owner. A user is an
  owner when they have the `owner` role or a verified email address in
  `owners.emails` in `chatto.toml`. Use `owners.emails` to recover access if
  you lock yourself out.
- **Message access also needs membership.** An account must be a member of the
  room or the DM to read it. Owners and administrators cannot read DMs that
  they are not part of.

| Settings | Result |
| -------- | ------ |
| Server: `everyone` Deny, `admin` Allow | **Allowed** for admins. Both settings are at the same scope. |
| Room: `everyone` Deny. Server: `admin` Allow | **Denied**. The room setting is more specific. Add a room-level allow for `admin`. |
| Server: `admin` Allow, `suspended` Deny | **Denied** for a user with both roles. The deny wins. |

Bots do not get permissions from `everyone` or from other roles. A bot has only
the permissions that you allow directly on the bot, and never more than its
owner has. See [Bot accounts](/guides/integrations/bot-accounts/).

## Built-in roles

Every server has four system roles. You cannot delete them. The order of the
roles does not change which setting wins.

| Role | Defaults on a new server (Server scope) |
| ---- | --------------------------------------- |
| `everyone` | `room.list`, `room.join`, `message.read`, `message.post`, `message.post-in-thread`, `message.attach`, `message.react`, `message.echo`, all `call.*` permissions, `bot.create`, `user.delete-self` |
| `moderator` | `message.manage`, `room.remove-member` |
| `admin` | `server.manage`, `room.create`, `room.manage`, `room.remove-member`, `message.manage`, `role.manage`, `role.assign`, `admin.view-users`, `admin.view-audit`, `user.invite`, `user.manage-accounts`, `user.manage-permissions`, `user.delete-any`, `bot.manage` |
| `owner` | Every permission. You cannot edit these settings. |

Moderators and admins get their member permissions from `everyone`. A new
server also makes the `announcements` room read-only: in that room, it denies
`message.post` for `everyone` and allows it for `admin`.

## Privileged mode

Administrative and moderation permissions stay off during normal chat use. To
use them:

<Steps>

1. Select the shield in your user area.
2. Confirm **Enable privileged mode**.

</Steps>

Privileged mode lasts 15 minutes and does not extend. Select the shield again
to stop it sooner. It applies only to the server
session where you enabled it. The event log records each activation and
deactivation.

Privileged mode turns on permissions, not roles. It applies to each permission
marked **Yes** in the [permission reference](#permission-reference), from any
role or user setting. It also applies to owners. It does not give you
permissions that you do not have.

Without privileged mode, Server Administration stays visible, but its
protected actions are not available. The Moderation page needs server-wide
`room.remove-member`, so it is available only in privileged mode.

Bots do not use privileged mode. To allow a privileged permission for a bot,
you must have that permission active at the same scope. You can remove a bot's
permission without privileged mode.

## Permission reference

Scopes: **S** Server, **G** Room group, **R** Room, **DM** Direct messages.
**All** means all four scopes.

| `server.manage` | S | Yes | Change server settings, such as the name, description, and logo. Includes `server.manage-neighbors`. |
| `server.manage-neighbors` | S | Yes | Manage the public Neighbor directory. |
| `room.list` | S, G, R | | See rooms in the room directory and room lists. |
| `room.join` | S, G, R | | Join channel rooms. |
| `room.create` | S, G | Yes | Create channel rooms. |

| `message.read-interactions` | All | | Read only threads that the account started, where another account mentioned it directly, or where it received a DM. It can read the full thread. |
| `message.post` | All | | Post messages and thread replies. At DM scope, a person can also start DMs. Includes `message.post-in-thread` and `message.post-in-interactions`. |

System diagnostics are only for owners. They are not a permission.

An allow for a broad permission also allows the permissions that it includes. A
deny for an included permission does not restrict that broad allow. For
example, to stop all posting, deny `message.post`, `message.post-in-thread`,
and `message.post-in-interactions`.

Posting also needs room membership and must agree with the room's Threading
Mode. A thread reply also needs read access to the thread. `room.manage` and
`message.manage` bypass Slow Mode. See [Calls](/guides/infrastructure/voice-calls/) for media limits in
calls.

## Direct messages

DMs use the `message.*` and `call.*` permissions at the **Direct messages**
scope. No `room.*` permission applies to DMs. If you do not set a Direct
messages value, the Server setting applies.

- Only people can start a DM. They need `message.post`. A bot cannot start a
  DM, even with `message.post`. After a person starts a DM with a bot, the bot
  can use the DM permissions that you allow for it.
- A participant with `message.manage` can edit or delete the messages of other
  participants. Nobody can moderate a DM that they are not part of.

## Common patterns

### Read-only room

In the room's permissions, deny `message.post` for `everyone`. Allow it for
each role that can post, in the same room. To also stop replies, deny
`message.post-in-thread` and `message.post-in-interactions` for `everyone`. To
stop uploads, deny `message.attach`. Remove the denies to go back to the server
defaults.

### Room for one role only

<Steps>

1. Create a role, such as `engineering`, and assign it.
2. In the room's permissions, deny `room.list` and `room.join` for `everyone`.
3. In the same room, allow `room.list` and `room.join` for `engineering`.
4. Turn on **Universal** to add each member of the role to the room
   automatically.
5. Remove the current room members who must not have access.

</Steps>

Other roles need their own allow in the room. A server or room-group allow does
not override the room-level `everyone` deny. If **Universal** added a user,
removing the role also removes the user from the room.

### Suspend a user

Create a `suspended` role. At Server scope, deny `message.post`,
`message.post-in-thread`, and `message.post-in-interactions`. You can also deny
`message.attach`, `message.react`, and `message.echo`. Assign the role to the
user. Do not add room or room-group allows to this role, because they replace
its server-level denies.

For a single case, set the same denies directly on the user. First remove room
or room-group allows on that user. To remove a user from one room, use
`room.remove-member` instead.

### Delegate one room or room group

Allow `room.manage` for a user or role at Room or Room group scope. Add
`message.manage` and `room.remove-member` at the same scope to let them
moderate. They must enable privileged mode to use these permissions.

### Limit an account to its own conversations

Allow `message.read-interactions` and `message.post-in-interactions` instead of
`message.read` and `message.post`. The account can then read and reply only in
the threads that `message.read-interactions` describes. This is useful for
bots.

## Where to configure permissions

| Task | Where |
| ---- | ----- |
| Create roles and edit their permissions | Server Administration → **Permissions** |
| Assign roles | Server Administration → **Members** → member |
| Set permissions for one user or bot | Server Administration → **Members** → member |
| Set room permissions | The room's settings |
| Set room-group permissions | The room group's settings |
| Set recovery owners | `owners.emails` in `chatto.toml` |

To add an account to a room or remove it, use the **Joined** row in the
account's permissions. You need `user.manage-accounts`, or `room.manage` for
that room. The account does not need `room.join`. This row does not change
permissions or DMs.

## Upgrading from 0.4

Chatto applies default permissions only on a new server. An upgraded server
keeps its permissions and does not get the new defaults, except the call
permissions. Chatto allows each `call.*` permission for `everyone` if you did
not set it before.

Make these changes on an upgraded server:

- **Allow `message.read`** for `everyone` at Server scope. Without it, only
  owners can read messages.
- **Allow `room.remove-member`** for `moderator` and `admin`. `room.ban-member`
  has no effect in 0.5.
- **Allow `user.invite` and `bot.manage`** for `admin`.
- **Allow `bot.create`** for `everyone` if members can create bots.
- **Allow `room.manage`** for delegated room managers. In 0.4, room-group
  management used `role.manage`.
- **Allow `message.post`** for `admin` in the `announcements` room if admins
  must post there. Until you do this, admins cannot post there.
- **Check `message.post`.** It now also allows thread replies, so a deny of
  `message.post-in-thread` does not stop replies.
- **Check `everyone` denies.** An allow on a named role or user at the same or
  a more specific scope now overrides them.

<Aside type="caution">
  Administrators, moderators, and owners must now enable
  [privileged mode](#privileged-mode) to use their administrative permissions.
  This also applies to custom `room.create` grants.
</Aside>
