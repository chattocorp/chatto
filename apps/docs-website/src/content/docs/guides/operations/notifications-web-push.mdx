Chatto has persistent in-app notifications and optional browser Web Push. Operators configure whether push is available; members decide which rooms, threads, and devices should alert them.

## How Notifications Work

Chatto creates persistent notifications for attention-worthy events:

| Event | Default behavior |
| ----- | ---------------- |
| DM messages | Notify the recipient. |
| Root messages in channel rooms | Add a neutral room dot by default. |
| Direct `@username` mentions | Notify the mentioned user. |
| Role, `@all`, and `@here` mentions | Notify matching recipients, with confirmation for broad sends. |
| Replies to your message | Notify you. |
| Followed thread replies | Notify followers. |
| Reactions to your messages | Add a non-interruptive notification by default. |

Notifications are stored for the user, survive browser restarts, sync across tabs and devices, and expire after 90 days. Read and Delete changes synchronize everywhere for that user.

## Notification Centre

Open the notification centre as its own page from the bell in the app header.
It shows one chronological list:

- Unread notifications use orange emphasis for important activity and a neutral indicator for non-interruptive activity such as reactions.
- Read notifications stay in the same chronological list with muted styling and no unread indicator.
- Delete permanently removes a notification from the list.

Related activity is grouped by DM, room, thread, or reacted-to message. Opening a group goes to its newest unread event, or its newest event when everything in the group is read. Reading a room or thread marks covered notifications read. All notifications expire 90 days after their source activity.

## Notification Policy

Members use a matrix to control each notification cause at server, room-group, and room scope. The rows contain the nine notification causes. The columns contain the server, visible room groups and their current-member channel rooms, and current-member direct-message rooms.

| Mode | Effect |
| ---- | ------ |
| Inherit | Use the next broader room-group or server setting. |
| Off | Do not create attention for this cause. |
| Badge | Add only a neutral unread dot. Do not create a notification, play a sound, or send push. |
| Notification | Add an in-app notification. The configured in-app sound can play, but Chatto does not send push. |
| Push notification | Add the same in-app notification and make it eligible for Web Push or native delivery. |

Direct messages, direct mentions, replies, role mentions, `@here`, and `@all` use Push notification by default. Root messages in channel rooms use Badge. Followed threads and reactions use Notification. A message that matches several causes creates one exact output per cause, so each keeps its own policy and triage identity. The client can still consolidate related activity for display.

The server column always shows a concrete setting. If you have not configured a server preference, the matrix shows the product default at full intensity. Select a server cell to cycle through Off, Badge, Notification, and Push notification.

Room-group and room cells cycle through Inherit, Off, Badge, Notification, Push notification, and back to Inherit. A grey crossed bell means Off. A grey filled bell means Badge. An orange bell means Notification. An orange phone means Push notification. An inherited value uses the same icon at reduced intensity.

A Badge setting uses the neutral dot for its room or thread. Thread dots also roll up to their parent room. Reading the room or thread clears covered Badge attention. An orange notification dot takes priority over the grey dot. Badge does not change an operating-system or application-icon badge.

Room dots are controlled only by notification policy. If you set Room messages to Off, ordinary root messages do not add a dot. Chatto still keeps the Message Read Cursor and uses it to place the New messages separator when you open the room.

Channel rooms inherit from their current room group, then from the server. Direct-message rooms inherit directly from the server. A room move changes the policy for future activity only. It does not change earlier notification decisions.

The Direct messages row applies to the server and direct-message rooms. The Room messages row applies to the server, room groups, and channel rooms. Cells outside these scopes are not available.

Use the matrix filter to find a group or room. A room match keeps its parent group visible. A group match keeps all of its current-member room columns visible. The server column always remains in the matrix.

## Do Not Disturb

Do Not Disturb does not discard notifications. Chatto still records the pending notification and updates counts, but suppresses interruptive delivery while the user is in DND:

- no notification sound
- no Web Push delivery
- no active interruption

This preserves "review later" behavior without waking the user's devices.

## Enable Web Push

Web Push is disabled until you provide VAPID keys. Without push config, Chatto hides the push UI entirely.

Generate VAPID keys:

```bash
npx web-push generate-vapid-keys
```

Then configure Chatto:

<Tabs>
<TabItem label="TOML">

```toml
[push]
enabled = true
vapid_public_key = "<generate-me>"
vapid_private_key = "<generate-me>"
vapid_subject = "mailto:admin@example.com"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_PUSH_ENABLED=true
CHATTO_PUSH_VAPID_PUBLIC_KEY=<generate-me>
CHATTO_PUSH_VAPID_PRIVATE_KEY=<generate-me>
CHATTO_PUSH_VAPID_SUBJECT=mailto:admin@example.com
```

</TabItem>
</Tabs>

Use a `mailto:` or HTTPS contact URI for `vapid_subject`. Keep the private key secret and stable; changing it can invalidate existing browser subscriptions.

## Device Behavior

Each browser or installed PWA creates its own subscription for each connected server. A user can have up to 16 active subscriptions on a server, and Chatto attempts every current endpoint for each push. Once any endpoint accepts a notification, Chatto does not retry the complete device set merely because another endpoint failed; this avoids repeatedly alerting healthy devices.

When a user reopens Chatto, the app refreshes the server's stored subscription for that browser. Expired subscriptions are cleaned up automatically when push providers report them as gone.

Chatto sends regular notifications in a declarative-compatible Web Push format, with browser-managed display and app-badge updates where supported. User-visible pushes request high-urgency delivery so mobile push services can wake sleeping devices promptly. Its service worker preserves notification display and click compatibility for browsers that do not handle the declarative payload directly. Read and delete actions synchronize inside Chatto; they do not attempt to retract an OS notification that a browser already displayed. Operators do not need to change VAPID keys or push configuration for this behavior.

For security, Chatto connects directly only to absolute HTTPS push endpoints with public network addresses. It does not follow endpoint redirects or route push delivery through `HTTP_PROXY` or `HTTPS_PROXY`. Standard browser-created subscriptions already meet these requirements; private-network, redirecting, and proxy-only custom push endpoints are unsupported.

On iOS and iPadOS, Web Push works only for supported Home Screen web apps. Safari tabs that are not installed as an app may not receive native push.

<Aside type="note">
  In multi-server use, each remote server registers its own browser subscription under the installed app's origin and continues to use its own VAPID keys. Push traffic travels directly from that server to the browser push service; the server hosting the app does not relay it. This requires a 0.5 client and server.
</Aside>

## Operator Checklist

1. Set `webserver.url` to the public HTTPS origin.
2. Enable Web Push with stable VAPID keys.
3. Keep the service worker path reachable through your proxy.
4. Test from a normal member account, not only an owner account.
5. Test one desktop browser and one mobile installed PWA if mobile push matters.
6. Explain to members that push is per device and opt-in.
