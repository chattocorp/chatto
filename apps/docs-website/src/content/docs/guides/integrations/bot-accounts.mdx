Bot accounts give unattended integrations their own visible user identity and
API credential. They use the normal public ConnectRPC API and realtime
protocol, but start with no permissions and cannot sign in through Chatto's
login forms.

<Aside type="caution">
  A bot API key does not expire automatically. Treat it like a password: keep it
  out of source control, logs, URLs, screenshots, and support requests.
</Aside>

## Create and configure a bot

<Steps>

1. Open **Server Admin → Bots** and choose **Create Bot**.
2. Enter a username ending in `_bot`, a display name, and a name for the first
   API key.
3. Copy the API key before closing the dialog. Chatto cannot show this raw key
   again. Chatto stops in-app navigation until you acknowledge the key. Your
   browser asks for confirmation if you try to unload the page.
4. Open the bot's detail page and enable the server, room-group, or room
   permissions the integration needs.

</Steps>

Every human member receives `bot.create` on a freshly bootstrapped server.
Administrators can remove that default through the permission matrix.
Administrators and effective owners can manage every bot through `bot.manage`;
the creator can always manage bots they already own.

A person with `bot.manage` can also choose **Reassign owner** on a bot's detail
page and select another active human account. Reassignment does not require the
recipient to accept it or hold `bot.create`. It keeps the configured bot
permissions and API keys, but effective permissions immediately follow the new
owner's permission ceiling. If previous custody is a concern, create a new key,
move the integration to it, and revoke the affected key.

Bots do not inherit `everyone`, named roles, or the owner's roles. The bot
matrix exposes a simple enabled/disabled allowlist. A configured permission is
effective only while the owner currently has sufficient effective authority at
that scope; a lock marks one currently blocked by this owner ceiling. The matrix
lists only rooms visible to both the bot owner and the person managing it,
while retaining the directory's complete group layout so permissions such as
`room.create` remain configurable for an empty group.

Channel-room membership alone does not expose messages to a bot. Grant
`message.read` for broad room access. Grant `message.read-interactions` when
the bot must read only complete threads that it started or where another
account directly mentioned it. A direct mention gives access to messages from
before the mention. An effective `message.read` allow includes
`message.read-interactions` for the bot and for its owner. A narrow allow does
not grant broad access. A DM also needs membership and the matching DM-scoped
read permission. Posting remains a separate `message.post` or
`message.post-in-thread` decision.

## Post from an external webhook

Open the bot's detail page and choose **Create Webhook**. Give the webhook a
name that identifies its caller. Copy the complete URL before you close the
dialog. Chatto cannot show the credential again. Chatto stops in-app
navigation while it creates or shows the credential. Your browser asks for
confirmation if you try to unload the page. A bot can have at most 20 active
webhooks.

Create a separate webhook for each external integration. To replace a webhook,
create a new one, move the caller to it, and then revoke the old webhook. You
can revoke one webhook without a change to the other webhooks. The detail page
shows when each webhook was created and approximately when Chatto recorded its
last use. Last-use telemetry is optional. **No use recorded** does not prove
that the webhook was not used. Chatto shows **Temporarily unavailable** if it
cannot read the telemetry.

Send a JSON request with Slack-compatible `text` and `channel` fields:

```http
POST /webhooks/incoming/cht_IW_…
Content-Type: application/json

{"text":"Deployment finished","channel":"R…"}
```

Chatto also accepts `body` instead of `text`, and `room_id` instead of
`channel`. You can put `room_id` in the query string:

```http
POST /webhooks/incoming/cht_IW_…?room_id=R…
Content-Type: application/json

{"text":"Deployment finished"}
```

If you specify more than one body or room field, the values must be equal. Use
a stable room ID, not a room name. Set `"create_thread": true` to start a
thread in a channel room that supports threads. The bot needs `message.post`
and `message.post-in-thread` for explicit thread creation. A room that requires
threads creates one automatically. Direct messages do not support threads.

The bot must already be a room member and have `message.post`. A webhook can
post to a DM only after a human starts that DM with the bot. It cannot start or
find a DM.

A successful request returns HTTP 200 and the plain-text body `ok`. The first
version has no idempotency key. If the caller retries after it loses a
response, Chatto can post the message more than once.

Chatto records the webhook as used after successful credential authentication.
It records this use even if the JSON is invalid or the message operation fails.
The recorded time can be delayed by approximately one minute.

<Aside type="caution">
  The URL contains a credential. Keep it out of source control, application
  logs, screenshots, and support requests. Configure reverse proxies to redact
  `/webhooks/incoming/…` paths.
</Aside>

## Activate a bot from Chatto activity

Use the normal `subscribe_events` realtime subscription. See the
[Realtime Protocol Overview](/guides/integrations/realtime-protocol/) for the
connection and resume model, or follow the
[TypeScript tutorial](/guides/integrations/realtime-typescript/) to build a
small client. Chatto does not use a bot-only realtime channel or a separate
bot-interaction event. The same subscription sends semantic events for all
authorized public activity, including messages, edits, reactions, rooms,
membership, profiles, and calls. Select `LIVE_ONLY` when the bot does not need
an initial current-resource snapshot. Use the
[`RealtimeEvent`](/reference/connectrpc-api/realtime/#chatto-realtime-v1-RealtimeEvent)
reference to select the variants that the bot handles.

Read `NotificationService.ListNotificationOccurrences` and filter by cause when
the integration needs Chatto's attention policy instead of all visible
activity:

| Cause                      | When Chatto creates it                                                     |
| -------------------------- | -------------------------------------------------------------------------- |
| `direct_message_received`  | Another account sends a message in a DM that a human started with the bot. |
| `direct_mention_received`  | Another account directly mentions the bot in a channel-room root or reply. |
| `reply_received`           | Another account replies to a message from the bot.                         |
| `followed_thread_activity` | Another account posts in a thread that the bot follows.                    |

The response can also contain other notification causes that apply to the
account. Ignore causes that the integration does not use.

A delivered direct mention in a channel-room root or reply also attempts to
follow that thread. Thus, a root mention can activate the bot immediately and
later replies can activate it through `followed_thread_activity`. An explicit
unfollow is not replaced. If direct-mention delivery is Off, Chatto creates no
mention occurrence and does not follow the thread. The mention still creates
the interaction relationship that controls narrow read access.

Each occurrence has a stable ID and an exact message reference. Save processed
occurrence IDs because a latest-value replacement can contain an occurrence
more than once. One message can create multiple causes. If the integration
must act only once for each message, also deduplicate by the referenced
`event_id`.

The notification read contains the newest finite page. Read it again after a
disconnect for recovery within the notification retention period. Then use the
message reference with the normal message or thread API. For example, use
`ThreadService.GetThreadEvents` to get the complete thread. The server returns
content only when the bot has current membership, permission, and interaction
access.

## Direct messages

A bot cannot start a DM. This rule also prevents a bot from using
`RoomService.StartDM` to get a self-DM or an existing DM. A permission grant
cannot change the rule.

A human can start a DM that includes the bot. Membership remains necessary.
Grant `message.read`, `message.post`, and `message.post-in-thread` at the
**Direct messages** scope when the bot must run a threaded private
conversation without channel access. The owner must also have each effective
permission at that scope. Messages from another participant create normal
`direct_message_received` occurrences only while the bot can read them.

## Authenticate requests

Send the key as an HTTP bearer credential to the same public API used by other
clients:

```http
Authorization: Bearer cht_BK_…
```

The request is authorized as the bot user. For example, posting a message
requires an explicit effective `message.post` allow and normal room access.
The canonical `User.is_bot` field identifies bot authors to API clients;
the bundled client also shows a robot marker on their avatars, except on
extra-small avatars such as thread participants. The marker uses
soft shading and changes its colours to match the light or dark theme.

A bot API key can update its own login, display name, and bio through
`MyAccountService.UpdateProfile`. It can upload or delete its own avatar through
`UserService.UploadAvatar` and `UserService.DeleteAvatar` when it sends its own
user ID as the target. It cannot target another account, create or manage bots,
revoke keys itself, or enrol a password, browser session, OAuth token, verified
email, or external login identity.

## Create and revoke API keys

A bot can have at most 20 active API keys. Create a named key for each
integration. Names do not need to be unique, but a clear name helps you select
the correct key later. Chatto shows each raw key only once. The bundled client
enables named-key management for Chatto 0.5.0-alpha.4 or later.

To replace one key, create a new key, move the integration to it, and revoke
the old key. Revocation immediately invalidates only the selected key. Realtime
connections that used that key also close. Other API keys and their realtime
connections stay active.

The detail page shows when each key was created and approximately when Chatto
recorded its last use. **No use recorded** does not prove that the key was not
used. Chatto shows **Temporarily unavailable** if it cannot read this optional
telemetry.

Deleting a bot invalidates all of its keys and permanently deletes the account
through the normal account-deletion process. Deleting the human owner also
deletes all bots they still own, so reassign long-lived integrations before
deleting that account.

## API reference

`BotService` exposes bot lifecycle, owner reassignment, independent management
for multiple named API keys, and independent management for multiple named
incoming webhook credentials. The bot can use
`MyAccountService.UpdateProfile` with its API key for self-profile
changes. Avatar mutations use the target-aware `UserService` methods. A raw key
appears only in `CreateBot` and `CreateBotApiKey` responses.
Bot permissions use the same `AdminPermissionService` user-permission RPCs as
human accounts, with the bot's user ID as the target. See the
[BotService reference](/reference/connectrpc-api/bots/),
[UserService reference](/reference/connectrpc-api/users/), and
[AdminPermissionService reference](/reference/connectrpc-api/admin-permissions/).

## Outbound webhooks

Open a bot in **Server Admin → Bots**, then use **Outbound webhook**. Enter
your tool's destination URL and, if required, its complete Authorization header
value. Enable delivery and select **Save endpoint**. Copy the signing secret
if your tool will verify Chatto signatures.

Each bot has one endpoint. It receives new messages that directly mention the
bot and new messages in DMs that include the bot. This includes thread replies.
A DM that mentions the bot produces one delivery with both triggers. Messages
from the bot itself, ordinary channel messages, edits, and reactions do not
activate the webhook. Notification preferences do not affect it.

Chatto does not return the saved URL or Authorization value. To change them,
enter all settings and select **Replace endpoint**. Replacement creates a new
signing secret and cancels pending work for the previous endpoint. Removing the
endpoint also stops delivery.

### Request body

Every request has this structure:

```json
{
  "version": 1,
  "id": "stable-delivery-id",
  "type": "message.created",
  "triggers": ["direct_message", "mention"],
  "occurred_at": "2026-09-05T12:00:00Z",
  "bot_id": "bot-id",
  "room_id": "room-id",
  "thread_root_id": null,
  "message": {
    "id": "message-id",
    "author_id": "author-id",
    "body": "Hello @helper_bot"
  }
}
```

Use `triggers` to route mentions and DMs in your tool. `thread_root_id` is null
for a root message. Attachments and other event types are not included in this
version. Your tool must accept this JSON structure; Chatto does not translate
it to a tool-specific payload.

Return an HTTP 2xx response after you accept the request. Process longer tasks
separately and use the bot API key to reply through the normal API. Chatto does
not interpret the response body.

### Signatures and authentication

Chatto adds these headers:

- `Chatto-Webhook-Id`: the delivery ID from the JSON body.
- `Chatto-Webhook-Timestamp`: Unix time in seconds for this attempt.
- `Chatto-Webhook-Signature`: `v1=` followed by a hexadecimal HMAC-SHA256 value.

To verify the signature, use the signing secret **as its displayed UTF-8 text**
without Base64 decoding. Compute HMAC-SHA256 over the timestamp, a full stop,
and the exact request-body bytes. Compare signatures in constant time. Reject
an old timestamp, for example after five minutes, and deduplicate the delivery
ID. A retry has the same ID and a new timestamp.

A generic tool can authenticate through its own secret URL or the configured
Authorization header. It can ignore the signature headers if it does not
support verification. Keep URL credentials, header values, and the signing
secret private.

### Retries, expiry, and access

Chatto retries transport failures and all non-2xx responses. It never follows
redirects. The default policy permits five attempts within 24 hours of the
source message. The delay starts at 30 seconds and doubles up to 30 minutes.
Each request has a ten-second timeout and cannot run beyond delivery expiry.

Delivery is at least once within these limits. A lost response can cause a
repeat, even if your tool processed the request. Use the delivery ID to avoid
repeating work. Attempts count deliveries to a worker, including deliveries that stop before
HTTP starts. JetStream keeps pending jobs and retry progress across restart. Deliveries can arrive
out of order.

Chatto checks the bot's current access before sending. It skips delivery when
access is lost, the message is unavailable, or the endpoint is replaced. The
body contains the currently readable message text. An edit can therefore
change the body between attempts. The bot page shows the latest recorded failure for the current endpoint.
Successful deliveries and intentional skips are not recorded. Later success
does not clear a previous failure.

Operators can change retry and expiry policy through
[environment variables or TOML](/reference/environment-variables/#outbound-bot-webhooks).
The shared job queue discards any outstanding job after seven days by default,
even if no worker picked it up. This hard retention limit is separate from
webhook expiry and does not produce a failure record. Operators can change it
with `jobs.max_age` or `CHATTO_JOBS_MAX_AGE`.

The default network policy permits public HTTPS destinations. An operator can
allow private networks and HTTP for trusted internal tools.
