Боти дають зовнішнім інструментам змогу публікувати повідомлення й відповідати в розмовах Chatto. Створіть обліковий запис бота, надайте доступ до потрібних кімнат і під’єднайте інструмент за допомогою API-ключа або вебхука. Програму бота ви запускаєте окремо.

Нижче показано налаштування бота, що публікує відомості про розгортання. Вам потрібні дозвіл створювати ботів і доступ до цільової кімнати.

## Виберіть спосіб підключення інструмента

Є три способи підключення. Бот може використовувати кілька одночасно.

- **Вхідний вебхук: ваш інструмент → Chatto.** Надайте службі сповіщень або інструменту автоматизації URL для публікації повідомлень.
- **API-ключ: ваша програма → Chatto.** Надайте програмі бота ключ, щоб вона могла читати повідомлення, надсилати відповіді або виконувати інші дозволені вами операції API.
- **Вихідний вебхук: Chatto → ваш інструмент.** Укажіть Chatto кінцеву точку для сповіщень, коли хтось згадує бота або надсилає йому приватне повідомлення. Інструмент обробляє подію й використовує API-ключ, якщо потрібна відповідь.

Для відомостей про розгортання використовуйте вхідний вебхук. Для бота, що відповідає на згадки чи приватні повідомлення, використовуйте вихідний вебхук для отримання повідомлень і API-ключ для надсилання відповідей.

## 1. Створіть обліковий запис бота

1. Відкрийте **Адміністрування сервера → Боти** на сервері, де працюватиме бот.
2. Виберіть **Створити бота**. У цьому прикладі використовуйте `release-bot` як ім’я користувача й **Оновлення випусків** як відображуване ім’я. Ім’я користувача ідентифікує обліковий запис; відображуване ім’я учасники бачать біля повідомлень.
3. Створіть бота. Chatto покаже API-ключ один раз. Якщо плануєте використовувати API, збережіть ключ у сховищі секретів інтеграції. Після закриття діалогу показати ключ знову не можна.
4. Відкрийте сторінку бота. Додайте короткий опис профілю, наприклад «Публікує результати розгортання з нашого конвеєра випуску».

Якщо **Створити бота** недоступно, попросіть в адміністратора `bot.create`. Володіння ботом дозволяє керувати цим ботом; дозвіл керувати всіма ботами надається окремо.

Якщо інструмент використовує лише вхідний вебхук, API-ключ йому не потрібен. Відкличте невикористаний початковий ключ у **Інтеграції → API-ключі**.

## 2. Надайте доступ до однієї кімнати

Новий бот не має дозволів. Він не успадковує ролі власника або дозволи ролі `everyone`. Приєднання до кімнати й дозвіл публікувати в ній — окремі вимоги.

1. Відкрийте вкладку **Дозволи** бота.
2. Знайдіть стовпець кімнати для відомостей про розгортання.
3. У рядку **Приєднався** вгорі матриці виберіть цю кімнату й підтвердьте зміну членства.
4. Дозвольте `message.post` для цієї кімнати. Не пов’язані із завданням дозволи залиште невстановленими.

Боту розгортання не потрібен доступ на читання. Надайте `message.post` у стовпці кімнати, щоб обмежити публікації цією кімнатою. Дозвіл на рівні сервера діє в різних кімнатах.

Вам також потрібні повноваження додавати бота до кімнати. Архівовані кімнати й блокування в кімнаті можуть перешкоджати приєднанню. Власний дозвіл бота `room.join` призначений для приєднання через API й не замінює рядок **Приєднався**.

### Доступ бота не може перевищувати доступ власника

Кожен дозвіл бота обмежений поточними дозволами власника-людини в тій самій області. Збережений дозвіл може бути неактивним: замок у матриці означає, що дозволи власника блокують його. Якщо власник втрачає доступ, бот теж втрачає цей доступ. Вихід з облікового запису не зупиняє бота.

Для деяких дозволів потрібен привілейований режим. Якщо Chatto просить увімкнути його, зробіть це до надання дозволу.

## 3. Під’єднайте вхідний вебхук

1. Відкрийте **Інтеграції** на сторінці бота.
2. У розділі **Вхідні вебхуки** виберіть **Створити вебхук**.
3. Назвіть його за інструментом, що надсилає запити, наприклад **Конвеєр випуску**.
4. Виберіть кімнату оновлень розгортання як **Цільову кімнату**.
5. Створіть вебхук і скопіюйте повний URL до налаштувань вебхука інструмента. Збережіть частину `?room_id=…` в URL.

Налаштуйте інструмент на надсилання HTTP **POST** із `Content-Type: application/json` і таким тілом:

```json
{
  "text": "Розгортання завершено: версія **0.5** готова до тестування."
}
```

Вибрану кімнату вже вказано в URL, тому поле `channel` у цьому запиті не потрібне. Якщо натомість вибрати **Вибирати в кожному запиті**, додайте `"channel": "YOUR_ROOM_ID"` до JSON. Використовуйте ID кімнати, а не її назву.

Вибір призначення додає ID кімнати до URL. Сторона, що викликає вебхук, може змінити ID й надсилати повідомлення до будь-якої кімнати, де бот може публікувати. Щоб обмежити вебхук однією кімнатою, надайте боту право публікації лише в ній.

## 4. Надішліть тест і перевірте результат

Використовуйте тестову функцію зовнішнього інструмента. Успішний вхідний запит повертає HTTP `200` із текстом `ok`. У Chatto повідомлення має з’явитися у вибраній кімнаті від імені **Оновлення випусків**, із міткою **BOT** і жирним «0.5».

Якщо запит завершився помилкою, перевірте відповідь:

- **`401 invalid_token`:** URL неповний, недійсний або відкликаний. Створіть новий вхідний вебхук, якщо повний URL більше недоступний.
- **`404 channel_not_found`:** перевірте ID кімнати, членство бота, його дозвіл `message.post` і право власника публікувати в цій кімнаті.
- **`400 invalid_payload`:** надішліть коректний JSON із непорожнім текстом повідомлення та ID кімнати. Якщо ID є і в URL, і в тілі, значення мають збігатися. Політика кімнати й обмеження розміру повідомлень також діють.
- **Повідомлення з’являється двічі:** повтор запиту може створити ще одне повідомлення. Вхідні вебхуки не надають ключа ідемпотентності для усунення дублікатів.

Після успішного тесту налаштуйте інструмент на виклик вебхука після завершення розгортання.

## Створіть бота, який відповідає людям

Укажіть у програмі бота його API-ключ Chatto. Зберігайте ключ у секретній конфігурації програми. Запити API використовують заголовок `Authorization: Bearer YOUR_API_KEY` для автентифікації.

Виберіть потрібні боту дозволи:

- **Відповідати лише при зверненні:** надайте `message.read-interactions` і `message.post-in-interactions`. Бот може читати повністю гілки, які він розпочав, гілки з його прямою згадкою та свої приватні повідомлення. Тому згадка бота також може відкрити йому попередні повідомлення в гілці.
- **Читати кімнату, але відповідати лише при зверненні:** надайте `message.read` і `message.post-in-interactions`.
- **Читати всі повідомлення й починати розмови:** надайте `message.read` і `message.post`.

Застосуйте дозволи до потрібних кімнат. Для приватних повідомлень використовуйте область **Приватні повідомлення** в матриці. Дозволи власника й далі обмежують ці права.

### Повідомте програмі, коли відповідати

Якщо програма приймає події вебхуків Chatto:

1. Відкрийте **Інтеграції → Вихідні вебхуки → Створити вебхук**.
2. Введіть назву й загальнодоступну кінцеву точку HTTPS програми.
3. Якщо одержувачу потрібен **Заголовок Authorization**, введіть повне очікуване значення, включно з префіксом на зразок `Bearer`.
4. Скопіюйте секрет підпису до налаштувань одержувача, якщо він перевіряє підписи вебхуків Chatto. Секрет показується лише один раз.
5. Згадайте бота в доступній йому для читання кімнаті або надішліть приватне повідомлення. Перевірте журнали одержувача й відповідь бота в Chatto.

Кінцева точка отримує нові повідомлення з прямою згадкою бота або з його приватних розмов. Звичайні повідомлення кімнати, редагування, реакції та повідомлення самого бота не викликають ці вебхуки. Подальша звичайна відповідь у гілці кімнати також не викликає вебхук, якщо в ній знову не згадано бота.

Одержувач має прийняти подію відповіддю HTTP 2xx, а потім надіслати відповідь у чат через API. Chatto ігнорує тіло HTTP-відповіді. Доставлення може повторюватися, тому одержувач має використовувати ID доставлення, щоб не виконувати одну роботу двічі. Для програми, якій потрібні всі доступні для читання події, використовуйте API реального часу Chatto замість вебхука згадок і приватних повідомлень.

Опис даних події, перевірки підпису й операцій API див. у [довіднику вебхуків ботів](https://docs.chatto.run/reference/bot-webhooks/) і [довіднику API](https://docs.chatto.run/reference/connectrpc-api/).

Вихідний вебхук передає налаштованій кінцевій точці текст повідомлення та ідентифікатори повідомлення, автора, кімнати й бота. Одержувач також бачить вихідну IP-адресу сервера Chatto. Якщо бот пересилає повідомлення постачальнику ШІ або іншому сервісу, поясніть це учасникам до використання бота в їхніх розмовах.

### Якщо бот мовчить

Перевірте, чи отримала програма подію. У вихідному вебхуку відкрийте **Нещодавні помилки**, щоб побачити записані помилки доставлення. Перевірте, що кінцева точка ввімкнена, доступна, приймає налаштовану автентифікацію й повертає 2xx без перенаправлення. Порожній список помилок не доводить успішного доставлення.

Якщо подію отримано, але відповіді немає, перевірте API-ключ програми, операцію відповіді й чинні права бота на читання та публікацію.

## Підтримуйте інтеграцію

- **Заміна облікових даних:** створіть новий іменований ключ або вебхук, оновіть сторону, що надсилає запити, перевірте роботу й відкличте старий. API-ключі не спливають автоматично. Ніколи не вставляйте справжній ключ або URL з обліковими даними в чат чи систему контролю версій.
- **Тимчасова зупинка вихідного доставлення:** виберіть **Призупинити** біля кінцевої точки. **Відновити** дозволяє нові події, але не відтворює період паузи.
- **Передавання бота іншому власнику:** обліковий запис із `bot.manage` може використати **Перепризначити власника**. Чинний доступ бота одразу відповідає доступу нового власника. Наявні ключі залишаються дійсними, тому замініть облікові дані, якщо попередній оператор має втратити доступ.
- **Видалення облікового запису власника:** спочатку передайте ботів, що мають працювати тривалий час. Видалення власника-людини також видаляє належних йому ботів.
- **Покажіть учасникам можливості бота:** відкрийте його профіль і перевірте **Власник** і **Що він може робити**. Перевіряйте доступ після зміни кімнат або власника.
