# Chatto interchange format v1

**Status: draft; initial import implemented, export planned.** This specification and the
[JSON Schemas](../../schema/interchange/v1/) define the contract together.
JSON Schema defines structure. This document defines cross-record rules and
meaning. An archive must satisfy both. See [ADR-119](../adr/ADR-119-portable-history-interchange.md)
and [FDR-053](../fdr/FDR-053-history-import-export.md) for rationale and
operator behavior.

## Purpose and scope

The format transfers readable channel history between platforms. It preserves
known events and explicit final state when a source has incomplete history.
It does not require converters to construct internal Chatto EVT events.

V1 covers human and bot identities, public and private channels, message
content, edits, tombstones, threads, Unicode reactions, membership history,
channel metadata history, files, and user avatars. DMs, roles, grants, credentials, sessions,
read markers, notifications, calls, custom emoji, pins, channel echoes,
and canvases are outside this draft. Producers must declare omitted source data.
An importer must not treat public visibility as permission to grant access or
make a private room public. Chatto destination support can be narrower than
format support; destination validation must reject unsupported cases.

## Directory layout and encoding

```text
export/
  manifest.json
  users.jsonl
  rooms.jsonl
  assets.jsonl
  events.jsonl
  files/
    asset-1.txt
```

All five metadata files are required. JSONL files may be empty. Each nonempty
JSONL file contains one JSON object per line and ends with a newline. LF and
CRLF are accepted. Blank lines, byte-order marks, duplicate object keys,
non-finite numbers, and invalid UTF-8 are invalid. JSON strings must contain
Unicode scalar values, not unpaired surrogates. There are no comments.

Only listed metadata files and asset files are permitted. File references are
relative to the archive root. Symlinks, hard links, devices, path traversal,
absolute paths, and unlisted files are forbidden. Readers must not fetch URLs
or follow links. ZIP packaging is deferred; v1 currently defines directory input.
An importer must apply explicit byte, line, record, and file limits before writes.
An implementation limit must produce an error, never a truncated import.

Records reject unknown fields and unknown event types. There is no opaque
extension payload in v1. A producer must convert unsupported content, declare
its omission, or stop. A consumer must not silently discard a record.

## Manifest

| Field                                    | Meaning                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- |
| `format`, `version`                      | Exactly `chatto-interchange` and integer `1`.                                                |
| `export_id`                              | UUID identifying one immutable archive. A changed archive needs a new UUID.                  |
| `captured_at`                            | Known source capture time, or `null`. Never substitute conversion time.                      |
| `consistency`                            | `consistent` if the source guarantees one capture cut; otherwise `unknown`.                  |
| `source.platform`, `source.workspace_id` | Source provenance; neither value authorizes account linking.                                 |
| `scope.kind`                             | `channels`.                                                                                  |
| `scope.coverage`                         | `all` channels in the source, or `selected`. `rooms.jsonl` enumerates the included channels. |
| `history`                                | `complete` or `partial` supported event history within this scope.                           |
| `omissions`                              | Category, readable reason, and count (`null` when unknown) for each known gap.               |

`complete` means all supported historical transitions in scope are present,
with known times. It does not mean that deleted content is recoverable or that
this is a server backup. `message.snapshot` requires `partial` history. Missing
reaction times, missing edits, and unknown membership history also require
`partial`, with a `history` omission. Missing bytes or readable content require
`files` or `content` omissions respectively. Other excluded data uses the
appropriate omission category, including `unsupported`.

Chatto's exporter must hold a consistent source cut while collecting catalogs,
events, and files. Capturing a timestamp alone does not establish that cut.
A foreign converter can use `consistency: unknown` when the source gives no
guarantee. It must then use partial history and declare the uncertainty as a
history omission. A null capture time also requires unknown consistency.
Snapshots describe the source's observed final state; unknown consistency is
not permission to accept contradictory IDs or broken references.

## Identity, time, and ordering

IDs are opaque, case-sensitive strings. They must be unique within each of
these namespaces: users, rooms, assets, events, and messages. These namespaces
are independent. A message ID is not an edit or reaction event ID. Source IDs
are valid; destination IDs need not match. Do not derive account identity from
an email address or display name.

Read the catalogs before the event file. Catalog references can point to any
catalog row. In `events.jsonl`, file order is authoritative. Message references
must point to an earlier message introduction, except for the introduction's
own `message_id`. A message is introduced by `message.posted` or its first
`message.snapshot`. A second post for that message is invalid.

Historical events have an `occurred_at` UTC timestamp with `Z`, from whole
seconds through nanoseconds. Leap-second notation is not supported. Consumers must validate calendar dates as well as
syntax, preserve precision, and reject timestamps after a known `captured_at`. Do not
sort solely by timestamp: ties and source clock corrections are possible.
Order must preserve known causal dependencies. An unknown operation time must
not be replaced by capture time. Represent its known result with a snapshot.

All events have an `actor_id`: the source initiator, or `null` if unknown.
The actor can differ from the affected user or message author. Snapshots have
`actor_id: null` and `occurred_at: null`; they are observations at the manifest
cut, not timeline activity. A destination's audit actor can be the operator
without replacing source attribution.

## Catalogs

### Users

User records contain `id`, `username` (nullable), `display_name`, `kind`
(`human` or `bot`), `status` (`active`, `deactivated`, or `deleted`), and `emails`.
These values describe the user at capture time. An absent email list does not
invalidate history. Single-character usernames are valid format data; a
destination that cannot represent one must report that before writes.

Optional `avatar_asset_id` references an entry in `assets.jsonl`. The asset holds
the original local image bytes and their integrity metadata. It must exist in
the asset catalog. An absent field makes no claim about the user's avatar.
Chatto fills empty destination avatars and preserves existing ones, including
for accounts matched by email. It processes avatar images through its normal
image pipeline. Avatar imports use permanent retry receipts.

Emails are source claims; the destination defines their trust policy. Chatto's
root-equivalent importer trusts these claims, matches existing accounts by
normalized email, and attaches unowned addresses as verified emails. Shared
source emails resolve to one account. Claims pointing to different existing
accounts fail validation; the importer never merges those accounts. Existing
profiles and credentials stay unchanged. No passwords or invitations are
created. Deleted-user placeholders must not restore erased personal data.

### Rooms

Room records contain final `name`, `topic`, `purpose`, `visibility`, and
`archived` state, plus `id` and `kind: channel`. These final values are
authoritative at capture time. Historical metadata events describe the
timeline; they do not override the catalog after import. When a last known
metadata event contradicts final metadata, history is incomplete: declare a
`history` omission. Do not invent a change event to explain the difference.

### Assets

Assets have `id`, `filename`, `media_type`, and `storage`. Available storage
has a safe `files/` path, byte `size`, and lowercase hexadecimal `sha256`.
The original filename is display metadata only; never use it as a storage path.
Each available asset has one distinct path. Consumers verify bytes against size
and hash before writes. Unavailable storage has only a `reason`; do not insert
zero-byte files as substitutes. Assets can be referenced by multiple events.

Do not put signed URLs, API tokens, cookies, or encryption keys in an archive.
Converters own any source authentication and downloading. Exports contain
plaintext personal data and content; use private filesystem permissions.
Consumers must not include raw record contents or identifiers in logs.

## Event envelope and catalogue

Each record contains `id`, `type`, `room_id`, `actor_id`, `occurred_at`, and
typed `data`. Every referenced user, room, and asset must be in its catalog.

| Type                                                              | Data and meaning                                                                                                  |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `message.posted`                                                  | Introduces `message_id`, `author_id`, `thread_id`, `reply_to`, and `content`. Creation time is the envelope time. |
| `message.edited`                                                  | Replaces the content of an earlier `message_id`; it does not change its author or thread placement.               |
| `message.deleted`                                                 | Marks an earlier `message_id` deleted at the envelope time. It does not remove its identity or reactions.         |
| `message.snapshot`                                                | Introduces or supplies final state for a message whose history is incomplete; fields are described below.         |
| `reaction.added`, `reaction.removed`                              | Changes the Unicode `emoji` reaction of `user_id` on `message_id`.                                                |
| `thread.created`                                                  | Establishes an empty thread on `root_id`, an earlier top-level message.                                           |
| `room.member_joined`, `room.member_left`                          | Records the affected `user_id`. The actor can be an inviter or remover.                                           |
| `room.membership_snapshot`                                        | Final complete `user_ids` membership set for the room. It creates no join/leave timeline activity.                |
| `room.name_changed`, `room.topic_changed`, `room.purpose_changed` | Records the new string `value`.                                                                                   |
| `room.archived`, `room.unarchived`                                | Records an archive transition; `data` is an empty object.                                                         |

`thread_id` is the root message ID, not a separate thread-record ID.
`reply_to` is a quoted/replied-to message ID and is independent of thread
placement. Both fields are required and nullable. A thread root must be
top-level in the same room. A reply target must be in the same room. Deleted
roots remain valid. A first threaded reply establishes its thread if no
`thread.created` exists. A duplicate thread declaration is invalid.

Edits, deletions, and reactions target an earlier message in the same room.
Join/leave records can also contain an optional `data.reactions` array with
the same entries as message snapshots: `emoji` and nonempty unique `user_ids`.
Each emoji has at most one group, and all reactors must exist in the user
catalog. This array records the final known reactions on that membership event;
it does not give reaction times. An absent array makes no claim about reactions.
The `reaction.added` and `reaction.removed` event types still target messages.
An edit after deletion is invalid. Repeated deletion, adding an already present
reaction, or removing an absent reaction is invalid when that state is known.
With partial history, a first reaction removal may have an unknown prior add;
it establishes absence without inventing an add. Membership follows the same
rule: a first leave may lack a prior join. Repeated known joins/leaves are
invalid. Complete history starts with no members or reactions.

### Message content and snapshots

Content has one of three shapes:

- `available`: `body` with `format: chatto-markdown` and `text`, plus `asset_ids`.
- `unavailable`: a reason such as `not_retained`; the message is not known to be deleted.
- `deleted`: no body or asset references; the message is a tombstone.

Posts and edits permit available or unavailable content, not deleted content.
Available content must have non-whitespace text or at least one asset reference.
The Markdown dialect is Chatto's [message formatting](../fdr/FDR-032-message-formatting.md):
`**bold**`, `__underline__`, and `~~strike~~` are distinct. Text alone does not
encode authoritative user mentions. Structured mentions and custom emoji assets are
deferred; converters must declare that loss instead of inventing identities.
No links or media in a body are fetched during import.

A snapshot has the post fields plus `created_at`, `edited_at`, `deleted_at`,
and `reactions`. Timestamps are nullable. A deleted snapshot can have an unknown
`deleted_at`; nondeleted content must have `deleted_at: null`. Reactions are
Unicode sequences or reaction names with nonempty unique `user_ids`; each value
appears once. Reaction names contain 1–128 ASCII letters, digits, underscores,
plus signs, or hyphens, without colons. Names are case-sensitive and remain
unchanged, including unknown names. Clients can show unknown names as `:name:`.
Existing Unicode archives remain supported. Do not normalize away variation
selectors or skin tones. Custom emoji assets are not imported.

At most one message snapshot is allowed per message. It is terminal for
that message's content and reactions: subsequent edits, deletions, or reaction
changes are invalid. Later replies and thread declarations can still refer to
it. When it follows a post, it must retain the same author, room, thread,
reply target, and known creation time. Its final content and reactions replace
the known intermediate state. It must not resurrect a known deleted message.
All supplied message times must be no later than a known capture time; edit/deletion
times cannot precede known creation time or place an edit after deletion.

An exporter must not recover deleted plaintext from old revisions. When a
message is deleted at the cut, its earlier post/edit content must be unavailable
and its final representation must be a tombstone. Omit files that are only
reachable through erased content. This rule preserves deletion across export.

### Final membership

Each room has exactly one `room.membership_snapshot`, after all its join/leave
events. It is the authoritative final set, not a baseline and not a collection
of joins at capture time. Historical timeline entries remain separate from
current access. A complete history must derive exactly that final set. A partial
history may differ, but must declare the history gap. No later membership
events or second membership snapshot are permitted for that room.

## Import, export, and compatibility

`chatto operator import PATH --validate-only` validates archive references, file
integrity, and destination support through the local operator socket without
writes. Normal import performs the same validation before it starts. The first
supported subset and limits are in the [schema guide](../../schema/interchange/README.md).
It accepts a blank destination initially and
does not silently rename identities, relax privacy, or merge accounts.
Declared omissions require `--accept-omissions` for writes. Optional channel and
username prefixes and suffixes apply only to destination names, not source IDs.
The exact naming options are part of the immutable import fingerprint.

The importer owns reference mapping and durable recovery. Repeating the same
immutable export resumes it. A changed record under the same export identity
must fail before another write; new export IDs are not an incremental-update
protocol. Recovery must survive process loss and lost acknowledgements beyond
the ordinary sending collision window. Partial progress is possible; validation
does not make the whole import one transaction. Progress belongs to one
destination and must not be reused elsewhere.

Import establishes history without sending invitations, notifications, webhooks,
or historical activity frames. The generic importer applies this policy; the
existing per-record operator APIs keep their own behavior. Internal event production
must preserve this behavior through replay. Raw input must never be appended
directly to EVT.

The planned `chatto operator export PATH` writes a new directory and refuses an
existing destination. Completion must be distinguishable from a partial export.
An export/import/export round trip preserves represented content, attribution,
timestamps, event order, threads, reactions, tombstones, final membership, and
file bytes, modulo destination IDs. It must not invent missing history. Capture
time and provenance may change. Exact byte identity is not required.

V1 is a draft. Before release, conformance must include real CLI round trips,
snapshot consistency, crash recovery, replay side effects, and deletion privacy.
Tests cover schemas, semantic rules, native import, interruption recovery on a
fresh core, and lost CLI responses. Export round trips remain unimplemented.
A consumer must reject an unsupported format version. Released schemas and
meanings are immutable; a later contract uses a new version and explicit
conversion. No silent downgrade or raw EVT passthrough is allowed.
