Chatto supports local password accounts, external login providers, email
verification and password reset, invitation codes, and owner recovery. This page
also tells you how other Chatto clients connect to your server.

## Choose Your Account Model

| Model | Setup |
| ----- | ----- |
| Local accounts only | Configure [transactional email](#transactional-email) for verification and password reset. |
| Invite-only server | Set [invite-only account creation](#invite-only-account-creation). |
| Organization SSO | Add [login providers](/guides/integrations/external-login-providers/) and turn off [password login](#sso-only-login). |
| Mixed community | Keep password accounts and add selected login providers. |

## Deactivate an Account

Upgrade every server replica to a version that supports account deactivation
before you use this feature. Older replicas do not enforce the access flag.

To stop access and keep the user's data, open **Server configuration → Members**,
select the member, and open **Account → Deactivate Account**. You need
`admin.view-users` and `user.manage-accounts`. Confirm the account and effect.
You cannot deactivate your own account or an owner account.

One-to-one conversations show a notice when the other account is deactivated
and stop accepting new messages.
Deactivated accounts do not appear in new-conversation, mention, or invitation
pickers. Existing messages and profiles remain readable. Reactivation restores
these controls without a page reload. Administrative details remain private.

Deactivation blocks sign-in and invalidates existing sessions. The profile,
messages, files, memberships, and roles remain intact. The user's bots also
lose access. Existing call connections are removed at the next participant
permission check. The account's login and email addresses remain claimed.

Select **Reactivate Account** to permit access again. The user must sign in
again; old human sessions stay invalid. Bot credentials work again after
reactivation. Account deletion remains a separate action that removes data.

## SSO-Only Login

Configure and test at least one login provider first. Then disable password
sign-in and email/password registration on every replica:

<Tabs>
<TabItem label="TOML">

```toml
[auth]
direct_login = false
direct_registration = false
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_AUTH_DIRECT_LOGIN=false
CHATTO_AUTH_DIRECT_REGISTRATION=false
```

</TabItem>
</Tabs>

With `direct_login = false`, the login page shows only the configured
providers, and the password login endpoint returns `403`. Existing sessions
stay valid. `direct_registration` controls registration separately.

Password changes and resets are unavailable while password login is disabled.
Stored passwords and local operator recovery remain available. Before you disable
password login, link the owner account to a working provider. An old or removed
provider link does not provide an alternative sign-in method.

<Aside type="caution">
  If no provider works, signed-out users cannot sign in. Keep an operator
  recovery path, such as the [Operator CLI](/guides/operations/operator-cli/).
</Aside>

If a provider's issuer changes, use the
[operator identity commands](/guides/operations/operator-cli/#recover-access-after-an-oidc-issuer-change)
to link the verified current identity to each original account. Password login
can remain disabled.

## Transactional Email

Chatto sends email for registration codes, email verification, and password
reset. Configure a transport before you invite members. SMTP is the default.
Use JMAP only when your mail provider supports JMAP submission with a bearer
token.

<Tabs>
<TabItem label="TOML">

```toml
[smtp]
enabled = true
host = "smtp.example.com"
port = 587
tls = "mandatory"
username = "chatto@example.com"
password = "<generate-me>"
from = "Chatto <chatto@example.com>"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_SMTP_ENABLED=true
CHATTO_SMTP_HOST=smtp.example.com
CHATTO_SMTP_PORT=587
CHATTO_SMTP_TLS=mandatory
CHATTO_SMTP_USERNAME=chatto@example.com
CHATTO_SMTP_PASSWORD=<generate-me>
CHATTO_SMTP_FROM="Chatto <chatto@example.com>"
```

</TabItem>
<TabItem label="JMAP (TOML)">

```toml
[email]
transport = "jmap"

[email.jmap]
session_url = "https://mail.example.com/.well-known/jmap"
access_token = "<generate-me>"
from = "Chatto <chatto@example.com>"
```

</TabItem>
<TabItem label="JMAP (Environment)">

```bash
CHATTO_EMAIL_TRANSPORT=jmap
CHATTO_EMAIL_JMAP_SESSION_URL=https://mail.example.com/.well-known/jmap
CHATTO_EMAIL_JMAP_ACCESS_TOKEN=<generate-me>
CHATTO_EMAIL_JMAP_FROM="Chatto <chatto@example.com>"
```

</TabItem>
</Tabs>

Use `smtp.tls_server_name` only when the certificate name is different from
the SMTP host. Use `smtp.tls_skip_verify` only for a trusted internal mail
server.

For JMAP, the `from` address must match a sending identity. Chatto finds the
account, identity, and Drafts mailbox automatically. To select different ones,
set `email.jmap.account_id`, `identity_id`, or `draft_mailbox_id`. The session
URL and the API URL must use HTTPS. A successful submission means that the
provider accepted the email, not that the email arrived.

## External Providers

Use [Login Providers](/guides/integrations/external-login-providers/) to configure
provider IDs, callback URLs, claims, and role mappings. Keep provider IDs stable
after accounts are linked. Chatto does not merge accounts by email address.

## Verified Email Addresses

An account can have multiple verified email addresses. Chatto sends account email
to the primary address. Sign-in, password reset, and owner matching accept all
verified addresses. Configure transactional email before members need verification
or password recovery.

## Invite-Only Account Creation

Open **Server Admin → Registration → Account creation** and select **Invite Code
Required**. This needs `server.manage`. Registration is open by default; changes
apply to all replicas without a restart.

The policy applies to email/password registration and provider auto-provisioning,
including signups already in progress. It does not affect existing accounts or
accounts that operators create. Chatto consumes a code only after successful
account creation. Each code permits one account and expires after seven days.

Grant `user.manage-invites` to administrators who manage all codes. Grant
`user.invite` only to members who can issue and revoke their own codes. The
**Server Admin → Invites** page provides these actions. Invitation managers need
privileged mode; members who manage only their own codes do not.

A code grants admission to anyone who has it. Do not put codes in logs or URLs.
Keep `core.secret_key` stable on all replicas and after a restore. A change makes
existing invitation credentials invalid.

See the [invitation API reference](/reference/connectrpc-api/admin-invitation-codes/)
for automated invitation management.

## Owner Recovery

```toml
[owners]
emails = ["admin@example.com"]
```

A user becomes an owner only after they verify one of these addresses. Owners
have every normal permission, and role denies cannot lock them out.

<Aside type="tip">
  Keep at least one owner email that the server operator controls. Do not
  depend only on an account at an external login provider.
</Aside>

## Password Managers

Chatto publishes `/.well-known/change-password` on each server origin. A
password manager uses this URL to open **Settings → Account**. A signed-out
user goes to account settings after sign-in.

If your reverse proxy handles `/.well-known` paths, forward
`/.well-known/change-password` to Chatto. Keep `404` responses for unknown
well-known paths. A separately hosted Chatto client does not publish this URL.
See the [W3C specification](https://www.w3.org/TR/change-password-url/).

## Sessions And Logout

The bundled client on your server origin uses an `HttpOnly` session cookie.
Other clients get a short-lived access token and a refresh credential. They
renew the session in the background. A session that is not used for one full
`auth.token_ttl` period expires, and the user must sign in again.

A password change, a password reset, or account deletion makes older sessions
invalid. Removing a login provider from an account keeps its sessions. See
[Security & Privacy](/guides/operations/security/#accounts-and-sessions) for
the durations.

## Clients From Other Origins

Members can add your server to a Chatto client on a different origin, such as
the client of another Chatto server or Chatto Desktop. You do not have to
configure this. There is no allowlist.

Each client identifies itself with a Client ID Metadata Document (CIMD). The
bundled client publishes its document at `/oauth/frontend-client-metadata.json`
and uses this HTTPS URL as its OAuth `client_id`. Your server gets and validates
the document, including the exact callback URL. The member then approves the
client, and the client gets a short-lived access token and a refresh
credential.

Requests from other origins cannot use session cookies. They must send the
bearer token.

Both servers must run Chatto 0.5 or later. Your server gets metadata documents
only from public HTTPS addresses. It does not follow redirects, and it rejects
large responses and private network addresses.

<Aside type="caution">
  A CIMD identity is not an endorsement. Any application can publish a document
  and ask a member for access. Tell members to approve only clients that they
  recognize.
</Aside>

Chatto Desktop uses the built-in `chatto://desktop` identity. Other native
clients publish HTTPS metadata with `application_type` set to `native`, and a
custom URL scheme or a local HTTP callback on `127.0.0.1`, `[::1]`,
`localhost`, or a name below `.localhost`. Only `127.0.0.1` and `[::1]`
callbacks can use a different port at runtime. Chatto matches the path and
query exactly and does not accept wildcards. For a local callback, the consent
page shows a warning, and the member must approve each authorization again.

The bundled client can also run on a local address of the member's computer,
for example a development server on `localhost`. Your server cannot get a
metadata document from that address. To let such a client sign in, set
`auth.loopback_client_enabled = true`. The client then uses the built-in
`chatto://loopback` identity. The list of OAuth clients shows it as
"Unverified local app" and does not show the local addresses of members.

<Aside type="caution">
  Any program on the member's computer can use this identity. Enable it only
  when your members need a local client, for example to develop Chatto.
</Aside>

Chatto accepts the bundled client's callback path on each local address, with
any port, over HTTP or HTTPS. The path and query must match exactly. As for
other local callbacks, the consent page shows the local address, and the
member must approve each sign-in. A session of this client ends at most 24
hours after sign-in and does not renew. When you disable the setting, existing
sessions of this client also stop working.

## Manage OAuth Clients

After a first successful authorization, the client appears under **Server
settings → Security → OAuth clients**. The list shows the client name and
identity, callback origins, the number of users, and the latest authorization.

| Policy | Effect |
| ------ | ------ |
| Default | Members can approve the client. |
| Trusted | A label only. Members must still approve the client. |
| Blocked | Chatto stops new authorizations, makes the client's tokens invalid, and closes its realtime connections on all replicas. |

Blocking a client does not end the same user's sessions in other clients.

## Additional Origins For The Bundled Client

Use `webserver.allowed_origins` only when a reverse proxy serves the bundled
client of this server on an additional origin:

<Tabs>
<TabItem label="TOML">

```toml
[webserver]
url = "https://chat.example.com"
allowed_origins = ["https://chat.example.org"]
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_WEBSERVER_URL=https://chat.example.com
CHATTO_WEBSERVER_ALLOWED_ORIGINS=https://chat.example.org
```

</TabItem>
</Tabs>

Each origin can then use session cookies and publishes its own client metadata.
Other hosts get no metadata document. This setting does not authorize clients
from other servers. They do not need it.

- Use exact origins. Do not add a path, query, or fragment.
- Do not configure HTTP and HTTPS origins with the same host.
- Do not use `*`. It permits none of these behaviors.
