By default, Chatto runs as one process with an embedded NATS server. This is
sufficient for small and medium communities. To get more capacity or
redundancy, run several Chatto server processes on an external NATS cluster.

Chatto server processes keep no local state. All persistent data is in NATS
JetStream, so any replica can serve any request.

| Layer | What you scale | Result |
| ----- | -------------- | ------ |
| Chatto replicas | `chatto run` server processes | More web, API, and realtime capacity. Rolling deploys. Redundancy if a process fails. |
| NATS cluster | NATS servers with JetStream | More storage and broker capacity. Data survives if a NATS node fails. |

<ArchDiagram />

## Requirements

- An external NATS deployment with JetStream. Use a cluster of 3 or more nodes
  for high availability. One external NATS server lets replicas share data, but
  it is a single point of failure.
- A load balancer that supports WebSockets, such as Caddy, nginx, or Traefik.
- The same secrets and public URL on all server processes.

## Configuring Chatto for Multiple Replicas

Disable embedded NATS and connect every server process to the cluster:

<Tabs>
<TabItem label="TOML">

```toml
[nats]
replicas = 3

[nats.embedded]
enabled = false

[nats.client]
url = "nats://nats-1:4222,nats://nats-2:4222,nats://nats-3:4222"
auth_method = "token"
token = "<generate-me>"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_NATS_REPLICAS=3
CHATTO_NATS_EMBEDDED_ENABLED=false
CHATTO_NATS_CLIENT_URL=nats://nats-1:4222,nats://nats-2:4222,nats://nats-3:4222
CHATTO_NATS_CLIENT_AUTH_METHOD=token
CHATTO_NATS_CLIENT_TOKEN=<generate-me>
```

</TabItem>
</Tabs>

List all NATS nodes in the URL. If one node is down, the client connects to a
different node. For other authentication methods, see
[Environment Variables](/reference/environment-variables/#client).

<Aside type="caution">
  All server processes must use the same `webserver.cookie_signing_secret`,
  `webserver.cookie_encryption_secret` (when you set it), `core.secret_key`,
  and `core.assets.signing_secret`. If the values are different, cookies,
  sessions, invite links, and asset URLs from one replica fail on a different
  replica.
</Aside>

## What You Need to Keep Consistent

| Setting | Must match? | Used for |
| ------- | ----------- | -------- |
| NATS client URL and credentials | Yes | Connection to the same NATS deployment |
| `nats.replicas` | Yes | JetStream replica count |
| `webserver.url` | Yes | Absolute links |
| `webserver.cookie_signing_secret` | Yes | Browser-flow cookies and CSRF proofs |
| `webserver.cookie_encryption_secret` | Yes, when set | Browser-flow cookie encryption |
| `core.secret_key` | Yes | Sessions, tokens, OAuth codes, account flows, and invite links |
| `core.assets.signing_secret` | Yes | Asset URLs |
| `livekit.server_id` | Yes, in one Chatto server | LiveKit room names |

## Scaling NATS Itself

Give each NATS node a configuration file. Use a unique `server_name` and the
same `routes` list on each node:

```
server_name: nats-1
listen: 0.0.0.0:4222

jetstream {
  store_dir: /data/jetstream
  max_mem: 1G
  max_file: 50G
}

cluster {
  name: chatto
  listen: 0.0.0.0:6222
  routes: [
    nats-route://nats-1:6222
    nats-route://nats-2:6222
    nats-route://nats-3:6222
  ]
}

authorization {
  token: "<generate-me>"
}
```

With Docker Compose, give each node its own configuration file and data volume:

```yaml
services:
  nats-1:
    image: nats:latest
    command: ["--config", "/etc/nats/nats.conf"]
    volumes:
      - ./nats-1.conf:/etc/nats/nats.conf:ro
      - nats1_data:/data
  # Add nats-2 and nats-3 with their own files and volumes.
```

For TLS, route authentication, and cluster sizing, see the
[NATS clustering](https://docs.nats.io/running-a-nats-service/configuration/clustering)
and
[JetStream clustering](https://docs.nats.io/running-a-nats-service/configuration/clustering/jetstream_clustering)
documentation.

## JetStream Replication

`nats.replicas` sets how many copies NATS keeps of each Chatto stream, KV
bucket, and object store. The value applies to all of them. Use an odd number
for quorum:

| `nats.replicas` | NATS nodes | Tolerates | Use |
| --------------- | ---------- | --------- | --- |
| `1` (default) | 1 or more | No node failure | Development, one node |
| `3` | 3 or more | 1 node failure | Production |
| `5` | 5 or more | 2 node failures | Critical deployments |

<Aside type="caution">
  Replication multiplies storage. With `replicas = 3`, NATS stores each byte
  three times. Attachments are in NATS unless you use
  [S3 storage](/guides/infrastructure/media-attachments/), so large
  communities should move them to S3.
</Aside>

Presence data is in memory only. If NATS loses it, Chatto builds it again
automatically.

## Load Balancing

- Use round-robin. Session affinity is not necessary.
- Make sure that the load balancer supports long-lived WebSocket connections.

The [Docker Compose guide](/guides/deployment/docker-compose/) includes a Caddy
configuration for this.

## Health Checks

| Endpoint | Probe | Returns 200 when |
| -------- | ----- | ---------------- |
| `GET /readyz` | Readiness and startup | NATS is connected, JetStream is available, and recovery is complete |
| `GET /healthz` | Liveness | The NATS client can still recover in its five-minute grace period |

During a NATS failover or a short outage, `/readyz` fails and `/healthz` stays
healthy. The load balancer stops sending traffic to the replica, but the
replica does not restart. If the NATS client closes permanently, or recovery
stays stuck for five minutes, both endpoints fail and the orchestrator can
restart the replica.

### Docker Compose

```yaml
chatto:
  image: ghcr.io/chattocorp/chatto:latest
  deploy:
    replicas: 3
  healthcheck:
    test: ["CMD", "wget", "-q", "--spider", "http://localhost:4000/readyz"]
    interval: 5s
    timeout: 3s
    retries: 3
```

To change the number of replicas at any time:

```bash
docker compose up -d --scale chatto=5
```

## Kubernetes

Chatto runs on Kubernetes. There are no maintained manifests or Helm charts
yet. Use the configuration on this page, and the
[Docker Compose guide](/guides/deployment/docker-compose/) as the most complete
example. You need:

- One or more Chatto replicas with the `ghcr.io/chattocorp/chatto` image.
- An external NATS cluster with JetStream. See
  [NATS on Kubernetes](https://docs.nats.io/running-a-nats-service/nats-kubernetes).
- The same secrets on all replicas, for example from one Kubernetes Secret.
- An ingress for HTTP and WebSocket traffic.
- Optional services: LiveKit, SMTP or JMAP, Web Push, and S3-compatible
  storage.

Use these probes:

```yaml
readinessProbe:
  httpGet:
    path: /readyz
    port: 4000
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /healthz
    port: 4000
  periodSeconds: 10
startupProbe:
  httpGet:
    path: /readyz
    port: 4000
  failureThreshold: 15
  periodSeconds: 2
```

## Voice and Video Calls with Multiple Server Processes

If you use LiveKit, set the same `livekit.server_id` on all replicas of one
Chatto server:

```bash
CHATTO_LIVEKIT_SERVER_ID=server-1
```

Chatto adds this value to LiveKit room names. If replicas use different
values, members on different replicas can join different LiveKit rooms for the
same Chatto room. Use a different value only for a different Chatto server
that shares the same LiveKit cluster.

## Failure Scenarios

| Failure | Effect | Recovery |
| ------- | ------ | -------- |
| One Chatto replica | The load balancer sends traffic to the other replicas. | Automatic |
| A minority of NATS nodes (for example, 1 of 3) | Short leader election. No data loss. Reads and writes continue. | Automatic |
| A majority of NATS nodes | NATS rejects writes because there is no quorum. Some reads can work. | Start the nodes again |
| All NATS nodes | Full outage | Start the cluster again, or [restore from a backup](/guides/operations/backup-restore/) |
