Chatto can transcode uploaded videos into multiple quality renditions for adaptive HLS playback. When a user uploads a video, the server stores HLS segments and a thumbnail, generates playlists on demand, and serves them through a built-in video player. Processed video audio is normalized to AAC stereo for consistent browser playback, including for uploads with unusual multichannel layouts.

## Prerequisites

Video processing requires **ffmpeg** and **ffprobe** to be installed on the server. The official Chatto Docker image includes both.

If you're running Chatto outside Docker, install ffmpeg through your system's package manager:

```bash
# Debian/Ubuntu
apt install ffmpeg

# macOS (Homebrew)
brew install ffmpeg

# Alpine
apk add ffmpeg

# FreeBSD
pkg install ffmpeg
```

## Enabling Video Processing

Add the following to your `chatto.toml`:

```toml
[video]
enabled = true

[asset_processing]
enabled = true
```

Or set the environment variable:

```bash
CHATTO_VIDEO_ENABLED=true
CHATTO_ASSET_PROCESSING_ENABLED=true
```

`video.enabled` allows uploads and enqueues their durable processing work.
`asset_processing.enabled` separately starts the built-in worker under
`chatto run`. Fresh configurations created by `chatto init` already set the
worker flag to `true`. Chatto auto-detects `ffmpeg` and `ffprobe` from `PATH`.

<Aside>
  When video uploads are disabled (the default), Chatto rejects new video uploads in the composer and API. Enabling uploads accepts videos and queues them for transcoding, adaptive playback, and thumbnail generation.
</Aside>

## Configuration Options

Video upload policy lives under `[video]`:

| Setting | Default | Description |
|---------|---------|-------------|
| `enabled` | `false` | Allow video uploads and enqueue processing work |
| `max_upload_size` | `100 MB` | Max upload size for video files |

Worker composition and execution settings live under `[asset_processing]`:

| Setting | Default | Description |
|---------|---------|-------------|
| `enabled` | `false` | Start the built-in worker inside `chatto run`; generated configs set it to `true` |
| `ffmpeg_path` | auto-detect | Path to `ffmpeg` binary |
| `ffprobe_path` | auto-detect | Path to `ffprobe` binary |
| `max_concurrent_jobs` | `2` | Max concurrent jobs in each worker process |
| `temp_dir` | system temp | Directory for temporary transcoding files |

See the [Environment Variables](/reference/environment-variables/#asset-processing) reference for the full list.

### Running Workers Separately

For larger installations, keep video uploads enabled but move ffmpeg work out
of the API process:

```toml
[video]
enabled = true

[asset_processing]
enabled = false
max_concurrent_jobs = 4
```

Then start one or more workers with the same Chatto configuration:

```bash
chatto asset-processing --config chatto.toml
```

The `asset_processing.enabled` flag only controls composition under
`chatto run`; invoking `chatto asset-processing` explicitly always runs the
worker. Standalone workers connect to the existing NATS account and asset
backend. Set `nats.client.url`; if the main process uses embedded NATS, expose
its TCP port first. Multiple workers share one durable queue, so each
processing request is delivered to one worker at a time and is redelivered
after an interrupted attempt. The API continues accepting messages while
workers are offline, with their videos remaining in the processing state.

### Upgrading from the Process-Local Worker

<Aside type="caution">
  Do not start the durable worker while any older Chatto replica still runs the
  process-local video callback. Both generations could receive the same request
  and transcode it concurrently.
</Aside>

Use a two-stage rollout when upgrading a multi-replica installation from a
version without `chatto asset-processing`:

1. Upgrade every Chatto replica with `asset_processing.enabled = false`. Older
   replicas keep processing their own posts during the rolling window; upgraded
   replicas safely leave new work in the durable queue.
2. After the final older replica has stopped, enable the embedded worker or
   start one or more standalone `chatto asset-processing` processes.

Existing configuration files default the new worker setting to `false`, which
makes the first stage safe. Fresh files generated by `chatto init` enable it
because a new installation has no callback-era replicas.

### Tuning Concurrency

Each transcoding job uses significant CPU. The default of 2 concurrent jobs is conservative. On a dedicated server with more cores, you can increase this:

```toml
[asset_processing]
max_concurrent_jobs = 4
```

One processing attempt has a 30-minute safety budget. Exceeding it records a
failed outcome instead of repeating the same expensive transcode forever;
stopping a worker still leaves its in-progress delivery retryable.

### Custom Binary Paths

If `ffmpeg` and `ffprobe` aren't in your `PATH`, specify their locations explicitly:

```toml
[asset_processing]
ffmpeg_path = "/usr/local/bin/ffmpeg"
ffprobe_path = "/usr/local/bin/ffprobe"
```

## How It Works

1. A user uploads a video through the chat composer
2. The original file is stored immediately
3. The message and its durable processing request commit atomically
4. The video appears with a "Processing..." indicator
5. A worker receives the request from JetStream and creates temporary MP4 renditions, packages them into six-second HLS segments, and generates a thumbnail
6. Once processing completes, Chatto generates authorised playlists on demand and the player uses adaptive HLS playback

If processing fails (e.g. corrupt file, unsupported codec), the user sees an error message and can try uploading again.

## Storage Considerations

Video transcoding persists the original upload, a thumbnail, and HLS segments. The temporary MP4 renditions and generated playlists do not consume durable asset storage. If you expect significant video usage, consider:

- **Using S3 storage** for assets (`core.assets.storage_backend = "s3"`) to avoid filling up NATS JetStream storage
- **Providing a fast temp directory** with enough free space for in-progress transcoding jobs

Processed videos are seekable on both NATS ObjectStore and S3 because HLS uses bounded segments instead of byte ranges into one large object. Videos processed before HLS support are not backfilled; they continue using their existing MP4 variants.

<Aside type="caution">
  During an upgrade to an HLS-capable release, update every Chatto replica behind the same endpoint before allowing new video uploads. Older replicas cannot expose HLS metadata or serve the playlist and segment routes required by newly processed HLS-only videos.
</Aside>
