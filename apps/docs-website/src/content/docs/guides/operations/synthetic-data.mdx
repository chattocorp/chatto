---
title: Synthetic data
description: Create reproducible users, channels, messages, and thread replies for development and testing.
---

Create synthetic conversations on a running development server:

```sh
chatto operator seed --seed 42 \
  --users 20 --rooms 5 --messages 200 --thread-replies 40 --json > seed.json
```

This command requires a build with `bootstrap` or `test_endpoints` and an enabled
[Operator API](/guides/operations/operator-cli/). The seeding command and service
are absent from release builds. The operator service is available only through
the private Unix socket. Pass `--operator-socket PATH` to select another socket.

## Choose a dataset

| Option | Default | Meaning |
| --- | --- | --- |
| `--seed` | `1` | Integer that controls generated content and relationships |
| `--users` | `20` | Passwordless accounts, from 1 to 5000 |
| `--rooms` | `5` | Channels, from 1 to 100 |
| `--messages` | `200` | Total posts, including thread replies, from 0 to 100000 |
| `--thread-replies` | `0` | Posts that reply to generated root messages |
| `--timeout` | `10m` | Maximum time to wait for the command |
| `--json` | Off | Print the resource manifest instead of a count summary |

All generated users join all generated channels. The user count multiplied by
the room count must not exceed 25000 memberships. Thread replies require at least
one root message. Each reply selects one generated root in the same channel.
The message count is a total for the dataset, not a count per user or channel.
Random selection can leave a user or channel without messages.

The pinned [gofakeit](https://github.com/brianvoe/gofakeit) library generates names,
usernames, room topics, descriptions, and sentence text. Authors, channels, and
thread links vary with the seed. Visible data has no dataset prefix or test marker.
Use the returned resource IDs and text for test selectors.
This version does not generate attachments, reactions, DMs, or backdated history.

## Use the result

The JSON manifest contains the generator version, seed, and resource
lists in creation order. Each message includes its ID, author ID, channel ID,
body, and optional thread root ID. Root messages precede thread replies.

Use the same generator version, seed, and counts to reproduce logical content
on a fresh server. Zero is also a reproducible seed. IDs and timestamps differ.
Each call adds another dataset. Existing login and room-name collisions receive
numeric suffixes. Only the manifest associates resources with a run; Chatto
does not store dataset labels or provide a dataset cleanup command.

Generated accounts have no password and receive no owner role. To sign in as
one, use `chatto operator user set-password USER_ID`. You can also use an existing
account to join the generated channels. Seeding uses normal account, membership,
and message operations, including encryption and permission checks. Existing
server permission changes can therefore prevent message creation.

Existing data is never cleared. Each operation commits separately. A failure,
timeout, or cancellation can leave a partial dataset. Inspect that data before
another run; the command does not resume or retry a run.

## Seed through a test API

A `test_endpoints` build also serves this unauthenticated test endpoint:

```sh
curl --fail-with-body http://localhost:4040/auth/test/seed \
  -H 'Content-Type: application/json' \
  --data '{"seed":42,"users":3,"rooms":2,"messages":20,"threadReplies":5}'
```

Supply `users` and `rooms`. Omitted `seed`, `messages`, and
`threadReplies` are zero. The HTTP wrapper returns the manifest after the serving
projections are current. A failure response can include a `partial` manifest.
Use `POST /auth/test/create-session` with `{"userId":"USER_ID"}` to create a real
cookie session for an existing human test account. Send it from a fresh browser
or request context before loading the app. This avoids password setup and login
when those operations are unrelated to the test.
The operator RPC is `chatto.operator.v1.OperatorSeedService/SeedData` under
`/api/connect/` on the local socket.

The test endpoint is absent from ordinary development and release builds. Use
test-endpoint builds only on isolated test servers. The fixed performance-test
fixture is separate and does not change when this generator changes.

Seeding speeds up scenario setup when it replaces repeated browser interactions
or separate HTTP calls. It does not remove server startup or the interactions
under test. For live-delivery tests, seed the starting state, connect the viewers,
and then perform the action whose delivery you want to verify.
