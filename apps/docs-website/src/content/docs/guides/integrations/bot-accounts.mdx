A bot is a visible user account for an unattended integration. It uses the
normal public ConnectRPC API and realtime protocol. A bot starts with no
permissions and cannot sign in through the login forms.

<Aside type="caution">
  Bot API keys do not expire. Treat keys and webhook URLs like passwords. Keep
  them out of source control, logs, URLs, screenshots, and support requests.
</Aside>

## Create and configure a bot

<Steps>

1. Open **Server Admin → Bots** and select **Create Bot**.
2. Enter a username and a display name.
3. Copy the API key before you close the dialog. Chatto cannot show it again.
4. Open the detail page of the bot. Enable the server, room-group, or room
   permissions that the integration needs.
5. Enable `room.join` for the rooms that the bot needs. In the **Joined** row
   at the top of the matrix, select each room to add the bot, and confirm.
   Clear a room to remove the bot.

</Steps>

On a new server, every human member has `bot.create`. Administrators can
remove this default in the permission matrix. The creator of a bot can always
manage it. Accounts with `bot.manage` can manage all bots and can select
**Reassign owner** to give a bot to another active human account. Reassignment
keeps the permissions and API keys of the bot. If the previous owner must lose
access, create a new key and revoke the old one.

When you delete the owner account, Chatto also deletes all bots that the
account owns. Reassign long-lived bots first.

## Grant permissions

Bots do not inherit `everyone`, named roles, or the roles of their owner. The
bot matrix is an allowlist. A permission is effective only while the owner also
has it at that scope. A lock icon marks a permission that the owner ceiling
blocks. If the owner loses a permission, the bot also loses it. Bots do not
need privileged mode, and they keep working while the owner is signed out.

To grant a permission that requires elevation, activate privileged mode. You
must have that permission active at the target scope. Removal of a grant does
not require activation.

Room membership alone does not let a bot read messages. Grant one read
permission:

- `message.read` reads all messages in the room. It includes
  `message.read-interactions`.
- `message.read-interactions` reads only complete threads that the bot
  started, where another account mentioned it directly, or where it received a
  DM. A mention also gives access to older messages in that thread.

Grant one post permission:

- `message.post` posts root messages and thread replies.
- `message.post-in-thread` posts replies in all readable threads.
- `message.post-in-interactions` posts replies only in the threads that
  `message.read-interactions` allows.

For a bot that reads all messages but replies only when someone speaks to it,
grant `message.read` and `message.post-in-interactions`.

You can add your own bots to rooms without `room.manage`. Room suspensions and
archived rooms prevent joining. Universal-room membership is automatic.

## View a bot's access

Open the profile pane of the bot. **Owned by** shows its human owner. **What
it can do** lists its effective permissions, such as **Read all messages** and
**Reply in threads**. All signed-in members can see this summary, but it shows
room names only to members who can see those rooms. Owners and managers can
expand **Inactive grants** to see saved grants that the owner ceiling blocks.

## Authenticate requests

Send the API key as a bearer credential:

```http
Authorization: Bearer cht_BK_…
```

Chatto authorizes the request as the bot user. For example, a post needs an
effective `message.post` and normal room access. API clients can identify bot
authors with `User.bot`. The bundled client shows a **BOT** label. This label
does not mean that the account is verified.

A bot can change its own profile with `UserService.UpdateUserProfile`, and its
own avatar with `UserService.UploadAvatar` and `UserService.DeleteAvatar`. Send
the user ID of the bot as `user_id`. The bot cannot change other accounts,
manage bots or keys, or add a password, session, OAuth token, email, or
external login.

The owner of the bot can also change its display name, username, bio, and
avatar. Open the bot in **Server Admin → Bots**, or call the same `UserService`
methods with the user ID of the bot. Members with `bot.manage` or
`user.manage-accounts` can do this for all bots.

`BotService` manages bots, owners, API keys, and incoming webhooks. To read
the effective permissions of a bot, use
`PermissionService.ListEffectivePermissions`. To change them, use the
`AdminPermissionService` user-permission methods with the user ID of the bot.
See the [BotService reference](/reference/connectrpc-api/bots/).

## Create and revoke API keys

A bot can have at most 20 active API keys. Create one named key for each
integration. To replace a key, create a new key, move the integration to it,
and revoke the old key. Revocation immediately makes only that key invalid and
closes its realtime connections.

The detail page shows when each key was created and approximately when Chatto
last recorded its use. **No use recorded** does not prove that nobody used the
key.

## Direct messages

A bot cannot start a DM, and no permission changes this. A human can start a
DM that includes the bot. To let a bot talk in DMs without channel access,
grant `message.read` and `message.post` at the **Direct messages** scope. The
owner must have the same permissions at that scope. For a bot that only
replies, `message.read-interactions` at this scope is enough to read its DMs
and receive their outbound webhooks.

## Post from an external webhook

An incoming webhook lets an external tool post as the bot without an API key.

<Steps>

1. Open the detail page of the bot and select **Create Webhook**.
2. Enter a name that identifies the caller. Optionally, select a destination
   channel room. Chatto adds its room ID to the URL.
3. Copy the complete URL before you close the dialog. Chatto cannot show it
   again.

</Steps>

Send JSON with Slack-compatible `text` and `channel` fields:

```http
POST /webhooks/incoming/YOUR_WEBHOOK_CREDENTIAL
Content-Type: application/json

{"text":"Deployment finished","channel":"YOUR_ROOM_ID"}
```

- Chatto also accepts `message` or `body` for the text, and `room_id` for the
  room. You can put `room_id` in the URL query string.
- Every request needs a room ID. Use the ID, not the room name. If you send
  more than one text field or room ID, all non-empty values must match.
- Set `"create_thread": true` to start a thread in a channel room that supports
  threads.
- The bot must be a member of the room and have `message.post`. A webhook can
  post to a DM only after a human starts the DM with the bot.
- A successful request returns HTTP 200 with the body `ok`. There is no
  idempotency key, so a retry can post the message two times.

A bot can have at most 20 active webhooks. Create one webhook for each
integration. To replace a webhook, create a new one, move the caller to it, and
revoke the old one.

<Aside type="caution">
  The URL contains a credential. Configure your reverse proxy to redact
  `/webhooks/incoming/…` paths from its logs.
</Aside>

### Webhook troubleshooting

| Response | Check |
| --- | --- |
| `400 invalid_payload` | Send valid JSON with non-empty `text`, `message`, or `body`, and a room ID. Make sure that duplicate fields match. Message size and room policy limits apply. |
| `404 channel_not_found` | Use the room ID. Make sure that the bot is a member, and that the bot and its owner can post there. |
| `401 invalid_token` | The credential is invalid or revoked. Create a new webhook and update the caller. |

## Send Grafana alerts

Grafana's **Webhook** integration works without a custom payload. Chatto reads
the `message` field of the default Grafana JSON.

<Steps>

1. Create a bot, add it to the destination channel room, and grant it
   `message.post`. The owner must have this permission too.
2. [Create an incoming webhook](#post-from-an-external-webhook) named
   `Grafana` and select the destination room. Make sure that the URL ends with
   `?room_id=YOUR_ROOM_ID`.
3. In Grafana Alerting, open **Contact points** and add a contact point. Select
   **Webhook** and paste the Chatto URL. Keep the **POST** method. Leave
   **Custom Payload** unset.
4. Send a test notification and make sure that it appears in the room. Then
   select the contact point in an alert rule or a notification policy.

</Steps>

To change the text, use the **Message** field of the contact point. You can use
Grafana notification templates there. Firing and resolved alerts post separate
messages. Chatto does not update or group earlier alerts. See
[Grafana's webhook documentation](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/).

## Outbound webhooks

An outbound webhook sends an HTTP request to your tool when someone speaks to
the bot.

<Steps>

1. Open the bot in **Server Admin → Bots**. In **Outbound webhooks**, select
   **Create webhook**.
2. Enter a name, the destination URL, and, if necessary, the complete
   `Authorization` header value.
3. Copy the signing secret if your tool verifies signatures. Chatto shows it
   only once.

</Steps>

Each enabled endpoint receives new messages, including thread replies, that
mention the bot directly or that are in a DM with the bot. A DM that mentions
the bot sends one request with both triggers. Messages from the bot, ordinary
channel messages, edits, and reactions do not send requests. Notification
preferences do not apply.

- A bot can have up to 20 endpoints, including paused ones.
- **Edit webhook** changes the URL and the `Authorization` header. It keeps the
  signing secret and cancels queued retries. To change the name or secret,
  create a new endpoint and revoke the old one.
- **Pause** stops new requests and cancels queued retries. **Resume** does not
  send messages from the paused period.
- **Revoke webhook** removes the endpoint permanently.

Destinations require public HTTPS. `localhost` and `*.localhost` also permit
HTTP, but only when every resolved address is a loopback address. IP literals
such as `127.0.0.1` and other private-network hosts are not permitted.

The [Runling bot example](https://github.com/chattocorp/chatto/tree/main/examples/runling-bot)
receives these requests and replies through the Chatto API.

### Request body

```json
{
  "version": 1,
  "id": "stable-delivery-id",
  "type": "message.created",
  "triggers": ["direct_message", "mention"],
  "occurred_at": "2026-09-05T12:00:00Z",
  "bot_id": "bot-id",
  "room_id": "room-id",
  "thread_root_id": null,
  "message": {
    "id": "message-id",
    "author_id": "author-id",
    "body": "Hello @helper_bot"
  }
}
```

Use `triggers` to route mentions and DMs. `thread_root_id` is null for a root
message. The body does not contain attachments. Chatto does not change this
format for specific tools.

Return HTTP 2xx when you accept the request. Do long tasks separately, and
reply with the bot API key through the normal API. Chatto ignores the response
body.

### Signatures and authentication

Chatto adds these headers:

- `Chatto-Webhook-Id`: the delivery ID from the body.
- `Chatto-Webhook-Timestamp`: Unix time in seconds for this attempt.
- `Chatto-Webhook-Signature`: `v1=` followed by a hexadecimal HMAC-SHA256.

To verify a request:

1. Use the signing secret as its displayed UTF-8 text. Do not Base64-decode it.
2. Compute HMAC-SHA256 over the timestamp, a full stop (`.`), and the exact
   request body bytes.
3. Compare the result in constant time.
4. Reject old timestamps, for example older than five minutes.
5. Deduplicate by delivery ID. A retry has the same ID and a new timestamp.

If your tool cannot verify signatures, authenticate with a secret URL or the
`Authorization` header instead.

### Retries, expiry, and access

Chatto retries transport failures and all non-2xx responses. It does not
follow redirects. By default, Chatto makes up to five attempts within 24 hours
of the message. The delay starts at 30 seconds and doubles up to 30 minutes.
Each request has a 10-second timeout. To change these values, see
[Outbound bot webhooks](/reference/environment-variables/#outbound-bot-webhooks).

Delivery is best effort. A server restart discards pending requests and
retries without a failure record. Requests can arrive more than once or out of
order, so use the delivery ID to prevent repeated work.

Before each attempt, Chatto checks the current access of the bot. It skips the
request if the bot lost access, the message is unavailable, or the endpoint is
paused or revoked. The body contains the current message text, so an edit can
change it between attempts.

Select **Recent failures** on an endpoint to see failed deliveries with time,
attempt count, HTTP status, and failure category. Chatto keeps failures for
seven days; change this with `core.log.retention`. Chatto does not record
successes, so an empty list does not prove that delivery succeeded.

## Activate a bot from Chatto activity

To react to all activity that the bot can see, use the normal realtime
subscription with `LIVE_ONLY`. There is no bot-only channel. See
[Realtime](/guides/integrations/realtime-protocol/) and the
[`RealtimeEvent`](/reference/connectrpc-api/realtime/#chatto-realtime-v1-RealtimeEvent)
reference.

To react only when Chatto would notify the bot, read
`NotificationService.ListNotificationOccurrences` and filter by cause:

| Cause                      | When Chatto creates it                                                      |
| -------------------------- | --------------------------------------------------------------------------- |
| `direct_message_received`  | Another account sends a message in a DM with the bot.                       |
| `direct_mention_received`  | Another account mentions the bot directly in a channel room.                |
| `reply_received`           | Another account replies to a message from the bot.                          |
| `followed_thread_activity` | Another account posts in a thread that the bot follows.                     |

Ignore other causes. A delivered direct mention also makes the bot follow the
thread, so later replies arrive as `followed_thread_activity`. An explicit
unfollow stays in effect.

Save the IDs of processed occurrences, because one occurrence can appear more
than once. One message can create more than one cause. To act only once for
each message, also deduplicate by `event_id`. After a disconnect, read the list
again to recover missed occurrences within the notification retention period.
Then load the message or thread, for example with
`ThreadService.GetThreadEvents`.
