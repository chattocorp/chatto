Боты позволяют внешним инструментам публиковать сообщения и отвечать в беседах Chatto. Создайте аккаунт бота, дайте ему доступ к нужным комнатам и подключите инструмент с помощью API-ключа или вебхука. Программу бота вы запускаете отдельно.

Ниже показана настройка бота, публикующего сведения о развёртывании. Вам нужны разрешение создавать ботов и доступ к целевой комнате.

## Выберите способ подключения инструмента

Есть три способа подключения. Бот может использовать несколько сразу.

- **Входящий вебхук: ваш инструмент → Chatto.** Предоставьте службе оповещений или инструменту автоматизации URL для публикации сообщений.
- **API-ключ: ваша программа → Chatto.** Выдайте программе бота ключ, чтобы она могла читать сообщения, отправлять ответы или выполнять другие разрешённые вами операции API.
- **Исходящий вебхук: Chatto → ваш инструмент.** Укажите Chatto конечную точку для уведомлений, когда кто-то упоминает бота или отправляет ему личное сообщение. Инструмент обрабатывает событие и использует API-ключ, если нужен ответ.

Для сведений о развёртывании используйте входящий вебхук. Для бота, отвечающего на упоминания или личные сообщения, используйте исходящий вебхук для получения сообщений и API-ключ для отправки ответов.

## 1. Создайте аккаунт бота

1. Откройте **Администрирование сервера → Боты** на сервере, где будет работать бот.
2. Выберите **Создать бота**. В этом примере используйте `release-bot` как имя пользователя и **Обновления выпусков** как отображаемое имя. Имя пользователя идентифицирует аккаунт; отображаемое имя участники видят рядом с сообщениями.
3. Создайте бота. Chatto покажет API-ключ один раз. Если планируете использовать API, сохраните ключ в хранилище секретов интеграции. После закрытия диалога снова показать ключ нельзя.
4. Откройте страницу бота. Добавьте короткое описание профиля, например «Публикует результаты развёртывания из нашего конвейера выпуска».

Если **Создать бота** недоступно, попросите у администратора `bot.create`. Владение ботом позволяет управлять этим ботом; разрешение управлять всеми ботами выдаётся отдельно.

Если инструмент использует только входящий вебхук, API-ключ ему не нужен. Отзовите неиспользуемый начальный ключ в **Интеграции → API-ключи**.

## 2. Дайте доступ к одной комнате

У нового бота нет разрешений. Он не наследует роли владельца или разрешения роли `everyone`. Вступление в комнату и разрешение публиковать в ней — отдельные требования.

1. Откройте вкладку **Разрешения** бота.
2. Найдите столбец комнаты для сведений о развёртывании.
3. В строке **Присоединился** вверху матрицы выберите эту комнату и подтвердите изменение членства.
4. Разрешите `message.post` для этой комнаты. Не относящиеся к задаче разрешения оставьте незаданными.

Боту развёртывания не нужен доступ на чтение. Выдайте `message.post` в столбце комнаты, чтобы ограничить публикации этой комнатой. Разрешение на уровне сервера действует в разных комнатах.

Вам также нужны полномочия добавлять бота в комнату. Архивные комнаты и блокировки в комнате могут препятствовать вступлению. Собственное разрешение бота `room.join` предназначено для вступления через API и не заменяет строку **Присоединился**.

### Доступ бота не может превышать доступ владельца

Каждое разрешение бота ограничено текущими разрешениями владельца-человека в той же области. Сохранённое разрешение может быть неактивно: замок в матрице означает, что разрешения владельца блокируют его. Если владелец теряет доступ, бот тоже теряет этот доступ. Выход из аккаунта не останавливает бота.

Для некоторых разрешений нужен привилегированный режим. Если Chatto просит включить его, сделайте это до выдачи разрешения.

## 3. Подключите входящий вебхук

1. Откройте **Интеграции** на странице бота.
2. В разделе **Входящие вебхуки** выберите **Создать вебхук**.
3. Назовите его по вызывающему инструменту, например **Конвейер выпуска**.
4. Выберите комнату обновлений развёртывания как **Целевую комнату**.
5. Создайте вебхук и скопируйте полный URL в настройки вебхука инструмента. Сохраните часть `?room_id=…` в URL.

Настройте инструмент на отправку HTTP **POST** с `Content-Type: application/json` и таким телом:

```json
{
  "text": "Развёртывание завершено: версия **0.5** готова к тестированию."
}
```

Выбранная комната уже указана в URL, поэтому поле `channel` в этом запросе не требуется. Если вместо этого выбрать **Выбирать в каждом запросе**, включите `"channel": "YOUR_ROOM_ID"` в JSON. Используйте ID комнаты, а не её имя.

Выбор назначения добавляет ID комнаты в URL. Вызывающая сторона может изменить ID и отправлять сообщения в любую комнату, где бот может публиковать. Чтобы ограничить вебхук одной комнатой, выдайте боту право публикации только в ней.

## 4. Отправьте тест и проверьте результат

Используйте тестовую функцию внешнего инструмента. Успешный входящий запрос возвращает HTTP `200` с текстом `ok`. В Chatto сообщение должно появиться в выбранной комнате от имени **Обновления выпусков**, с меткой **BOT** и жирным «0.5».

Если запрос завершился ошибкой, проверьте ответ:

- **`401 invalid_token`:** URL неполный, недействительный или отозван. Создайте новый входящий вебхук, если полный URL больше недоступен.
- **`404 channel_not_found`:** проверьте ID комнаты, членство бота, его разрешение `message.post` и право владельца публиковать в этой комнате.
- **`400 invalid_payload`:** отправьте корректный JSON с непустым текстом сообщения и ID комнаты. Если ID есть и в URL, и в теле, значения должны совпадать. Политика комнаты и ограничения размера сообщений также действуют.
- **Сообщение появляется дважды:** повтор запроса может создать ещё одно сообщение. Входящие вебхуки не предоставляют ключ идемпотентности для подавления дубликатов.

После успешного теста настройте инструмент на вызов вебхука по завершении развёртывания.

## Создайте бота, который отвечает людям

Укажите в программе бота его API-ключ Chatto. Храните ключ в секретной конфигурации программы. Запросы API используют заголовок `Authorization: Bearer YOUR_API_KEY` для аутентификации.

Выберите нужные боту разрешения:

- **Отвечать только при обращении:** выдайте `message.read-interactions` и `message.post-in-interactions`. Бот может читать целиком темы, которые он начал, темы с его прямым упоминанием и свои личные сообщения. Поэтому упоминание бота также может открыть ему более ранние сообщения в теме.
- **Читать комнату, но отвечать только при обращении:** выдайте `message.read` и `message.post-in-interactions`.
- **Читать все сообщения и начинать беседы:** выдайте `message.read` и `message.post`.

Примените разрешения к нужным комнатам. Для личных сообщений используйте область **Личные сообщения** в матрице. Разрешения владельца по-прежнему ограничивают эти права.

### Сообщите программе, когда отвечать

Если программа принимает события вебхуков Chatto:

1. Откройте **Интеграции → Исходящие вебхуки → Создать вебхук**.
2. Введите имя и общедоступную конечную точку HTTPS программы.
3. Если получателю нужен **Заголовок Authorization**, введите полное ожидаемое значение, включая префикс вроде `Bearer`.
4. Скопируйте секрет подписи в настройки получателя, если он проверяет подписи вебхуков Chatto. Секрет показывается только один раз.
5. Упомяните бота в доступной ему для чтения комнате или отправьте личное сообщение. Проверьте журналы получателя и ответ бота в Chatto.

Конечная точка получает новые сообщения с прямым упоминанием бота или из его личных бесед. Обычные сообщения комнаты, изменения, реакции и сообщения самого бота не вызывают эти вебхуки. Последующий обычный ответ в теме комнаты также не вызывает вебхук, если в нём снова не упомянут бот.

Получатель должен принять событие ответом HTTP 2xx, затем отправить ответ в чат через API. Chatto игнорирует тело HTTP-ответа. Доставка может повторяться, поэтому получатель должен использовать ID доставки, чтобы не выполнять одну работу дважды. Для программы, которой нужны все доступные для чтения события, используйте API реального времени Chatto вместо вебхука упоминаний и личных сообщений.

Описание данных события, проверки подписи и операций API см. в [справочнике вебхуков ботов](https://docs.chatto.run/reference/bot-webhooks/) и [справочнике API](https://docs.chatto.run/reference/connectrpc-api/).

Исходящий вебхук передаёт настроенной конечной точке текст сообщения и идентификаторы сообщения, автора, комнаты и бота. Получатель также видит исходящий IP-адрес сервера Chatto. Если бот пересылает сообщения поставщику ИИ или другому сервису, объясните это участникам до использования бота в их беседах.

### Если бот молчит

Проверьте, получила ли программа событие. В исходящем вебхуке откройте **Недавние ошибки**, чтобы увидеть записанные ошибки доставки. Проверьте, что конечная точка включена, доступна, принимает настроенную аутентификацию и возвращает 2xx без перенаправления. Пустой список ошибок не доказывает успешную доставку.

Если событие получено, но ответа нет, проверьте API-ключ программы, операцию ответа и действующие права бота на чтение и публикацию.

## Поддерживайте интеграцию

- **Замена учётных данных:** создайте новый именованный ключ или вебхук, обновите вызывающую сторону, проверьте работу и отзовите старый. API-ключи не истекают автоматически. Никогда не вставляйте настоящий ключ или URL с учётными данными в чат или систему контроля версий.
- **Временная остановка исходящей доставки:** выберите **Приостановить** у конечной точки. **Возобновить** разрешает новые события, но не воспроизводит период паузы.
- **Передача бота другому владельцу:** аккаунт с `bot.manage` может использовать **Переназначить владельца**. Действующий доступ бота сразу следует за новым владельцем. Существующие ключи остаются действительными, поэтому замените учётные данные, если прежний оператор должен потерять доступ.
- **Удаление аккаунта владельца:** сначала передайте долгоживущих ботов. Удаление владельца-человека также удаляет принадлежащих ему ботов.
- **Покажите участникам возможности бота:** откройте его профиль и проверьте **Владелец** и **Что он может делать**. Проверяйте доступ после изменения комнат или владельца.
