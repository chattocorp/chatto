Chatto exposes typed protobuf APIs for clients, bots, tools, and operator automation. Start with the [ConnectRPC API overview](/reference/connectrpc-api/) to explore the available services and methods. Use the public ConnectRPC API for normal integrations, the realtime WebSocket protocol for live updates, and the local operator socket only for trusted recovery workflows.

<Aside type="caution">
  Chatto's public API is experimental while Chatto is pre-1.0. We prefer
  additive changes, but breaking changes can happen in the `0.x` line. Pin
  server versions for production integrations, test the releases you support,
  and read release notes before upgrading. See [API
  Compatibility](/guides/integrations/api-compatibility/).
</Aside>

## API Surfaces

| Surface               | Path or transport                               | Use for                                                                                                   |
| --------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Public ConnectRPC API | `/api/connect/chatto.api.v1.*`                  | Normal client and integration behavior.                                                                   |
| Admin ConnectRPC API  | `/api/connect/chatto.admin.v1.*`                | Permission-gated administrative tooling on the public web listener.                                       |
| Realtime WebSocket    | `/api/realtime`                                 | Canonical protobuf events, canonical resource snapshots, and bounded resume for authenticated clients.    |
| MCP                   | `/mcp` on the public HTTP listener when enabled | Experimental agent tool discovery and bounded user-scoped operations.                                     |
| Operator API          | Unix socket                                     | Root-equivalent local automation and recovery.                                                            |

Do not expose the Operator API over a network. It is intentionally separate from the public web listener.

## Start With Server Discovery

Use `ServerDiscoveryService.GetServer` as the high-compatibility discovery endpoint. It tells clients what server they are talking to, which login providers are available, which public profile metadata should be rendered before authentication, and which software version is running.

Discovery is also the right place for custom clients to learn public server identity and compatibility before starting OAuth or login flows. Custom clients should pin and test the server releases they support; discovery does not expose method-level feature flags.

## Authentication Choices

| Client shape                 | Credential                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Same-origin browser app      | HttpOnly cookie session. Dedicated bundled-browser authentication does not create or return bearer credentials. |
| Cross-origin Chatto frontend | OAuth authorization code with PKCE, then a renewable opaque bearer session.                                     |
| Bot integration              | Bot API key created in Server Admin → Bots.                                                                     |
| User-authorized client       | OAuth authorization code with PKCE, then a renewable opaque bearer session.                                     |
| Local recovery automation    | Operator socket, not user auth.                                                                                 |

Human bearer sessions return a short-lived access token, a rotating refresh
credential, and both lifetimes. Send only the access token to ConnectRPC and
realtime. Rotate through `/oauth/token` with `grant_type=refresh_token`, the
issuing `client_id` when applicable, and the refresh token. Chatto also accepts
an optional client-generated `refresh_request_id`. Generate a cryptographically
random UUID version 4 for each rotation when you use this extension. Treat it
as a show-once recovery nonce. Persist it before you send the request, and
reuse it until you persist the complete response. An
exact retry can recover only the immediately previous refresh generation, and
only during the access-token lifetime created by that rotation. A retry outside
that boundary is stale reuse and revokes the renewable session. Serialize
refresh attempts. An `invalid_grant` response requires explicit authentication.
You can retry network failures and `5xx` responses promptly with the same
request ID.

Bearer credentials and bot API keys are opaque. They are not JWTs. See
[Bot Accounts](/guides/integrations/bot-accounts/) for unattended integration
identities and their explicit permission model.
See [Model Context Protocol](/guides/integrations/mcp/) for the resource-bound
agent integration.

## Realtime Delivery

Authenticated realtime clients connect to `/api/realtime` and exchange
protobuf `chatto.realtime.v1` frames. The package name is the protobuf
namespace; 0.5 servers accept only behavioral protocol version 4. The stream
sends authorized canonical events for messages, edits, reactions, rooms,
membership, profiles, calls, and other public activity.

A subscription selects a `SNAPSHOT` or `LIVE_ONLY` fallback. A bot can select
`LIVE_ONLY` and use ConnectRPC for resource detail. The bundled frontend
selects `SNAPSHOT` and uses canonical resource chunks to build its local
projection. A valid cursor resumes a bounded recent gap before live delivery.

Resume and timeline cursors are opaque. Clients must store and return them
unchanged and must not infer persistence coordinates from them. The server
binds cursors to the authenticated viewer. It also binds timeline cursors to
the exact room or thread that issued them.

Start with the [Realtime Protocol Overview](/guides/integrations/realtime-protocol/)
for the connection lifecycle and reducer rules. Then use the
[TypeScript tutorial](/guides/integrations/realtime-typescript/) to connect a
small browser client.

Durable events contain one authorized canonical event and an opaque resume
cursor. They do not contain resource sidecars. Typing, presence changes, and
session termination are transient and do not have resume cursors. Projection
clients use event variants as refresh hints and read current resources through
ConnectRPC.

Realtime does not replace `chatto.api.v1`. Use the resource-oriented
ConnectRPC services for explicit reads, pagination, commands, and
read-your-writes responses. Add realtime when an integration must react to new
activity or repair a recent connection gap.

Realtime delivery uses the same room membership, RBAC, projection readiness, and session-termination checks as the rest of the server.

## Integration Patterns

| Goal                           | Recommended API                                                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Render room navigation         | `RoomDirectoryService`                                                                                       |
| Read room history              | `RoomService.GetRoomEvents` and `RoomService.GetRoomEventsAround`                                            |
| Post, edit, or delete messages | `MessageService`                                                                                             |
| React to messages              | `MessageService.AddReaction` and `MessageService.RemoveReaction`                                             |
| Track unread state             | `RoomService.MarkRoomAsRead` and `ThreadService.MarkThreadAsRead`                                            |
| React to bot activations       | Canonical realtime events and `NotificationService.ListNotificationOccurrences`                             |
| Start DMs                      | `RoomService`                                                                                                |
| Read users and profiles        | `UserService.ListUsers`, `GetUser`, and `BatchGetUsers`                                                      |
| Manage bot identities and keys | `BotService`                                                                                                 |
| Manage roles or permissions    | `chatto.admin.v1` role and permission services                                                               |
| Inspect operational health     | `AdminDiagnosticsService`, metrics, and exporter                                                             |

## Message Body Tokens

Message bodies are plain text with Chatto's supported Markdown subset: headings,
emphasis, links and autolinks, inline and fenced code, blockquotes, ordered and
unordered lists, and GFM pipe tables. Tables support the GFM delimiter-row
alignment markers (`:---`, `:---:`, and `---:`), optional outer pipes, inline
formatting in cells, and backslash-escaped pipes.

Message bodies may also contain inline timestamp tokens in the form
`<t:UNIX_SECONDS:F>`. Render valid tokens as the referenced UTC instant in the
viewer's locale and timezone, or leave the token literal if your client does not
support inline timestamps.

## Programmatic Safety

1. Prefer generated protobuf clients over hand-built JSON or path calls.
2. Treat `NOT_FOUND` on singular reads as the normal absence signal.
3. Use pagination fields instead of assuming unbounded lists.
4. Keep access tokens, refresh credentials, and refresh request IDs out of logs, URLs, and issue reports.
5. Handle permission failures explicitly; admin APIs are method-gated.
6. Watch release notes for ConnectRPC package, service, or field changes during `0.x`.
