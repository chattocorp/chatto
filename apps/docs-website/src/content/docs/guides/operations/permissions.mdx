A **permission** controls one action, such as posting messages or managing
rooms. A **role** gives a set of permissions to many people. A permission
setting is **Allow** or **Inherit** for a role, also for `everyone`, and
**Allow**, **Deny**, or **Inherit** for a single user. **Inherit** means no
setting.

## How permissions work

- **Every signed-in person has the `everyone` role.** You can also assign the
  built-in `moderator` and `admin` roles, and your own roles.
- **You set a permission at a scope.** A channel room uses its Room, Room
  group, and Server settings. A direct message (DM) uses the Direct messages
  and Server settings.
- **Roles only allow.** This includes `everyone`. An allow of a role at any
  scope of the room gives the permission. Giving a role never removes access.
- **A Server-scope allow reaches every room.** A room or room group cannot
  take it away. Allow room access and room content at Room group or Room
  scope.
- **A deny on a user always wins.** When the most specific setting on the user
  is a deny, the user does not get the permission, whatever their roles allow.
  The only exception is a broader permission that includes it (see below).
  An allow on a user works like a role allow.
- **No allow means no access.**
- **Prefer roles.** Give permissions through roles, also when only one person
  has the role. Use settings on a single user only for rare exceptions. They
  are hard to find later, and they do not give [rank](#role-order).
- **Owners have every permission in privileged mode.** Without the mode, an
  owner has only the permissions of their roles and grants. You cannot lock
  out an owner, because an owner can always enable privileged mode. A user is
  an owner when they have the `owner` role or a verified email address in
  `owners.emails` in `chatto.toml`. Use `owners.emails` to recover access if
  you lock yourself out.
- **Message access also needs membership.** An account must be a member of the
  room or the DM to read it. Owners and administrators cannot read DMs that
  they are not part of.

| Settings | Result |
| -------- | ------ |
| Server: `everyone` Inherit, `admin` Allow | **Allowed** for admins only, in every room. |
| Room: `engineering` Allow. Room group and Server: `everyone` Inherit | **Allowed** in this room for `engineering` only. |
| Server: `everyone` Allow. Room: `engineering` Allow | **Allowed** for all members. The Server allow reaches this room. |
| Server: `admin` Allow. User: Deny | **Denied** for that admin. The deny on the user wins. |

Bots do not get permissions from `everyone`, and they cannot hold roles. A bot
has only the permissions that you allow directly on the bot, and never more
than its owner has. See
[Bot accounts](/guides/integrations/bot-accounts/).

## Built-in roles

Every server has four system roles. You cannot delete them. The order of the
roles does not change which setting wins. It decides who can manage whom; see
[Role order](#role-order).

| Role | Defaults on a new server |
| ---- | ------------------------ |
| `everyone` | Server: `user.delete-self`. Direct messages: `message.read`, `message.post`, `message.attach`, `message.react`, `message.echo`, all `call.*` permissions. |
| `moderator` | Server: `message.manage`, `room.remove-member` |
| `admin` | Server: `server.manage`, `room.create`, `room.manage`, `room.remove-member`, `message.manage`, `role.manage`, `role.assign`, `admin.view-users`, `admin.view-audit`, `user.invite`, `user.manage-accounts`, `user.manage-permissions`, `user.delete-any`, `user.delete-self`, `bot.create`, `bot.manage` |
| `owner` | Every permission while privileged mode is active. You cannot edit these settings. |

Moderators and admins get their member permissions from `everyone`. `admin`
has no Server-scope `room.list` or `room.join`, because these would also open
private rooms. Admins find and join rooms like other members. With
`room.manage` in privileged mode, they can open a room or room group, and add
members to a room, also themselves.

A new server starts closed. It opens only the two rooms in the `Lobby` room
group, at Room scope:

| Room | `everyone` can |
| ---- | -------------- |
| `#general` | Find and join the room, read, post, attach files, react, echo replies, and use calls. |
| `#announcements` | Find and join the room, read, react, and reply in threads. The room is universal, so all members are in it. Only `admin` can post root messages and attach files there. |

The `Lobby` room group has no allows for `everyone`. Each new room and room
group starts without allows for `everyone`. Only owners in privileged mode and
members that you add can reach it. Admins and room managers can open it in
privileged mode. To open it, see
[Open a room or room group](/guides/operations/common-setups/#open-a-room-or-room-group).
The settings page of each room and room group shows who can find and join it.
Owners can post in `#announcements` only in privileged mode.

## Privileged mode

Administrative and moderation permissions stay off during normal chat use. To
use them:

<Steps>

1. Select the shield in your user area.
2. Confirm **Enable privileged mode**.

</Steps>

Privileged mode lasts 15 minutes and does not extend. Select the shield again
to stop it sooner. It applies only to the server
session where you enabled it. The event log records each activation and
deactivation.

Privileged mode turns on permissions, not roles. It applies to each permission
marked **Yes** in the [permission reference](#permission-reference), from any
role or user setting. It does not give you permissions that you do not have.

For owners, privileged mode also turns on the owner permissions. Without the
mode, an owner cannot see, join, or read a room unless their roles or their
own settings allow it, as for other members. If an owner
joins such a room in privileged mode, they stay a member, but they can read the
room only while the mode is active. Chatto removes them from a call in such a
room shortly after the mode ends. Notifications use the permissions without the
mode. MCP clients cannot enable privileged mode.

Without privileged mode, Server Administration stays visible, but its
protected actions are not available. The Moderation page needs server-wide
`room.remove-member`, so it is available only in privileged mode.

Bots do not use privileged mode. To allow a privileged permission for a bot,
you must have that permission active at the same scope. You can remove a bot's
permission without privileged mode.

## Permission reference

Scopes: **S** Server, **G** Room group, **R** Room, **DM** Direct messages.
**All** means all four scopes.

| Permission | Scopes | Privileged | Allows |
| ---------- | ------ | ---------- | ------ |
| `server.manage` | S | Yes | Change server settings, such as the name, description, and logo. Includes `server.manage-neighbors`. |
| `server.manage-neighbors` | S | Yes | Manage the public Neighbor directory. |
| `room.list` | S, G, R | | See rooms in the room directory and room lists. |
| `room.join` | S, G, R | | Join channel rooms. |
| `room.create` | S, G | Yes | Create channel rooms. A new room starts closed. To open it, the user also needs `room.manage` in the room group. |
| `room.manage` | S, G, R | Yes | Configure, rename, archive, and delete rooms and room groups at that scope, and add or remove room members. [Open rooms](#limits-for-non-owners) at that scope. At Server scope, also create and order room groups. |
| `room.remove-member` | S, G, R | Yes | Remove a member from a channel room, with a reason and an optional suspension. Replaces `room.ban-member`. |
| `message.read` | All | | Read messages, threads, attachments, search results, and typing indicators. Includes `message.read-interactions`. |
| `message.read-interactions` | All | | Read only threads that the account started, where another account mentioned it directly, or where it received a DM. It can read the full thread. |
| `message.post` | All | | Post messages and thread replies. At DM scope, a person can also start DMs. Includes `message.post-in-thread` and `message.post-in-interactions`. |
| `message.post-in-thread` | All | | Reply in each thread that the account can read. |
| `message.post-in-interactions` | All | | Reply only in the threads that `message.read-interactions` describes. |
| `message.attach` | All | | Attach files to new messages. |
| `message.react` | All | | Add and remove reactions. |
| `message.echo` | All | | Echo a thread reply to the room. |
| `message.manage` | All | Yes | Edit or delete messages from other accounts. Remove a thread reply's room echo through the edit checkbox. Adding an echo remains author-only. |
| `call.start` | All | | Start a call. Also needs `call.join`. |
| `call.join` | All | | Join a call, also as a listener. |
| `call.voice` | All | | Send microphone audio. |
| `call.camera` | All | | Send camera video. |
| `call.screenshare` | All | | Share a screen, window, tab, or application, with its audio. |
| `role.manage` | S | Yes | Create, change, move, and delete roles and their permission settings, for every role except `owner`. A non-owner can change only the settings of permissions that they have at that scope, with [one exception](#limits-for-non-owners). To delete a role, a non-owner must have every permission that the role allows, with the same exception. |
| `role.assign` | S | Yes | Assign and remove roles. A non-owner can assign only roles below them whose allows they have ([with one exception](#limits-for-non-owners)), and only to accounts below them or to their own account. Only owners can assign `owner`. |
| `admin.view-users` | S | Yes | See the member list in Server Administration. |
| `admin.view-audit` | S | Yes | See the event log. |
| `user.invite` | S | Yes | List, create, copy, and revoke invite links. The holder can use all active invite links. |
| `user.manage-accounts` | S | Yes | Create accounts, edit account identity, reset passwords, attach verified email addresses, and clear login cooldowns. |
| `user.manage-permissions` | S | Yes | Change the permission settings of users. A non-owner can change only users below them or themselves, and only the settings of permissions that they have at that scope, with [one exception](#limits-for-non-owners). |
| `user.delete-any` | S | Yes | Delete any account. |
| `user.delete-self` | S | | Delete your own account. |
| `bot.create` | S | | Create bots that you own. |
| `bot.manage` | S | Yes | Manage bots whose owners rank below you. A bot ranks like its owner. |

System diagnostics are only for owners. They are not a permission.

An allow for a broad permission also allows the permissions that it includes. A
deny for an included permission does not restrict that broad allow. For
example, to stop all posting, deny `message.post`, `message.post-in-thread`,
and `message.post-in-interactions`.

Posting also needs room membership and must agree with the room's Threading
Mode. A thread reply also needs read access to the thread. `room.manage` and
`message.manage` bypass Slow Mode. See [Calls](/guides/infrastructure/voice-calls/) for media limits in
calls.

## Direct messages

DMs use the `message.*` and `call.*` permissions at the **Direct messages**
scope. No `room.*` permission applies to DMs. If you do not set a Direct
messages value, the Server setting applies.

- Only people can start a DM. They need `message.post`. A bot cannot start a
  DM, even with `message.post`. After a person starts a DM with a bot, the bot
  can use the DM permissions that you allow for it.
- A participant with `message.manage` can edit or delete the messages of other
  participants. Nobody can moderate a DM that they are not part of.

## Role order

The role order decides who can manage whom. It does not change which
permission setting wins.

- `owner` is always highest and `everyone` is always lowest. You can move
  `admin`, `moderator`, and custom roles: drag them on the **Roles** page in
  Server Administration. A new role starts lowest.
- A user ranks at their highest role. Owners rank above all roles.
- To change another account, you need the permission for the change and a
  higher rank than the account. This applies to passwords, profiles,
  deletion, roles, permission settings, room removal and suspensions, room
  membership removal, and bots. To manage a bot, you also need a higher rank
  than its owner, unless you own the bot.
- You can assign and remove only roles below your own highest role.
- With `role.manage`, you can edit, delete, and move every role except
  `owner`, also roles above your own. Only owners can change `owner`.
- Without `role.manage`, for example as a room manager, you can edit the
  room settings only of roles below your own highest role. You can always
  edit the settings of `everyone`.
- Two users with the same highest role cannot change each other. Only an
  owner can change a user whose highest role is the top role. By default,
  this role is `admin`.
- Permission settings directly on a user do not give rank. Give
  administrators a role.
- Give `role.manage` only to administrators. A user with `role.manage` can
  move their own role higher and then manage more users. They can also
  change the settings of `everyone`, and these settings apply to all members,
  also to users who rank higher.
- Moderating messages and adding a member to a room do not depend on rank.

## Limits for non-owners

To change a permission setting of a role or user, a non-owner must have that
permission at that scope. To assign, remove, or delete a role, a non-owner
must have each permission that the role allows, at its scope.

One exception lets admins and room managers open rooms. At Room group or Room
scope, `room.manage` there is enough for each permission that does not need
privileged mode, such as `room.list`, `room.join`, `message.read`, and
`message.post`. `room.manage` already lets them add any account to the room.
The exception does not apply to permissions that need privileged mode, such
as `room.manage`, `room.remove-member`, and `message.manage`.

## Where to configure permissions

| Task | Where |
| ---- | ----- |
| Create, edit, and order roles | Server Administration → **Roles** |
| Compare the permissions of all roles. These settings apply in every room. | Server Administration → **Permissions** |
| Assign roles | Server Administration → **Members** → member → **Roles** |
| Set permissions for one user | Server Administration → **Members** → member → **Permissions** |
| Set permissions for one bot | Server Administration → **Bots** → bot → **Permissions** |
| Set room permissions | The room's settings → **Permissions** |
| Set room-group permissions | The room group's settings |
| See who can find and join a room or room group | The settings of the room or room group |
| Set recovery owners | `owners.emails` in `chatto.toml` |

To add an account to a room or remove it, use the **Joined** row in the
account's permissions. You need `user.manage-accounts`, or `room.manage` for
that room. To remove an account, you also need a higher rank. The account does
not need `room.join`. This row does not change permissions or DMs.

## Upgrading from 0.4

<Aside type="caution" title="Private rooms open on upgrade">
  Chatto 0.5 ignores denies on roles, also on `everyone`. A room that is
  private or read-only only because of an `everyone` deny opens to all members
  who have the access at Server scope. On a default 0.4 server, this is every
  member. This includes `#announcements`. Before you upgrade, follow the steps
  in
  [Make private rooms private before you upgrade](/releases/0-5-0/#make-private-rooms-private-before-you-upgrade).
  After the upgrade, the server log lists the affected rooms and room groups.
</Aside>

Chatto applies default permissions only on a new server. When a 0.4 server
starts with 0.5 for the first time, Chatto adds these grants one time to keep
the 0.4 behavior:

- `message.read` for `everyone` at Server scope.
- `room.remove-member` for each role and user that had `room.ban-member`, at
  the same scope. `room.ban-member` has no effect in 0.5.
- Each `call.*` permission for `everyone`.

Make these changes on an upgraded server:

- **Allow `user.invite` and `bot.manage`** for `admin` if admins must manage
  invite links and bots.
- **Allow `bot.create`** for the roles that can create bots.
- **Allow `room.manage`** for delegated room managers. In 0.4, room-group
  management used `role.manage`.
- **Make private and read-only rooms work without denies.** Do this before
  you upgrade. See the caution above.
- **Allow `message.post` and `message.attach`** for `admin` in the
  `announcements` room if admins must post there.
- **Check `message.post-in-thread`.** `message.post` now also allows thread
  replies. An upgraded server keeps its Server allow of
  `message.post-in-thread` for `everyone`, so members can reply in threads in
  every room, also in read-only rooms. Remove it if necessary, and allow it in
  the room groups or rooms where members can reply.
- **Replace role denies.** Denies on roles, also on `everyone`, have no
  effect. Set denies on the users instead. To restrict a group of people, do
  not allow the access for `everyone`, and allow it for a role. See
  [Common Setups](/guides/operations/common-setups/).
- **Check the role order.** The role order now decides who can manage whom.
  An upgraded server keeps `admin` above `moderator` and both above custom
  roles. A user with a custom management role ranks below moderators and
  cannot manage them. Move roles on the **Roles** page if necessary.
- **Check delegated permission editors.** A user who is not an owner can now
  change only the permission settings of permissions that they have at that
  scope. To delete a role, this user must have every permission that the role
  allows. A room manager can also change the settings of room permissions
  that do not need privileged mode. See
  [Limits for non-owners](#limits-for-non-owners). Give these users the
  permissions that they must manage.

<Aside type="caution">
  Administrators, moderators, and owners must now enable
  [privileged mode](#privileged-mode) to use their administrative permissions.
  This also applies to custom `room.create` grants. Owners also need privileged
  mode to see, join, or read rooms that their roles do not open to them, and to
  post in the `announcements` room. If an owner needs this access during
  normal use, give them a role or a room-level allow that opens these rooms.
  The `admin` role lets them post in `announcements`.
</Aside>

See the [0.5.0 release notes](/releases/0-5-0/) for all upgrade steps.
