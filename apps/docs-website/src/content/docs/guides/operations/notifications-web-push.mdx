Chatto has persistent in-app notifications and optional browser Web Push. Operators configure whether push is available; members decide which rooms, threads, and devices should alert them.

## How Notifications Work

Chatto creates persistent notifications for attention-worthy events:

| Event | Default behavior |
| ----- | ---------------- |
| DM messages | Notify the recipient. |
| Root messages in channel rooms | Add a neutral room dot by default. |
| Direct `@username` mentions | Notify the mentioned user. |
| Role, `@all`, and `@here` mentions | Notify matching recipients, with confirmation for broad sends. |
| Replies to your message | Notify you. |
| Followed thread replies | Notify followers. |
| Reactions to your messages | Add a non-interruptive notification by default. |

Notifications are stored for the user, survive browser restarts, sync across tabs and devices, and expire after 90 days. Read and Delete changes synchronize everywhere for that user.

## Notification Centre

Open the notification centre as its own page from the bell in the app header.
It shows one chronological list:

- Unread notifications use orange emphasis for important activity and a neutral indicator for non-interruptive activity such as reactions.
- Read notifications stay in the same chronological list with muted styling and no unread indicator.
- Delete permanently removes a notification from the list.

Related activity is grouped by DM, room, thread, or reacted-to message. Opening a group goes to its newest unread event, or its newest event when everything in the group is read. Reading a room or thread marks covered notifications read. Chatto reads only up to the newest message that you can see. If you open an older message, newer notifications stay unread until you scroll to them. All notifications expire 90 days after their source activity.

## Notification Policy

Members use a matrix to control each notification cause at server, room-group, and room scope. The rows contain the nine notification causes. The columns contain the server, visible room groups and their current-member channel rooms, and current-member direct-message rooms.

| Mode | Effect |
| ---- | ------ |
| Inherit | Use the next broader room-group or server setting. |
| Off | Do not create attention for this cause. |
| Badge | Add only a neutral unread dot. Do not create a notification, play a sound, or send push. |
| Notification | Add an in-app notification. Important notifications can play the configured in-app sound, but Chatto does not send push. |
| Push notification | Add the same in-app notification and make it eligible for Web Push or native delivery. |

Direct messages, direct mentions, replies, role mentions, `@here`, and `@all` use Push notification by default. Root messages in channel rooms use Badge. Followed threads and reactions use Notification. A message that matches several causes creates one exact output per cause, so each keeps its own policy and triage identity. The client can still consolidate related activity for display.

Ambient notifications, such as reactions, use a neutral badge and do not play an in-app sound. In the room list, a room shows its Important and Ambient notifications as two separate counts. Each count opens its newest notification. Important notifications use orange indicators and can play your selected sound.

The installed app icon shows an unnumbered badge for Important unread notifications. The window title shows their total count across signed-in servers. Ambient notifications do not contribute to either indicator, even when you enable pushes for them. An Important background push can set the app icon badge when the browser runs the app's notification handler and the server includes the attention level; otherwise, the badge stays unchanged until the app can update it.

The server column always shows a concrete setting. If you have not configured a server preference, the matrix shows the product default at full intensity. Select a server cell to cycle through Off, Badge, Notification, and Push notification.

Room-group and room cells cycle through Inherit, Off, Badge, Notification, Push notification, and back to Inherit. A grey crossed bell means Off. A grey filled bell means Badge. An orange bell means Notification. An orange phone means Push notification. An inherited value uses the same icon at reduced intensity.

A Badge setting uses the neutral dot for its room. Thread Badge activity rolls up to its parent room. Reading the room or thread clears covered Badge attention. The dot uses your current settings. If you change a setting from Badge to a different setting, unread messages of that type do not show the dot. If you unfollow a thread, its replies do not show the dot. An orange notification dot takes priority over the grey dot. Badge does not change an operating-system or application-icon badge.

Room dots are controlled only by notification policy. If you set Room messages to Off, ordinary root messages do not add a dot. Chatto still keeps the Message Read Cursor and uses it to place the New messages separator when you open the room.

Channel rooms inherit from their current room group, then from the server. Direct-message rooms inherit directly from the server. Chatto uses the current room group and policy when it creates notification output. A room move or policy change can affect source activity that is still waiting for this step. It does not change notification output that Chatto has already created.

The Direct messages row applies to the server and direct-message rooms. The Room messages row applies to the server, room groups, and channel rooms. Cells outside these scopes are not available.

Use the matrix filter to find a group or room. A room match keeps its parent group visible. A group match keeps all of its current-member room columns visible. The server column always remains in the matrix.

## Do Not Disturb

Do Not Disturb does not discard notifications. Chatto still records the pending notification and updates counts, but suppresses interruptive delivery while the user is in DND:

- no notification sound
- no Web Push delivery
- no active interruption

This preserves "review later" behavior without waking the user's devices.

## Enable Web Push

Web Push is disabled until you provide VAPID keys. Without push config, Chatto hides the push UI entirely.

Generate VAPID keys:

```bash
npx web-push generate-vapid-keys
```

Then configure Chatto:

<Tabs>
<TabItem label="TOML">

```toml
[push]
enabled = true
vapid_public_key = "<generate-me>"
vapid_private_key = "<generate-me>"
vapid_subject = "mailto:admin@example.com"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_PUSH_ENABLED=true
CHATTO_PUSH_VAPID_PUBLIC_KEY=<generate-me>
CHATTO_PUSH_VAPID_PRIVATE_KEY=<generate-me>
CHATTO_PUSH_VAPID_SUBJECT=mailto:admin@example.com
```

</TabItem>
</Tabs>

Use a `mailto:` or HTTPS contact URI for `vapid_subject`. Keep the private key secret and stable; changing it can invalidate existing browser subscriptions.

## Device Behavior

When a signed-in server supports push and browser permission is unset, Chatto shows an invitation to enable push notifications. **Enable** opens the browser or operating-system permission prompt. **Not now**, or a dismissed prompt, hides the invitation on this device for 14 days. If the user blocks notifications, Chatto does not ask again; the user can change the choice in browser or operating-system settings.

Push is on for every registered server or for none of them. Each server's notification settings have one checkbox, **Push notifications on this device**. Unchecking it stops push from every server on this device; checking it turns push on again for all servers and asks the browser for permission if necessary.

While push is on, use **Send test notification** in a server's notification settings to check delivery to your devices.

When the user grants permission, Chatto creates a separate subscription for each registered server that supports push, including remote servers. While permission is granted, Chatto also registers servers that the user adds or signs in to later, without asking again. A user can have up to 16 active subscriptions on a server, and Chatto attempts every current endpoint for each push. Once any endpoint accepts a notification, Chatto does not retry the complete device set merely because another endpoint failed; this avoids repeatedly alerting healthy devices.

A server keeps a device's subscription for 180 days after the device last saved it. While the device uses Chatto, the app saves its subscriptions again when it starts, about once a day after that, and when the browser replaces a subscription. A device that does not open Chatto for 180 days stops receiving pushes until it opens Chatto again. Chatto also removes subscriptions when push providers report them as gone.

Chatto sends regular notifications in a declarative-compatible Web Push format, with browser-managed display and app-badge updates where supported. User-visible pushes request high-urgency delivery so mobile push services can wake sleeping devices promptly. Its service worker preserves notification display and click compatibility for browsers that do not handle the declarative payload directly.

While the app is running, confirmed read and delete actions also ask the browser to close matching OS notifications. The app checks again when it resumes or receives updated notification state. Cleanup is limited to the matching server and account. It preserves unread notifications and leaves uncertain results unchanged if a request fails or the server returns only part of the list. Older pushes without account metadata are not eligible for automatic cleanup. A closed or suspended app cannot guarantee immediate cleanup on another device; browser support also determines whether a close request removes the notification.

Operators do not need to change VAPID keys or push configuration for this behavior.

For security, Chatto connects directly only to absolute HTTPS push endpoints with public network addresses. It does not follow endpoint redirects or route push delivery through `HTTP_PROXY` or `HTTPS_PROXY`. Standard browser-created subscriptions already meet these requirements; private-network, redirecting, and proxy-only custom push endpoints are unsupported.

On iOS and iPadOS, Web Push works only for supported Home Screen web apps. Safari tabs that are not installed as an app may not receive native push.

<Aside type="note">
  In multi-server use, each server, including the server that hosts the app, registers its own browser subscription under the installed app's origin and continues to use its own VAPID keys. Push traffic travels directly from that server to the browser push service; the server hosting the app does not relay it. This requires a 0.5 client and server.
</Aside>

## Operator Checklist

1. Set `webserver.url` to the public HTTPS origin.
2. Enable Web Push with stable VAPID keys.
3. Keep the service worker path reachable through your proxy.
4. Test from a normal member account, not only an owner account.
5. Test one desktop browser and one mobile installed PWA if mobile push matters.
6. Explain to members that push is per device and that they enable it once per device.
