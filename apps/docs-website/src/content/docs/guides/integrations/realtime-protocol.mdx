Use realtime protocol 4 when a bot or client must react to activity on one
Chatto server. The protocol sends binary protobuf frames over a WebSocket at
`/api/realtime`.

Use [ConnectRPC](/reference/connectrpc-api/) for commands, explicit resource
reads, pagination, history, and read-your-writes results. Realtime events tell
you what happened. ConnectRPC gives you the resource detail that your
integration needs.

| Need                                                                     | Use                             |
| ------------------------------------------------------------------------ | ------------------------------- |
| React to a message, edit, reaction, membership change, or other activity | Realtime event                  |
| Create, update, or delete a resource                                     | ConnectRPC                      |
| Read one resource or a paginated list                                    | ConnectRPC                      |
| Build a current local content view                                       | Realtime snapshot               |
| Repair a short connection gap                                            | Realtime resume                 |

## Connection lifecycle

<div style="margin-block:1.5rem;overflow-x:auto" set:html={realtimeSequence} />

1. Open a WebSocket to `wss://chat.example.com/api/realtime`.
2. Send a binary [`RealtimeClientFrame`](/reference/connectrpc-api/realtime/#realtimeclientframe)
   with `hello`. Request protocol version `4`. Include a bearer credential when
   you do not use a same-origin cookie.
3. Wait for the server `hello`. Check that it accepts version `4`.
4. Send `subscribe_events`. Select `SNAPSHOT` or `LIVE_ONLY` as the required
   initial-state fallback. You can also include a safe resume cursor.
5. Read `subscribed.recovery_mode` to learn whether the server selected
   `SNAPSHOT`, `LIVE_ONLY`, or `RESUME`.
6. For `SNAPSHOT`, apply each snapshot resource as a complete replacement for
   that resource family.
7. Process replayed events, if any. The server sends `caught_up` when recovery
   reaches the live boundary.
8. Save the `caught_up` cursor after all earlier work succeeds. Continue to
   process live events.

The `subscribed` frame does not mean that recovery is complete. Treat the
stream as live only after `caught_up`.

## Choose snapshot or live-only startup

Select `LIVE_ONLY` for a bot that wants new events and reads resources through
ConnectRPC. If the cursor is absent or unusable, the server starts at a stated
current boundary. It does not send old events or current resources.

Select `SNAPSHOT` for a client that keeps a server projection. If the cursor is
absent or unusable, the server sends an exact authorized content snapshot at
boundary `E`. It then sends `caught_up(E)`. The bundled frontend uses this
mode.

When a cursor is usable, both choices can result in `RESUME`. The server sends
authorized durable events after that cursor and then sends `caught_up`. The
client does not send a separate catch-up command.

A cursor can become unusable because it is invalid, expired, too far behind,
from another server history, or unsafe for current authorization. Fallback is
normal recovery behavior. The server does not send a partial replay.

<Aside type="caution">
  Keep a resume cursor with the client state that it describes. Do not apply a
  cursor to an unrelated projection. A cursor is valid for 15 minutes, and the
  server binds it to the authenticated viewer.
</Aside>

## Handle public events

Each [`RealtimeEvent`](/reference/connectrpc-api/realtime-events/) contains one
authorized public payload variant. Durable variants
include messages, edits, retractions, reactions, pins, assets, rooms,
membership, profiles, threads, and calls. Typing, presence changes, and session
termination are transient variants and have no resume cursor.

The public event contains common metadata outside its event `oneof`:

- a stable event ID;
- source time;
- a visible actor ID, when applicable.

The optional `resume_cursor` is outside the payload `oneof`. A public event
does not contain broker coordinates.

The public union contains only event variants that are part of the realtime
API. Each union member reuses the canonical EVT or live payload message and
field number. The complete stored Event union is not part of the public API.

The server omits internal event variants and storage-only fields. It can add
authorized delivery-only `_plaintext` fields. It never sends raw EVT bytes,
ciphertext, credential data, subjects, or JetStream sequences.

Field surfaces are static exposure classes. Event authorization makes every
delivered shared or client-only field safe for that viewer. The protocol does
not currently define viewer-specific visibility for one field inside an
otherwise authorized event.

`MessagePostedEvent.body_plaintext` lets a client show a new message without
waiting for another request. The event does not duplicate the complete message
resource. Use `MessageService.GetMessage` to load attachments, link previews,
reactions, pin state, thread details, and other resource state. A client can
render the event metadata and plaintext first, then replace that temporary row
with the authoritative resource response.

Process one event as one unit:

1. Decode the complete frame.
2. Process the public variant that you understand.
3. Save `resume_cursor` only after your processing succeeds.

Delivery is at least once across reconnects. Use the stable event ID to
deduplicate effects.

New event variants are additive. You can ignore a variant that you do not use
and still save the common cursor. If a complete top-level frame cannot be
decoded, close the socket and keep the preceding cursor.

## Apply the exact snapshot at `E`

If `subscribed.recovery_mode` is `SNAPSHOT`, clear the state that your client
projection owns. The server sends these canonical resource families before
`caught_up(E)`:

| Snapshot value | Meaning |
| --- | --- |
| `ServerPublicProfile` | Current public server profile |
| `ListRoomsResponse` | Complete visible room directory |
| `ListRoomGroupsResponse` | Complete visible room-group layout |
| `BatchGetUsersResponse` | The viewer and users referenced by snapshot resources |
| `ListActiveCallsResponse` | Complete visible active-call state |

The snapshot does not contain the complete user directory. It also excludes
message and thread history, search results, files, pins, notifications,
presence, read markers, and account-security state. Read these resources
through ConnectRPC only when your integration needs them.

Treat each snapshot list as a complete replacement. Do not expose the partial
state as current before `caught_up`. If the socket closes first, discard the
incomplete snapshot and reconnect without its cursor. Events after `E` follow
the snapshot in order, so no client-driven second replay is required.

## Bind a targeted resource read to an event

Some events contain enough data for immediate use but not a complete resource.
When a durable event causes a follow-up ConnectRPC read, set this header:

```http
Chatto-Realtime-Minimum-Cursor: <event.resume_cursor>
```

The serving replica validates the viewer-bound cursor and waits until its
content view includes that event boundary. This prevents a request that reaches
another replica from returning older content. Give each bounded read a finite
deadline. Save the event cursor only after the required read succeeds.

If a new snapshot starts, discard late reads from the earlier local projection
generation. They must not replace newer state.

## Detect a dead connection

The server `hello` reports an approximate heartbeat interval. Reset your
liveness timer after every server frame. Replace the socket when no frame
arrives for several expected heartbeat intervals.

You can send `ping` with an opaque nonce. The server returns the same nonce in
`pong`. WebSocket control pings do not replace the application heartbeat.

A heartbeat can contain a fresh resume cursor for the last durable boundary
that this socket delivered. Save it only after all earlier events and resource
work succeed.

## Handle errors and reconnects

| Frame                           | Client action                                                                                                                                         |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Non-fatal `error`               | Keep the socket open. Retry only the rejected operation and honor `retry_after_ms`.                                                                   |
| Fatal `error`                   | Stop processing that socket and keep the preceding cursor. Retry temporary failures with backoff. Fix protocol or authentication errors before retry. |
| `close` with `reconnect: true`  | Close the socket, wait for `retry_after_ms` or local backoff, and subscribe with the last safe cursor.                                                |
| `close` with `reconnect: false` | Stop automatic reconnects and require the applicable user or authentication action.                                                                   |
| Network close without guidance  | Retry with bounded exponential backoff and the last safe cursor.                                                                                      |

Bearer access credentials can expire while the socket is open. Rotate the
credential and reconnect when the server requests authentication. Same-origin
cookie clients can receive a session-renewal close and must renew the browser
session before they reconnect.
