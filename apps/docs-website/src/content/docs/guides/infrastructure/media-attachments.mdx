Chatto can handle ordinary file uploads, images, avatars, server branding images, link-preview images, and optionally videos and animated GIFs. Small deployments can keep assets in NATS ObjectStore; larger deployments should usually move assets to S3-compatible storage.

## What Members Can Upload

Members can attach files through drag-and-drop, paste, or the file picker when they have `message.attach` and the relevant posting permission.

| Asset type | Behavior |
| ---------- | -------- |
| Images | Dimensions are inspected, image URLs can request resized WebP variants, and thumbnails are cached when enabled. |
| Documents and ordinary files | Stored as persisted assets and exposed through signed URLs. |
| Videos | Accepted only when video uploads are enabled. |
| Animated GIFs | Uploaded as images when video uploads are disabled; queued for derivative processing when enabled. |
| Avatars, logos, banners | Stored in the same asset system but gated by profile or admin permissions. |
| Link-preview images | Downloaded, bounded, stored, and served through the configured storage backend. |

Default upload limits are 25 MB for non-video files and 100 MB for videos when video uploads are enabled.

## Attachment Descriptions

Add a description in the attachment preview before you send a message. After
send, open the attachment controls to add, replace, or remove it. Descriptions
can contain line breaks and can contain at most 1,000 Unicode characters.

Chatto uses an image description as alt text and uses the filename when no
description exists. The attachment viewer shows descriptions for all file types
beside the preview on desktop and below it on smaller screens. File details and
Download share the desktop side panel. You can read an HTML description before
you select **Show preview**. In a gallery, the description follows the selected
image. Long descriptions scroll so the Download and Close controls stay visible. Video, audio,
and file controls expose the description to assistive technology.

Descriptions belong to a message attachment, not to the uploaded asset. Chatto
encrypts each description with the message author's content key. It does not put
the description in upload-session state or permanent asset-ownership events.
Description changes use the same three-hour window and `message.manage` override
as message-text edits.

Message attachments use upload chunks of up to 10 MiB. The browser uses the chunk
limit returned by the server. This limit is fixed and reduces the number of
requests on connections with high latency. If you set a reverse proxy request
body limit, allow at least 11 MiB for each attachment upload request to include
the chunk and request metadata. Avatar and branding uploads can need larger
request bodies.

## Permission And Access Model

File attachments require:

- room membership
- `message.post` or `message.post-in-thread`
- `message.attach`

Attachment URLs are signed per user and still check that the signed user can access the room. If a user leaves, is removed, or loses room access, new asset fetches fail even if an old message still contains the URL.

<Aside type="note">
  Signed attachment URLs are bearer capabilities until they expire. Chatto keeps their TTL bounded and checks the signed user's current room access on every protected asset fetch.
</Aside>

## Room Files

The room sidebar Files panel lists current accessible attachments from root messages and thread replies. It derives from visible message state, so files disappear when their message is deleted or the attachment is removed.

Use this as a member convenience surface, not as a permanent document-management system. There is no attachment search or media filtering yet.

## Link Previews

Chatto fetches link-preview metadata when a user composes a message with a URL. Preview images are persisted through the asset backend, so S3-backed deployments store preview media alongside uploaded files.

The fetcher is designed to be SSRF-safe and caches successful and failed lookups for bounded periods. Operators do not need a separate preview worker.

Supported public Bluesky and Mastodon post URLs render as native Chatto cards. Provider adapters capture a bounded, common snapshot containing the provider, author, post text, attached images, any embedded website card, and at most one quoted post with its media. Mastodon content warnings and accepted quote posts use the same snapshot fields; warned text and media stay concealed until the reader reveals them, and boosts show the original post but do not currently identify who boosted it. Bluesky is resolved through its oEmbed and public post APIs. Mastodon is resolved through the linked server's public oEmbed and status APIs, so compatible public servers are supported without an instance allowlist. For federated proxy permalinks that do not have oEmbed metadata, Chatto verifies the linked server's public instance metadata before using its status API. Images are persisted through the configured asset backend, and clients render the stored snapshot without contacting the provider. If structured discovery fails while composing the message, Chatto falls back to the ordinary link-preview card when OpenGraph metadata is available.

## Storage Backend Choice

| Deployment | Recommended backend |
| ---------- | ------------------- |
| Small server with light uploads | NATS ObjectStore, the default. |
| Active community with many files | S3-compatible storage. |
| Video playback with seeking | Enable video uploads and run an asset-processing worker; HLS works with either storage backend. |
| Replicated NATS cluster | S3-compatible storage to avoid multiplying large binary storage. |

Switching to S3 affects new assets. Existing NATS-stored assets continue to work because each asset records its own backend.

## Video And Animated GIF Processing

Video uploads are optional and disabled by default. When enabled, Chatto stores the original upload and queues durable derivative work. Asset-processing workers require `ffmpeg` and `ffprobe`; they generate a thumbnail and package temporary renditions into durable six-second HLS segments. Chatto generates the small HLS playlists on demand rather than storing them.

Enable uploads only when at least one embedded or standalone worker has CPU and temporary disk space for transcoding:

```toml
[video]
enabled = true

[asset_processing]
enabled = true
max_concurrent_jobs = 2
```

The official Docker image includes the required ffmpeg tools. Host installs need those binaries installed separately.

<Aside type="caution">
  Transcoding is CPU-heavy background work. The durable worker can run inside `chatto run` or separately as `chatto asset-processing`; keep at least one worker available whenever video uploads are enabled.
</Aside>

<Aside type="note">
  New processed videos use HLS for reliable duration detection, seeking, and adaptive quality on both NATS ObjectStore and S3. Videos processed by older Chatto versions are not backfilled and continue using their MP4 variants; unprocessed NATS-backed video files remain complete, non-seekable responses.
</Aside>

## Attachment Viewer

Select a message attachment to open its viewer. For audio and video, select the
filename button below the player. The viewer shows the filename, file type, and
file size. Select **Download** to save the original file, including when the
preview shows a resized image or a processed video.

Images in the same message form a gallery. Use **Previous image**, **Next image**,
or the arrow keys to move between them. The filename, size, and download link
follow the selected image. Browser Back closes the whole gallery. Escape and
Close also close the viewer and return focus to its opening control.

The viewer fills the screen on phones. Close and Download stay visible outside
the preview. Images, audio, and video have previews. Other formats, including
PDFs, text files, and archives, show file details and Download.

### HTML and XHTML

HTML and XHTML previews require a separate choice. Download does not load the
preview.

Select **Show preview** to view the document. Before you select it, Chatto does
not load the document or its external resources. The notice below the button
explains that external websites can see your IP address if the document loads
content from them. Each new opening requires this choice again.

The preview blocks scripts, forms, popups, and access to Chatto's application
state. Documents that need scripts may not work fully. Download and Close stay
available outside the preview. Escape closes the viewer when focus is on its
controls. When focus is inside the document, use Close or press Tab to return
to the viewer controls first.

API clients can add `download=1` to the original attachment URL. Keep its
`access` ticket parameter. The server returns the original bytes with a download
disposition and filename, including for S3 storage.

## Active Document Safety

Uploaded HTML, XHTML, SVG, XML, and XML-derived active document formats are served with a sandbox policy and `nosniff`. S3-backed active documents stream through Chatto instead of redirecting directly to object storage so the sandbox headers stay in place. Active documents also use
`Referrer-Policy: no-referrer` so resource requests do not disclose their
ticketed URLs.
