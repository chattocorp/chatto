# FDR-023: Authentication & Sessions

**Status:** Active
**Last reviewed:** 2026-08-12

## Overview

Chatto authenticates users with typed opaque runtime credentials. API and multi-server clients present bearer credentials, while same-origin browser sessions present cookie-scoped first-party credentials through HTTP-only cookies. The bundled SPA stores bearer tokens for registered servers, including the origin after direct password login or registration, while cookie sessions remain for same-origin auth endpoints and compatibility login flows. Login flows include classic password login, configured external providers, and a bootstrap path for first-boot operator setup.

## Behavior

- **Login** — users sign in with login + password on a `/login` page. The page is also used for redirect-after-signup.
- **External provider login** — operators configure repeated `[[auth.providers]]` entries or equivalent counted `CHATTO_AUTH_PROVIDERS_<index>_<field>` environment variables. Supported provider types are `oidc`, `github`, `gitlab`, `google`, and `discord`. The login page renders buttons from `chatto.discovery.v1.ServerDiscoveryService.GetServer` login providers, and provider flows use `/auth/providers/{providerID}` plus `/auth/providers/{providerID}/callback`. OIDC also keeps `/auth/oidc` and `/auth/oidc/callback` as compatibility aliases for older clients and provider registrations. A matched browser login establishes the HTTP-only cookie session and redirects without a bearer credential; when provider login is nested inside Chatto OAuth authorization, the existing PKCE authorization-code flow continues instead.
- **CIMD public client** — OIDC providers may use a confidential client secret or Chatto's public client ID at `{webserver.url}/oauth/client-metadata.json`. The metadata document declares the exact callback URIs for OIDC providers configured with that client ID and requires Authorization Code with public token authentication, allowing CIMD-aware issuers to use Chatto without preregistration.
- **Chatto OAuth client identity** — browser client applications use their HTTPS CIMD URL as `client_id`; Chatto retrieves the document, verifies its self-identified client ID, public-client grant shape, and exact redirect URI, then binds that client ID through consent, authorization code exchange, and the resulting opaque access token. Metadata retrieval is bounded and blocks special-use network destinations. Chatto Desktop uses the built-in `chatto://desktop` client identity and exact popup callback. Native CIMD clients may declare private-use callbacks with `application_type = "native"`. CIMD identity means the app is identifiable, not endorsed; user consent is still required.
- **OAuth client authorization inventory** — after a successful user-approved authorization, Chatto durably records the client identity, source, validated display name, callback origins, first and latest authorization times, and distinct authorized-user count. Metadata retrieval and abandoned or denied authorization do not add a client to this inventory. Server managers can mark a recorded client default, trusted, or blocked from the Security page. Trusted is an informational label and never skips consent. Blocked clients cannot start or complete authorization or use existing OAuth access tokens; applying the policy terminates matching realtime connections on every replica and also revokes stored tokens best-effort across the shared runtime-state bucket. Unknown future source and policy values remain intact through the administration API. The frontend labels them explicitly and cannot overwrite an unsupported policy, while runtime enforcement denies access for unsupported policies during mixed-version operation.
- **External identity matching and confirmation** — provider identities are linked through durable `EVT` user facts. OIDC providers use the verified issuer URL plus subject; OAuth-only providers use the configured provider ID plus Goth `UserID`. Provider email is profile data unless the adapter has an explicit provider verification signal: OIDC requires `email_verified`, Discord requires `verified`, Google-through-Goth requires `verified_email`/`email_verified`, and GitHub requires a verified primary email from the GitHub emails API. Email is never used as the primary account match key. If a provider callback returns an identity that is not linked to an account, Chatto creates a short-lived pending external-identity flow only when the provider is eligible for the requested action: account creation requires `auto_provision = true`, while account linking requires an already authenticated user who created a provider link-start URL. The user must explicitly confirm create, link, or cancel through ConnectRPC; there is no silent email-based merge. Link confirmation uses the pending-flow capability token so remote-server callbacks do not depend on an origin-local bearer token. Linking and disconnecting providers require a fresh runtime credential or current-password proof. Disconnecting refuses to remove the last sign-in method from a passwordless account. Provider avatar URLs are transient profile hints: Chatto imports them as managed avatar assets during account creation or first matched login when no avatar is already set, and does not persist the remote URL.
- **Invite-link admission** — when `auth.account_creation_policy` is `invite_only`, direct registration and external-provider auto-provisioning carry a validated invite-link ID through their short-lived runtime flows and atomically redeem it with account creation. Existing-account sign-in and provider linking do not require or consume invite links. See FDR-036.
- **Password set/change** — users can set or change their own password from account settings through authenticated ConnectRPC. Adding the first password to a passwordless account does not require current-password proof and preserves existing sessions because it adds a new sign-in method. Changing an existing password requires the current password, applies the same password length policy as registration/reset, writes the password hash as a durable user event, and revokes existing runtime credentials. Server admins can set another user's password through `AdminUserManagementService`; admin-set passwords do not require the old password, reject self-targets, and revoke the target user's runtime credentials.
- **Chatto OAuth authorization** — cross-origin Chatto clients use `/oauth/authorize` with a stable `client_id` and PKCE to obtain a short-lived authorization code, then exchange it with that same client ID at `/oauth/token` for an opaque delegated access token. The bundled multi-server client opens the remote server's authorization UI in a separate browser or Electron window, so passwords, passkeys, and external-provider sign-in remain visibly hosted by that server while the main client stays mounted. The callback returns only the authorization result to the main client, which performs the code exchange and stores the token. Browser clients identify themselves through their published frontend CIMD document; Chatto validates the requested callback exactly against it. Desktop uses its fixed built-in client and callback. The first authorization shows a user consent screen and remembers approval per user + client ID. OAuth access tokens can authenticate ordinary API and realtime requests, but cannot satisfy or acquire fresh-auth status for account-security operations.
- **Cross-origin transport** — Chatto permits browser HTTP and realtime transport from any syntactically valid origin without enabling credentialed CORS. Requests carrying a foreign `Origin` never authenticate through ambient session cookies and must present a bearer token. The `allowed_origins` and `oauth_redirect_origins` settings and origin-only OAuth flow were removed for 0.5; compatibility with pre-0.5 clients is not required.
- **Cookie session** — on successful same-origin auth, the server issues an HTTP-only, SameSite=Lax cookie with a 90-day expiry. New signed browser sessions carry only an opaque first-party credential handle; the authoritative runtime credential lives in `RUNTIME_STATE` under `session.{hmac}` with user ID, kind `first_party_session`, presentation `cookie`, source/request metadata, auth generation, fresh-auth metadata, and a per-key TTL. The server validates the runtime credential and resolves the current user from projections per request. Deprecated legacy signed sessions may still carry `user_id` plus `cookie_session_id`, and deprecated legacy `cookie_session.{userId}.{hmac}` `CookieSession` protobuf records remain readable until existing sessions expire or a documented pre-1.0 compatibility cutoff removes them. The bundled SPA keeps this cookie as a compatibility fallback, but uses bearer tokens for registered-server API and realtime requests when one has been issued.
- **CSRF protection** — cookie-session unsafe same-origin requests must include an `X-CSRF-Token` header matching the readable `chatto_csrf` cookie, and that cookie value must be a server-signed token bound to the authenticated user session generation. Public auth/bootstrap endpoints, test endpoints, webhooks, OAuth token exchange, and ConnectRPC programmatic API traffic are exempt. Bearer-only requests are exempt because bearer credentials are not ambient browser cookies.
- **Bearer token** — direct password/registration flows and explicit external-identity account creation issue an opaque first-party session token (format: `cht_AT` + 14-char NanoID) for registered clients. Matched external-provider browser login is cookie-only and never places a bearer credential in its redirect URL; cross-origin clients use the Chatto OAuth PKCE flow instead. Registered clients store bearer tokens in `localStorage` and send them as `Authorization: Bearer …` on HTTP requests and as the realtime websocket token. The token record lives in `RUNTIME_STATE` as an HMAC-derived `session.{hmac}` key with kind `first_party_session`, presentation `bearer`, and a per-key TTL. Delegated OAuth access tokens use the same key family with kind `oauth_access_token`, presentation `bearer`. If bearer-token issuance fails after a cookie session was created in a flow that requires both presentations, the server revokes the cookie session and fails the auth response rather than leaving the client half-authenticated.
- **WebSocket auth** — bearer-token clients pass the token in `connectionParams`, which is checked at upgrade time. Cookie fallback is accepted only for same-origin browser connections (or non-browser requests without an `Origin` header).
- **API auth failures** — protected ConnectRPC methods return unauthenticated errors for missing or invalid credentials. The bundled multi-server client prefers structured error codes and keeps stable message fallbacks for compatibility with older servers.
- **Logout** — from the global header, users choose whether to sign out of the currently selected server or all connected servers. For registered bearer-token sessions, the client sends the token to `/auth/logout` so the server can revoke it and then removes the token locally. Cookie fallback logout deletes the current cookie-presentation runtime credential, clears the cookie, and the SPA does a hard reload. The HTTP logout route normalizes bearer and cookie credentials through the same runtime-credential revocation result before writing logout audit facts or publishing session-termination events. Logout requests are best-effort so users can still remove stale or unreachable server registrations locally.
- **Known signed-out servers** — the frontend server catalogue is independent from device-local sessions. A server restored through Authling can appear signed out on a new device; selecting it starts the server's normal OAuth flow. Chatto bearer tokens and local user summaries never synchronize through Authling.
- **Global sign-out** — signing out of all servers clears every device-local Chatto session, disconnects the frontend from Authling, removes remote catalogue entries on this device, and retains only a configured origin entry in a signed-out state. Remote revocation and Authling cleanup are best-effort, so unavailable services cannot trap the user in stale local state.
- **Session refresh** — runtime credentials use a sliding-window TTL: each successful validation rewrites the `RUNTIME_STATE` entry with a fresh per-key TTL. Cookie sessions also rotate their opaque browser cookie handle near the browser cookie's fixed expiry, preserving fresh-auth metadata while deleting the old credential best-effort.
- **Password and account lifecycle revocation** — password resets, password changes, external identity disconnects, and account deletion advance the user's auth generation through durable `EVT` user events. Cookie sessions, bearer tokens, and OAuth authorization codes store the auth generation they were issued against; validation waits the user projection to the current auth-generation events and rejects credentials from older generations. Adding the first password to a passwordless account marks the password event to preserve existing credentials and does not advance auth generation. Generation `0` is reserved for pre-field legacy runtime credentials and is upgraded on validation when the credential is not older than the current revoking password event. User-wide cleanup scans `session.*` by presentation to delete cookie and bearer runtime credentials, plus legacy `cookie_session.*` records while they remain readable.
- **Password reset tokens** — reset links are backed by `RUNTIME_STATE` HMAC-derived `password_reset.{hmac}` records with a 1-hour per-key TTL. A separate HMAC-derived `password_reset_request.{hmac}` reservation permits one delivered reset link per account every five minutes across all server replicas. Unknown addresses, accepted requests, and throttled requests receive the same generic response. Failed delivery cancels the unusable token and releases its matching reservation. Raw reset tokens, links, and account identifiers are never stored in reservation keys or written to `EVT` or backup archives.
- **Server version handshake** — the WebSocket `connection_ack` payload includes the server's version. The frontend uses this to detect deployed-version drift and prompt the user to refresh.
- **Auth audit facts** — successful cookie/provider logins, failed password login attempts, logout completion, bearer-token issuance/revocation, OAuth consent decisions, OAuth authorization-code issuance/exchange, registration-code issuance, email-verification-code issuance, password-reset link preparation, and password-reset completion are appended to `EVT` for admin audit-log inspection. Password-reset preparation is recorded before SMTP delivery so an audit-storage failure cannot leave a delivered but untracked credential; if delivery then fails, the runtime token is canceled even though the preparation fact remains. Payloads carry safe request metadata only: capped user agent, HMAC-hashed IP, and hashed identifiers where needed.

## Design Decisions

### 1. Cookie-based sessions for same-origin

**Decision:** The embedded SPA authenticates via HTTP-only `SameSite=Lax` cookies. New signed browser sessions store only an opaque first-party credential handle, while the authoritative typed runtime credential lives in `RUNTIME_STATE` with user ID, per-key TTL, source/request metadata, fresh-auth metadata, and auth generation. The current user record is resolved from projections per request.
**Why:** Cookies are the simplest mechanism for browser SPAs — the browser handles attachment, expiry, and HttpOnly protects against XSS-extracted tokens. Storing the server-side runtime credential in `RUNTIME_STATE` adds revocation for logout, password changes/resets, and account deletion while staying within Chatto's NATS-backed runtime-state model. WebSocket auth comes from the browser sending the cookie with the upgrade request. See ADR-017, ADR-036, and ADR-046.
**Tradeoff:** Non-browser clients can't use cookies. The bearer token path exists for them.

### 1a. CSRF protection for cookie-authenticated writes

**Decision:** Same-origin cookie-session writes require a CSRF proof unless they target public auth/bootstrap endpoints, test endpoints, webhooks, OAuth token exchange, or ConnectRPC programmatic API traffic. The server mirrors a readable `chatto_csrf` cookie for the SPA and accepts `X-CSRF-Token` only when it matches that cookie and verifies as a server-signed token for the current authenticated user generation. Bearer-only requests skip the CSRF check.
**Why:** Cookie sessions are ambient browser credentials, so another site can try to submit state-changing requests with the user's cookie attached. Storing CSRF state inside the signed browser session cookie made concurrent cookie refreshes brittle. Signed stateless tokens keep CSRF independent of session-cookie rewrites while preserving the double-submit browser proof. ConnectRPC requests are exempt because browsers cannot submit `application/proto` or `application/connect+proto` via plain HTML forms.
**Tradeoff:** The frontend must attach the CSRF header for protected origin POSTs outside the exempt API paths. The token is not HttpOnly by design; it is not an auth secret, only a same-origin request proof paired with server-side signature verification.

### 2. Bearer tokens for cross-origin

**Decision:** Cross-origin clients (multi-instance frontend, CLI tools) authenticate via opaque bearer tokens stored in `RUNTIME_STATE` under HMAC-derived `session.{hmac}` keys. Tokens are validated by KV lookup plus the current user auth generation derived from `EVT`; single-token revocation is one delete, and user-wide cleanup scans `session.*` for records owned by that user.
**Why:** Cookies are scoped to one origin and `SameSite=Lax` blocks them on cross-origin requests. Tokens are origin-agnostic. We chose opaque tokens over JWTs because Chatto still resolves the current user and permissions server-side per request — JWT's "stateless validation" advantage gives little here, while opaque tokens give instant revocation and natural TTL via KV's built-in expiry. See ADR-024.
**Tradeoff:** Tokens stored in `localStorage` are vulnerable to XSS; cookie sessions are not. Cross-origin clients accept this tradeoff in exchange for being able to authenticate at all. Operators must keep `[core].secret_key` stable across restores to preserve active bearer-token sessions.

### 3. Sliding-window TTL for tokens (and cookies)

**Decision:** Each successful runtime credential validation rewrites the runtime-state entry with a fresh per-key TTL (default 90 days). Cookie sessions use the same inactivity window and rotate the browser cookie handle near browser-cookie expiry.
**Why:** Time-from-creation expiry would surprise users — "you've been logged in for 90 days, time to re-auth, even though you've been using the app daily". Sliding-window means active users stay logged in indefinitely; only genuinely inactive sessions expire.
**Tradeoff:** A long-stolen token stays valid until it lapses, gets explicitly revoked, or the user's password lifecycle advances the auth cutoff. Operators concerned about shorter compromise windows can lower the TTL.

### 4. WebSocket auth at HTTP upgrade

**Decision:** For cookie clients, authentication happens at the HTTP upgrade handshake. For bearer-token clients, the token is validated from the `connectionParams` payload during the upgrade. By the time the WS is open, the user is already authenticated.
**Why:** Doing auth inside the WS protocol (a `connection_init` payload exchange) adds round-trips and creates a window where the WS is open but not authenticated — easy to misuse, easy to leave open by accident. Upgrade-time auth is atomic. See ADR-017.
**Tradeoff:** Bearer-token WebSocket clients have to deliver the token during the realtime websocket handshake.

### 5. Per-request user resolution, no in-session caching

**Decision:** Even though the session stores a user ID, the user record is resolved from the current projections on every request and every realtime websocket handler.
**Why:** Caching the user in the session would mean serving stale data (display name, roles) across requests. Users expect profile, role, and deletion changes to be immediate; projection-backed resolution gives the current view while keeping sessions small. Dataloaders batch within a single request to prevent fan-out.
**Tradeoff:** Each request still performs server-side user and permission resolution. At Chatto's volume, this is far below noise.

### 6. Cookie auth unchanged when token auth was added

**Decision:** ADR-024 added bearer tokens as a *parallel* presentation path rather than replacing cookies. The auth middleware checks the `Authorization` header first and falls back to the cookie; both paths now validate typed runtime credentials from `RUNTIME_STATE` and inject the same normalized request credential shape: presentation kind, user ID, and opaque handle.
**Why:** Existing deployments don't need user-visible migration. The embedded SPA keeps working through cookies. Multi-instance frontends and CLI tools get bearer tokens. Both presentation shapes coexist while sharing runtime credential semantics.
**Tradeoff:** The HTTP edge still has to understand both bearer and cookie presentation, and legacy `cookie_session.*` records remain readable during the rollout.

### 7. Server version in `connection_ack` for deploy detection

**Decision:** The WebSocket `connection_ack` payload includes the server's binary version. The frontend stores it and prompts the user to refresh when a newer version is detected mid-session.
**Why:** Without it, users get subtle errors when a deployed schema change lands but their old client is still connected. A "the server has been upgraded, please refresh" toast handles it explicitly.
**Tradeoff:** The frontend has to handle the toast and the user has to act on it. Considered acceptable for the rare deployment-during-session case.

### 8. OAuth code exchange and client metadata

**Decision:** Chatto's OAuth authorization endpoint returns a short-lived authorization code to the client's exact callback; the client exchanges that code plus its `client_id`, callback, and PKCE verifier at `/oauth/token` for a bearer token. Browser clients identify themselves with CIMD. The server retrieves and validates their metadata without following redirects or reaching special-use network addresses. Chatto Desktop has an exact built-in registration. Consent is remembered per user + stable client identifier, and the client ID remains attached to the authorization code and access-token runtime records. The bundled multi-server client runs authorization in a separate window and relays the result from its same-origin callback to the still-mounted main client.
**Why:** Keeping the remote server's own authorization UI visible makes password, passkey, and external-provider sign-in work without teaching the multi-server client each server's authentication methods or asking users to submit credentials to a lookalike client form. PKCE protects the code, while CIMD exact callback binding prevents a client or attacker from substituting another destination. The open CIMD model lets compatible apps connect without operator coordination while retaining identity for consent, audit, revocation, and policy.
**Tradeoff:** Browsers can block the secondary window when the flow is not started by a direct user action, while desktop hosts must provide and secure an equivalent native-window lifecycle. Every client must publish stable metadata and coordinate a second browsing context. Chatto performs a bounded outbound metadata request at authorization time. CIMD publication proves control of a client URL but is not an endorsement of its software. See ADR-071.

### 8a. Durable OAuth-client authorization inventory and policy

**Decision:** Every successful authorization of a stable client ID appends an authorization-recorded EVT fact. The projection retains its validated metadata, callback-origin set, first and latest authorization times, and distinct authorized-user set. Administrators can append policy changes for default, trusted, or blocked. A cold-replayed projection serves the admin list and the authorization hot path. Trusted is descriptive only. Blocked is enforced when authorization starts, before and after authorization-code issuance, at code exchange, before and after OAuth token creation, during token validation, and for established realtime connections. Unknown future policies use the same denied-access path so an older replica cannot bypass a newer policy during a rolling upgrade. After initial credential validation, each socket atomically checks the current projected policy while registering a process-local watcher; every replica's projection closes the matching watchers when it observes a blocked or unsupported policy. Applying a block also scans `session.*` to revoke matching OAuth access tokens. Per-client EVT aggregate subjects contain a SHA-256 digest of the client ID rather than its URL.
**Why:** Successful authorization is the point at which a client has actually gained access and is worth showing to administrators. Durable facts preserve that inventory and policy across restarts and replicas without allowing arbitrary CIMD probes to fill it. Checks around both sides of runtime-credential writes close the races where another replica blocks a client during issuance. Projection-backed socket watchers extend the same durable boundary to already authenticated transports without disconnecting the user's first-party or other-client sessions. Hashing the aggregate ID keeps URL punctuation and path data out of NATS subjects while the event payload retains the recognizable stable ID needed by the projection.
**Tradeoff:** Authorized user IDs are retained privately by the projection to compute a distinct count, although the admin API exposes only that count. Blocking requires a bounded global token scan in addition to the constant-time projection check; cleanup is best-effort because validation and realtime projection watchers independently enforce the durable policy. The watcher registry is process-local acceleration rebuilt naturally as sockets reconnect, while EVT remains authoritative. Trust does not currently unlock extra behavior.

### 8b. External provider registry and identity links

**Decision:** External login providers are configured as repeated `[[auth.providers]]` entries with stable local IDs, curated provider types, labels, client credentials, optional scopes, optional email-scope requests, configurable auto-provisioning, and provider options reserved for provider-specific expansion. OIDC clients may be confidential or public; a provider configured with `{webserver.url}/oauth/client-metadata.json` uses Chatto's built-in CIMD document and no client secret. OIDC verification remains on `go-oidc`; OAuth-only providers use Goth for authorization-code exchange and normalized user fetching. Linked and disconnected identities are durable `EVT` facts on the user aggregate. Pending create/link confirmations live in `RUNTIME_STATE` as HMAC-derived `external_identity_create.{hmac}` and `external_identity_link.{hmac}` records with short TTLs. Bearer-authenticated provider linking first creates a one-time `external_identity_link_start.{hmac}` handoff token, which the target server consumes before starting the browser redirect to the external provider. Users may disconnect linked provider identities from account settings, but Chatto refuses to remove the last available sign-in method from a passwordless account. The browser-only provider redirects remain HTTP routes, while confirmation uses `chatto.auth.v1.ExternalIdentityAuthService` and authenticated management uses `chatto.api.v1.MyAccountService`.
**Why:** A provider list lets operators expose more than one login option without hard-coding a single OIDC provider. Keeping the provider ID stable gives OAuth-only providers a local issuer namespace. OIDC uses the verified issuer URL as the durable namespace because the issuer owns subject uniqueness; the configured provider ID is event-time metadata and can change without invalidating existing OIDC links. Matching by issuer/provider plus subject survives provider-side email changes and avoids account takeover through recycled or unverified email addresses.
**Tradeoff:** Existing `[auth.oidc]` TOML configuration is not accepted by this shape; deployments should use `[[auth.providers]]`. Legacy `CHATTO_AUTH_OIDC_*` environment variables are still accepted as a compatibility bridge for one OIDC provider. Account creation/linking for new external identities adds an explicit confirmation step, but keeps external identity tokens capability-scoped and avoids surprising account creation. Email scopes are opt-in with `request_email = true`; OIDC providers can run with the default email-less `openid profile` request, in which case account creation, linking, and login still use issuer plus subject while password reset by email remains unavailable until the user verifies an email.

### 8c. Separate catalogue, server sessions, and Authling session

**Decision:** Known server metadata, device-local Chatto sessions, and the frontend's Authling grant have separate state owners. Cross-boundary sign-out commands run through one client account coordinator. The legacy combined browser-storage record remains only as a compatibility adapter.
**Why:** A synchronized server can be known while signed out, and public account data must never gain access to local Chatto credentials. Separate ownership also prevents entries learned from one Authling account from leaking into another account. See ADR-064.
**Tradeoff:** The frontend retains a composed server view and combined persisted shape during migration, so the adapter and coordinator require explicit tests.

### 9. EVT audit facts without raw secrets

**Decision:** Authentication workflows append durable audit facts to `EVT`, but token bodies, verification codes, links, passwords, auth codes, raw IP addresses, full redirect URIs, and raw login/email identifiers stay out of the event log. Source IPs are HMAC-hashed before persistence; forwarded client-IP headers affect attribution only when the direct peer matches an explicit `webserver.trusted_proxies` IP/CIDR entry, otherwise the direct peer is hashed. OAuth consent grant/deny facts store the canonical callback origin or native callback scheme plus validated client ID and display metadata in plaintext so users and administrators can recognize approved client applications. Successful user-scoped facts live on `evt.user.{userId}`; anonymous/server-wide facts such as registration-code issuance and failed login attempts live on `evt.auth.server`.
**Why:** `EVT` is Chatto's durable audit trail as well as the event-sourcing stream. Operators need to answer "what happened?" for sensitive workflows, but the audit log must not become a secondary secret store.
**Tradeoff:** Failed-login and unknown-code exchange attempts intentionally do not reveal whether the submitted identifier or code matched an account. Admins get timing, request metadata, and stable hashes for known-user workflows, not raw credential guesses.

**OTP guardrails:** Registration and authenticated email-verification OTPs share `RUNTIME_STATE` `email_otp.*` records. By default, throttling is enabled and each challenge allows at most ten successfully delivered codes and five wrong-code attempts in its 15-minute TTL window; operators can tune or disable these throttles through `auth.email_otp` / `CHATTO_AUTH_EMAIL_OTP_*`. Exhaustion blocks fresh codes for that challenge until TTL. If email delivery fails, the just-created OTP record is cancelled and does not count against the issued-code limit.

### 10. Short-lived auth codes in runtime state

**Decision:** Pending OAuth authorization browser flows, OAuth authorization codes, external-identity link-start handoffs, and pending external-identity confirmation flows live in `RUNTIME_STATE` as HMAC-derived records with short per-key TTLs and are deleted on successful consumption/exchange/confirmation. Pending OAuth authorization flows use `oauth_authorize.{hmac}` with a 15-minute TTL; the browser session carries only the opaque lookup token. OAuth authorization codes use `grant.{hmac}` with a 5-minute TTL. External identity confirmations use capability-scoped `external_identity_create.{hmac}` and `external_identity_link.{hmac}` records with a 15-minute TTL. Provider link-start handoffs use `external_identity_link_start.{hmac}` with a 15-minute TTL and are consumed before provider authorization begins.
**Why:** Authorization codes and external-identity tokens are short-lived runtime credentials. They need restart survival and TTL enforcement, but they are not domain history and must not be copied into `EVT`.
**Tradeoff:** Pending browser authorization now requires shared runtime storage even before a code is issued. The returned authorization code and browser behavior remain opaque and unchanged for clients, but stored keys are not human-recoverable from a backup without `[core].secret_key`.

## Permissions

Authentication itself doesn't have a permission gate (you're either authenticated or not). After authentication, downstream actions are gated by the permissions described in FDR-001.
