A **permission** controls one action, such as posting messages or managing
rooms. A **role** gives a set of permissions to many people. Each permission
setting is **Allow**, **Deny**, or **Inherit**.

## How permissions work

- **Every signed-in person has the `everyone` role.** You can also assign the
  built-in `moderator` and `admin` roles, and your own roles.
- **You set a permission at a scope.** A channel room checks Room, then Room
  group, then Server. A direct message (DM) checks Direct messages, then
  Server. **Inherit** uses the next broader setting of the same user or role.
- **The most specific setting wins for one user or role.** A room setting
  replaces the room-group and server settings of that user or role. It does not
  replace the settings of a different role.
- **A deny wins.** If the user or one of their roles denies an action, Chatto
  denies it, even when a different role allows it.
- **`everyone` is the baseline.** An allow on a user or a named role overrides
  an `everyone` deny only at the same scope or a more specific scope.
- **No setting means no access.**
- **Owners have every permission in privileged mode.** Without the mode, an
  owner has only the permissions of their roles and grants. You cannot lock
  out an owner, because an owner can always enable privileged mode. A user is
  an owner when they have the `owner` role or a verified email address in
  `owners.emails` in `chatto.toml`. Use `owners.emails` to recover access if
  you lock yourself out.
- **Message access also needs membership.** An account must be a member of the
  room or the DM to read it. Owners and administrators cannot read DMs that
  they are not part of.

| Settings | Result |
| -------- | ------ |
| Server: `everyone` Deny, `admin` Allow | **Allowed** for admins. Both settings are at the same scope. |
| Room: `everyone` Deny. Server: `admin` Allow | **Denied**. The room setting is more specific. Add a room-level allow for `admin`. |
| Server: `admin` Allow, `suspended` Deny | **Denied** for a user with both roles. The deny wins. |

Bots do not get permissions from `everyone` or from other roles. A bot has only
the permissions that you allow directly on the bot, and never more than its
owner has. This includes administrative permissions. `bot.manage` also permits
issuing credentials for other bots, which use those bots' permissions and
owner ceilings. See [Bot accounts](/guides/integrations/bot-accounts/).

## Built-in roles

Every server has four system roles. You cannot delete them. The order of the
roles does not change which setting wins.

| Role | Purpose |
| ---- | ------- |
| `everyone` | Baseline member access. |
| `moderator` | Message moderation and room-member removal. |
| `admin` | Server, account, room, role, and bot administration. |
| `owner` | Full authority while privileged mode is active. |

Moderators and admins also have the baseline member permissions of `everyone`.
Inspect the server's saved grants before you delegate access. Existing servers
keep their settings when defaults change.

## Privileged mode

Administrative and moderation permissions stay off during normal chat use. To
use them:

<Steps>

1. Select the shield in your user area.
2. Confirm **Enable privileged mode**.

</Steps>

Privileged mode lasts 15 minutes and does not extend. Select the shield again
to stop it sooner. It applies only to the server
session where you enabled it. The event log records each activation and
deactivation.

Privileged mode turns on permissions, not roles. It applies to each permission
marked as privileged in the server's permission settings, from any
role or user setting. It does not give you permissions that you do not have.

For owners, privileged mode also turns on the owner permissions. Without the
mode, an owner cannot see, join, or read a room that denies this to
`everyone`, unless one of their roles or a direct grant allows it. If an owner
joins such a room in privileged mode, they stay a member, but they can read the
room only while the mode is active. Chatto removes them from a call in such a
room shortly after the mode ends. Notifications use the permissions without the
mode. MCP clients cannot enable privileged mode.

Without privileged mode, Server Administration stays visible, but its
protected actions are not available. The Moderation page needs server-wide
`room.remove-member`, so it is available only in privileged mode.

Bots do not use privileged mode. To allow a privileged permission for a bot,
you must have that permission active at the same scope. You can remove a bot's
permission without privileged mode.

## Permission reference

Use the server's permission settings to inspect the available permissions.
For API integrations, see the
[permission API reference](/reference/connectrpc-api/permissions/) and
[role administration reference](/reference/connectrpc-api/admin-roles/).

An allow for a broad permission also permits the actions that it includes.
A deny for an included permission does not restrict that broad allow. To stop
all posting, deny `message.post`, `message.post-in-thread`, and
`message.post-in-interactions`.

## Direct messages

DMs use the `message.*` and `call.*` permissions at the **Direct messages**
scope. No `room.*` permission applies to DMs. If you do not set a Direct
messages value, the Server setting applies.

- People and bots need `message.post` to start a DM. Bots need an explicit
  grant, bounded by their owner's authority. This also lets existing bots
  with DM posting permission initiate conversations.
- A participant with `message.manage` can edit or delete the messages of other
  participants. Nobody can moderate a DM that they are not part of.

## Check room access

Explicit membership gives access independently of `room.list` and `room.join`.
A deny of discovery or self-join does not remove current members. Check the member
list when you restrict a room. Message access still requires a read permission.
Owners and administrators cannot read conversations through Chatto without
membership.

A universal room adds members according to `room.join`. Members cannot leave it;
to remove access, change the relevant permissions or suspend the member in that
room. Archiving hides a room from active lists but does not erase its data.

## Threading Mode

A room's Threading Mode controls whether threads are required, encouraged,
optional, or disabled. It applies to new posts and does not remove existing
threads. It does not replace message permissions. Check both room policy and
permissions when an integration cannot post.

## Neighbors

The Neighbors directory publishes server origins that your community recommends.
A recommendation grants no access and creates no trust relationship. Limit
`server.manage-neighbors` to accounts that can maintain this public list. It is
not a federation or data-replication setting.

## Room invitations

Grant `room.invite` only to members who can admit other server members to a room.
An accepted invitation bypasses `room.join`, but does not grant message or call
permissions. Check invitations and current membership when you restrict access.

## Where to configure permissions

| Task | Where |
| ---- | ----- |
| Create roles | Server Administration → **Roles** → **Create role** |
| Edit a role and its permissions | Server Administration → **Roles** → role |
| Set server-wide permission defaults | Server Administration → **Permissions** |
| View the members of a role (`role.assign` required) | Server Administration → **Roles** → role → **Members** |
| Assign roles | Server Administration → **Members** → member → **Roles** |
| Set permissions for one user | Server Administration → **Members** → member → **Permissions** |
| Set permissions for one bot | Server Administration → **Bots** → bot → **Permissions** |
| Set room permissions | The room's settings → **Permissions** |
| Set room-group permissions | The room group's settings |
| Set recovery owners | `owners.emails` in `chatto.toml` |

To add an account to a room or remove it, use the **Joined** row in the
account's permissions. You need `user.manage-accounts`, or `room.manage` for
that room. The account does not need `room.join`. This row does not change
permissions or DMs.

## Upgrading from 0.4

Chatto applies default permissions only on a new server. When a 0.4 server
starts with 0.5 for the first time, Chatto adds these grants one time to keep
the 0.4 behavior:

- `message.read` for `everyone` at Server scope.
- `room.remove-member` for each role and user that had `room.ban-member`, at
  the same scope. `room.ban-member` has no effect in 0.5.
- Each `call.*` permission for `everyone`.

Make these changes on an upgraded server:

- **Allow `user.manage-invites` and `bot.manage`** for `admin` if admins must manage
  invitation codes and bots.
- **Allow `bot.create`** for the roles that can create bots.
- **Allow `room.manage`** for delegated room managers. In 0.4, room-group
  management used `role.manage`.
- **Allow `message.post`** for `admin` and `owner` in the `announcements` room
  if they must post there without privileged mode. New servers have these
  grants; existing servers keep their current settings.
- **Check `message.post`.** It now also allows thread replies, so a deny of
  `message.post-in-thread` does not stop replies.
- **Check `everyone` denies.** An allow on a named role or user at the same or
  a more specific scope now overrides them.

<Aside type="caution">
  Administrators, moderators, and owners must now enable
  [privileged mode](#privileged-mode) to use their administrative permissions.
  This also applies to custom `room.create` grants. Owners also need privileged
  mode to see, join, or read rooms that deny this to `everyone` when no explicit
  grant allows access. Give the `owner` role a room-level allow if owners need
  this access during normal use.
</Aside>

See the [0.5.0 release notes](/releases/0-5-0/) for all upgrade steps.
