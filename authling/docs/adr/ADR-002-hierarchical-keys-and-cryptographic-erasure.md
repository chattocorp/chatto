# ADR-002: Protect User Data with Hierarchical Keys and Cryptographic Erasure

**Status:** Accepted

**Date:** 2026-07-31

## Context

[ADR-001](ADR-001-event-sourced-nats-architecture.md) makes Authling's
append-only event log the source of truth for accounts, credentials, linked
identities, OIDC state, and app-scoped user documents. Those events must remain
replayable, but much of their payload is personal, secret, or
credential-adjacent data that users may later erase.

Deleting or rewriting every historical event is incompatible with immutable
event sourcing and difficult to make reliable across JetStream replicas,
backups, projections, and snapshots. Merely appending a deletion event prevents
normal reads but leaves earlier plaintext recoverable to an operator or from a
backup.

Chatto already demonstrates useful mechanics: KMS-owned per-user wrapping keys,
purpose-scoped data-encryption-key (DEK) epochs, authenticated encryption bound
to event context, opaque key references, encrypted projection state, and
crypto-shredding. Authling can extract and harden application-neutral parts of
that design while keeping its own data classifications, key purposes, storage
coordinates, event vocabulary, and deletion policy.

Chatto also exposes a failure mode that Authling should not copy: destroying
keys before the corresponding durable shred event commits can leave data
irreversibly unreadable without a replayable tombstone or retry signal.

## Decision

Authling will encrypt sensitive durable payloads with hierarchical user and
data keys. Deleting key material will provide account-wide cryptographic
erasure without mutating historical events.

### Protected data

Raw personal and secret values must not be stored as plaintext in `EVT`,
runtime state, projection snapshots, durable indexes, logs, or ordinary data
backups. Protected values include:

- email addresses and normalized login identifiers;
- password verifiers and password-recovery material;
- upstream provider subjects, tokens, and provider profile data;
- consent details when they reveal user activity;
- user document keys and values; and
- any future field classified as personal, secret, or credential material.

Passwords, authorization codes, raw session credentials, and equivalent
bearer material must not be persisted in recoverable form at all. When a
password verifier or upstream token must be retained, it is encrypted in
addition to using the credential's own one-way or provider-defined protection.

Events may retain the non-sensitive structure required for deterministic
replay after erasure: opaque entity IDs, event IDs and types, key references,
key purposes and epochs, state transitions, timestamps, and deletion
tombstones. Event design must minimise this residual metadata and must not hide
personal data in subjects, IDs, key references, or diagnostic labels.

### Key hierarchy

Each account receives an opaque KMS-managed **user key**. Authling refers to it
only through an opaque key reference; event subjects and public user IDs must
not be usable as KMS storage coordinates.

Sensitive values are encrypted with random **data keys**, not directly with
the user key. A data key belongs to a declared purpose and epoch and is wrapped
by the user's key. Initial purpose boundaries will distinguish at least:

- core account and profile data;
- authentication credentials and linked identities; and
- app-scoped user documents.

Key granularity follows the promised erasure boundary. A feature that promises
independent cryptographic erasure of one credential, application namespace, or
document must give that scope independently destroyable key material. Purpose
names, scope identifiers, epochs, wrapping algorithms, and rotation rules are
persisted contracts and must be versioned deliberately.

Wrapped data-key records live in an Authling-owned key store outside `EVT`.
Events contain only the opaque data-key reference and the metadata required to
select and authenticate the correct key. The key store has its own access,
backup, restore, and deletion policy and must not be treated as ordinary
runtime state.

Destroying a user key makes every data key wrapped by it unusable and is the
account-wide cryptographic-erasure boundary. Destroying one wrapped data-key
record erases its current scope from live storage, but historical key exports
or backups may still contain that record. Authling must not promise narrower
cryptographic erasure across backups unless the scope uses an independently
destroyable wrapping key or a proven rewrapping and backup-retirement protocol.

### Encryption envelopes

The initial application encryption scheme will use XChaCha20-Poly1305 with
random 256-bit keys and 192-bit nonces generated by a cryptographically secure
random source. Key wrapping will also use authenticated encryption. Every
persisted envelope identifies its version, algorithm or key scheme, data-key
reference or epoch, nonce, and ciphertext.

Additional Authenticated Data (AAD) will bind ciphertext to a versioned,
Authling-specific context containing the relevant event ID and type, account
ID, data purpose, key epoch, and any application, credential, document, or
field identity needed to prevent ciphertext substitution. A ciphertext copied
to another event, account, field, application, or document must fail
authentication.

Algorithm and envelope versions are storage contracts. New writers may move to
a new scheme only with an explicit mixed-history read and migration plan.

### Projections, lookups, and plaintext lifetime

In-memory projections retain encrypted source fields and key references.
Plaintext is materialized only at the narrow command or response boundary that
needs it and is not cached beyond that operation.

Equality and uniqueness indexes derived from protected values will initially
remain in memory. They use normalized, keyed digests rather than plaintext map
keys and are rebuilt by decrypting active events during replay. Digests must
not be persisted in `EVT` or snapshots unless a later decision demonstrates
that their correlation and erasure properties are acceptable.

When an erasure tombstone is projected, every derived lookup entry and cached
plaintext or unwrapped key for the affected scope is purged. A missing key for
active data, an unavailable KMS, or a decryption failure is an operational
error and must fail closed; it must never look like an absent account,
available email address, invalid password, empty document, or successful
deletion.

Projection snapshots may contain ciphertext, opaque key references, and safe
structural state, but never plaintext protected values, password verifiers,
provider tokens, unwrapped keys, or derived indexes that weaken
crypto-shredding. Snapshot-level encryption from ADR-001 is defense in depth
and does not make unsafe projection contents eligible for persistence.

### Provisioning and erasure workflows

Key creation and destruction cross the transactional boundary between `EVT`
and a KMS or key store. These operations require durable, idempotent workflows;
best-effort compensation is insufficient.

Key provisioning uses a stable opaque operation identity. KMS and key-store
creation must be idempotent for that identity, and Authling must be able to
discover and remove provisioned keys that never become referenced by a
committed event. An event must never advertise active encrypted data before all
key material needed to decrypt it exists.

Erasure follows this order:

1. Commit an erasure-requested event with OCC.
2. Project the request as an immediate access-denial tombstone.
3. Let a replayable, multi-replica-safe effect worker idempotently destroy the
   applicable data keys and, for full account erasure, the user key.
4. Commit an erasure-completed event after destruction succeeds.

The committed request is the durable retry signal. If Authling crashes before
destruction, another worker resumes it. If it crashes after destruction but
before completion, the worker treats already-absent keys as success and records
completion. No request path may decrypt or expose data once the erasure request
is committed, even while physical key destruction is retrying.

The effect worker's cursor, lease, and retry policy are operational mechanics,
not the correctness boundary. Correctness comes from the durable request,
idempotent key destruction, projected denial, and completion event.

### Backup and KMS boundary

The user-key and wrapped-data-key store is separate from ordinary Authling data
backups. A data backup without the corresponding key material contains
ciphertext that cannot be recovered. Operators therefore need an explicit,
separately protected key export or external-KMS recovery procedure.

Key backups are exceptionally sensitive. Restoring an old key backup can
restore the technical ability to decrypt data that was later
crypto-shredded. Authling's documentation and tooling must state this limit,
separate key and data retention, and provide a way to retire key backups
consistently with an erasure policy. Authling cannot guarantee erasure against
copies of key material retained outside its control.

The KMS boundary owns user-key creation, data-key wrapping and unwrapping, key
rotation, and irreversible shredding. The default self-hosted implementation
may store keys in a dedicated JetStream resource, while external KMS or HSM
implementations remain possible. KMS references are opaque, and KMS
unavailability fails closed.

### Extraction boundary

Authling may drive extraction of these application-neutral mechanics from
Chatto:

- versioned authenticated-encryption and key-wrapping primitives;
- opaque KMS key-reference interfaces and a self-hosted provider;
- wrapped data-key storage and validation;
- bounded unwrapped-key resolution and cache invalidation; and
- envelope-neutral durable-effect consumption and retry mechanics.

The extracted layer must not know Authling or Chatto user IDs, data purposes,
protobuf messages, NATS resource names, AAD formats, backup policy, or erasure
events. Both products continue to own those decisions.

## Consequences

Compromise of event, runtime, snapshot, object, or ordinary backup storage does
not by itself reveal protected user data. Full account erasure can render
historical ciphertext permanently unreadable while preserving enough
non-sensitive event structure for deterministic replay.

The design does not protect plaintext from an authorized response, a
compromised live Authling process with working KMS access, endpoint compromise,
traffic analysis, ciphertext lengths, or intentionally retained external key
copies. Those require separate controls.

Authling becomes dependent on KMS availability for protected reads and writes.
Accidental user-key loss is permanent data loss. Key export, restore, rotation,
monitoring, and disaster-recovery procedures are therefore part of the
production security boundary.

Key provisioning, rotation, scoped erasure, and account deletion are
distributed workflows rather than simple event appends. They require failure,
restart, partial-completion, OCC-conflict, multi-replica, cache-invalidation,
backup-restore, and adversarial substitution tests.

Purpose-scoped keys add storage and operational overhead, but they constrain
the blast radius of key use and leave room for finer erasure guarantees where
the product needs them. Extraction work can reduce duplicated cryptographic
mechanics, but application-specific policy remains explicit in Authling.
