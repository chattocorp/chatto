Chatto can expose a small tool catalog through the Model Context
Protocol (MCP). The optional MCP integration uses the same public HTTP server,
OAuth implementation, and version as the rest of Chatto.

The experimental integration supports MCP `2026-07-28` and these tools:

| Tool | Result or action |
| --- | --- |
| `get_server_info` | Identify the connected server and get its effective name, canonical public URL, connected MCP URL, and Chatto version. |
| `get_current_user` | Get the account ID, display name, and account type for this connection. |
| `list_rooms` | List a bounded page of visible rooms and get the exact visible-room count. |
| `list_room_messages` | List a bounded page of messages in a joined room on the connected server. |
| `post_message` | Post one root text message in a joined room on the connected server. |
| `join_room` | Join one visible channel room on the connected server. |
| `leave_room` | Leave one joined channel room on the connected server. |

Use a host that supports the stateless `2026-07-28` protocol. Older hosts that
start with `initialize` cannot connect. Chatto does not expose MCP resources,
prompts, logging, or catalog-change subscriptions.

The tools apply the same RBAC, membership, validation, and visibility rules as
the public Chatto API. `post_message` is not idempotent. An agent must not retry
it when the first result is uncertain.

The MCP instructions tell an agent host to use these tools as the source of
truth for Chatto application data on the connected server. They tell the host
to use the advertised server title to distinguish the connection from other
Chatto connections. They also tell the host not to infer rooms or messages
from Kubernetes, deployment, DNS, or repository configuration. The host still
decides which available tool it calls.

<Aside type="caution">
  MCP access can expose private Chatto data to an agent host. Enable it only
  for hosts that you trust. Treat tool results as untrusted user content.
  Your browser connects to Chatto for consent. Chatto fetches the client's
  metadata document; its host receives Chatto's IP address. Your agent host
  receives the tool results and can send them to its model provider. Check
  that host's data policy before you grant access.
</Aside>

## Enable MCP

Add this section to `chatto.toml`:

```toml
[mcp]
enabled = true
```

Chatto mounts `/mcp` and `/.well-known/oauth-protected-resource/mcp` on its
existing public HTTP server. It uses the `webserver.url` origin and each exact
non-wildcard origin in `webserver.allowed_origins`. For example, a server at
`https://chat.example` has the MCP endpoint `https://chat.example/mcp`.

Each endpoint is a separate OAuth resource. A human access token for one
origin does not work on another origin. The authorization server always uses
the canonical `webserver.url` origin as its issuer. Bot API keys work on each
configured endpoint. A reverse proxy needs no separate MCP upstream.

## Authenticate an agent host

Human users authorize an MCP client through OAuth Authorization Code with S256
PKCE. Chatto resolves the client's Client ID Metadata Document (CIMD), shows
the exact `chatto:rooms:read`, `chatto:rooms:write`,
`chatto:messages:read`, and `chatto:messages:write` scopes on the consent page,
and issues an access token bound to the exact MCP resource in the request. A
first-party Chatto bearer token without this resource and grant cannot use
MCP.

A native agent host can register an HTTP callback on `127.0.0.1`, `[::1]`,
`localhost`, or one concrete `.localhost` hostname, even when Chatto is on a
remote server. Its CIMD document must set `application_type` to `native` and
must list the callback without a wildcard. Chatto shows the local callback
origin and asks for consent on every authorization. Literal loopback IP
callbacks can select a runtime port; named localhost callbacks must use their
registered port.

An unattended integration can send a current bot API key as its bearer token.
The bot acts as its own account. Its explicit permission allowlist and its
owner's current permission ceiling still apply. See [Bot Accounts](/guides/integrations/bot-accounts/).

<Steps>

1. Give your agent host the public Chatto URL with the `/mcp` path.
2. Let the host read protected-resource and authorization-server metadata.
3. Complete the Chatto consent screen when the host opens it.
4. Confirm that the host discovers the seven tools in the table above.
5. Ask the host to identify the server. Confirm that it reports the expected
   name and public URL.
6. Ask the host to identify the connected account and list its visible rooms.
7. In a test room, ask the host to join, post a unique test message, read the
   message, and leave.

</Steps>

### Codex CLI

The setup below was tested with Codex CLI `0.160.1`:

```sh
codex mcp add chatto --url https://chat.example.com/mcp
codex mcp login chatto --oauth-client-registration cimd
```

Complete sign-in and consent in the browser. Then start Codex and use the
identity and room checks above. Codex identifies itself with its public CIMD
document. You do not need a client secret or a first-party Chatto token.

### MCP Inspector

MCP Inspector `2.9.0` requires `--protocol-era modern` for this endpoint. Use a
client metadata document that you control. For example:

```json
{
  "client_id": "https://example.com/mcp-inspector-client.json",
  "client_name": "My MCP Inspector",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

Publish it at the exact `client_id` URL. Then run:

```sh
npx --yes @modelcontextprotocol/inspector@2.9.0 --cli \
  --server-url https://chat.example.com/mcp --protocol-era modern \
  --client-metadata-url https://example.com/mcp-inspector-client.json \
  --callback-url http://127.0.0.1:6276/callback --method tools/list
```

Open the printed authorization URL and approve the consent request. The
Inspector lists seven tools. Use `--method tools/call --tool-name
get_server_info` to check the connected server. Use `--stored-auth-only` on
later calls to use the stored grant without starting a new consent flow.

## Troubleshoot connection failures

| Failure | Action |
| --- | --- |
| `/mcp` returns `404` | Enable `[mcp].enabled` and check the public URL and reverse proxy. |
| `initialize` returns method not found | Use a host with stateless `2026-07-28` support. In Inspector, select the modern protocol era. |
| Consent rejects `redirect_uri` | Check the client's CIMD document. Runtime ports require a native client and a literal loopback IP callback. Named localhost callbacks must match exactly. |
| A tool request returns `401` | Authorize the exact MCP URL again. Check grant expiry, client blocking, and the complete MCP scope set. A first-party token or a grant for another origin cannot be used. |
| Inspector `--use-stored-auth` reports `no_stored_token` | Use `--stored-auth-only`. This Inspector version can fail to load its stored credentials through the older flag. |

Claude Code `2.1.291` fails callback validation with its current CIMD document.
That document omits `application_type: native`, while the client requests a
callback with a runtime port. Use another tested host until the client and its
metadata document agree. Do not disable callback validation.

## Understand permission failures

An MCP call can succeed only when both the MCP OAuth grant and the normal
Chatto authorization permit it. The current OAuth flow grants the complete
tester scope set. RBAC and room membership can still reject one operation or
target.

Chatto returns a failed operation as an MCP tool error. When Chatto can confirm
that an RBAC permission is missing, the error contains `permission_denied` and
the permission name, such as `room.join` or `message.post`. An agent can report
that name and ask the human driver to contact an administrator. Chatto uses a
generic error for room policy denials and hidden resources so it does not
disclose private state.

## Disable access

Set `[mcp].enabled = false` and restart Chatto to remove the MCP routes. You
can also block an OAuth client in Server Admin or rotate a bot API key. These
actions invalidate the related authority without changing other Chatto
clients.

Removing Chatto from an agent host or deleting its local credentials does not
guarantee that its server-side grant is revoked. Ask a server administrator to
block that OAuth client when you must terminate its access. A revoked grant
or blocked client cannot start another MCP request or refresh its credential,
also when the request reaches another Chatto replica.

The network MCP server does not expose the Operator API, bootstrap, password
reset, account management, or server management. Use the local Operator API
for root-equivalent recovery tasks.
