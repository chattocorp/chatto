Chatto has persistent in-app notifications and optional browser Web Push. Operators configure whether push is available; members decide which rooms, threads, and devices should alert them.

## Notification Policy

Members choose which activity can produce push notifications. Do Not Disturb
suppresses interruptive delivery. A working push configuration does not override
these choices. Test with an account whose policy permits the test activity.

Integrations read and update scoped policies with
[`NotificationPolicyService`](/reference/connectrpc-api/notification-policies/).
A policy can apply to a server, room group, or room. It controls whether activity
produces no attention, an unread dot, an in-app notification, or a push notification.

## Enable Web Push

Web Push is disabled until you provide VAPID keys. Without push configuration, the browser app's notification settings show a notice that push notifications are unavailable on this server. The notice replaces the device checkbox and push actions.

Generate VAPID keys:

```bash
npx web-push generate-vapid-keys
```

Then configure Chatto:

<Tabs>
<TabItem label="TOML">

```toml
[push]
enabled = true
vapid_public_key = "<generate-me>"
vapid_private_key = "<generate-me>"
vapid_subject = "mailto:admin@example.com"
```

</TabItem>
<TabItem label="Environment">

```bash
CHATTO_PUSH_ENABLED=true
CHATTO_PUSH_VAPID_PUBLIC_KEY=<generate-me>
CHATTO_PUSH_VAPID_PRIVATE_KEY=<generate-me>
CHATTO_PUSH_VAPID_SUBJECT=mailto:admin@example.com
```

</TabItem>
</Tabs>

Use a `mailto:` or HTTPS contact URI for `vapid_subject`. Keep the private key secret and stable; changing it can invalidate existing browser subscriptions.

## Device Behavior

To test delivery, open notification settings on a normal member account. Enable
**Push notifications on this device**, grant browser permission, and select
**Send test notification**. If permission is blocked, change the browser or
operating-system permission before you try again. Chatto Desktop uses native
alerts and does not require the Web Push configuration on this page.

On iOS and iPadOS, Web Push requires a supported Home Screen web app. Follow
[Install Chatto on Your Phone](/getting-started/install-pwa/), then open Chatto
from its Home Screen icon before you enable push.

Each Chatto server registers its own subscription and uses its own VAPID keys.
It sends encrypted notification payloads directly to the browser's push service;
the server that hosts the frontend does not relay them. The push service receives
the sending server's IP address. Browser and operating-system support determine
when a suspended device receives and displays an alert.

Subscriptions expire after 180 days without renewal. An active client renews
its subscriptions, and Chatto removes endpoints that the provider reports as gone.
Keep VAPID keys stable so existing subscriptions remain usable.

Chatto accepts only absolute HTTPS push endpoints with public network addresses.
It does not follow redirects or use `HTTP_PROXY` or `HTTPS_PROXY` for delivery.
Private-network, redirecting, and proxy-only custom endpoints are unsupported.

If delivery fails, check HTTPS, browser permission, notification policy, and
provider access from the server. Keep the service worker reachable through the
reverse proxy. Use **Try Again** in notification settings if browser subscription
setup has paused.

## Operator Checklist

1. Set `webserver.url` to the public HTTPS origin.
2. Enable Web Push with stable VAPID keys.
3. Keep the service worker path reachable through your proxy.
4. Test from a normal member account, not only an owner account.
5. Test one desktop browser and one mobile installed PWA if mobile push matters.
6. Explain to members that push is per device and that they enable it once per device.
