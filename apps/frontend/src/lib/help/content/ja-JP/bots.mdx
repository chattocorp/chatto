ボットを使うと、外部ツールから Chatto にメッセージを投稿し、会話に返信できます。ボットアカウントを作成し、必要なルームへのアクセスを与え、API キーまたは webhook でツールを接続します。ボットのソフトウェアは別に実行します。

以下の手順では、デプロイの更新を投稿するボットを設定します。ボットを作成する権限と、送信先ルームへのアクセスが必要です。

## ツールの接続方法を選ぶ

接続方法は 3 種類あります。1 つのボットで複数の方法を使えます。

- **受信 webhook：ツール → Chatto。** 通知サービスや自動化ツールに、メッセージを投稿する URL を渡します。
- **API キー：プログラム → Chatto。** 自作のボットプログラムにキーを渡し、メッセージの読み取り、返信の送信、その他の許可した API 操作を可能にします。
- **送信 webhook：Chatto → ツール。** ボットがメンションされたりダイレクトメッセージを受信したりしたときの通知先エンドポイントを Chatto に設定します。ツールがイベントを処理し、返信が必要なら API キーを使います。

デプロイの更新には受信 webhook を使います。メンションや DM に応答するボットでは、送信 webhook でメッセージを受け取り、API キーで返信を送ります。

## 1. ボットアカウントを作成する

1. ボットが動作するサーバーで**サーバー管理 → ボット**を開きます。
2. **ボットの作成**を選びます。この例では、ユーザー名に `release-bot`、表示名に**リリース更新**を使います。ユーザー名はアカウントを識別し、表示名はメッセージの横に表示されます。
3. ボットを作成します。Chatto は API キーを一度だけ表示します。API を使う場合は、連携のシークレット保管先に保存してください。ダイアログを閉じると、そのキーを再表示できません。
4. ボットの詳細ページを開きます。「リリースパイプラインからデプロイ結果を投稿します」など、短い説明をプロフィールに付けます。

**ボットの作成**を利用できない場合は、管理者に `bot.create` を依頼してください。ボットの所有者はそのボットを管理できます。全ボットの管理権限は別に付与されます。

ツールが受信 webhook だけを使う場合、API キーは不要です。**連携 → API キー**で、使わない最初のキーを取り消してください。

## 2. 1 つのルームへのアクセスを与える

新しいボットには権限がありません。所有者のロールや `everyone` ロールの権限も継承しません。ルームへの参加と、そのルームへの投稿許可は別の要件です。

1. ボットの**権限**タブを開きます。
2. デプロイ更新用のルームの列を探します。
3. 権限表の上部にある**参加しました**の行でそのルームを選び、メンバーシップの変更を確認します。
4. そのルームに対して `message.post` を許可します。無関係な権限は未設定のままにします。

デプロイ用ボットに読み取り権限は必要ありません。投稿先をそのルームに限定するには、ルームの列で `message.post` を付与します。サーバー全体への付与は複数のルームに適用されます。

ボットをルームに追加する権限も必要です。アーカイブ済みのルームやルームでの利用停止により、参加できないことがあります。ボット自身の `room.join` 権限は API 経由でルームに参加するためのもので、**参加しました**の行の代わりにはなりません。

### ボットは所有者を超えるアクセス権を持てません

ボットに付与する各権限は、同じ範囲で人間の所有者が現在持つ権限に制限されます。保存済みでも無効な権限があります。権限表の鍵は、所有者の権限がその許可を妨げていることを示します。所有者がアクセスを失うと、ボットも同じアクセスを失います。サインアウトしてもボットは停止しません。

一部の権限の付与には特権モードが必要です。Chatto から有効化を求められた場合は、有効にしてから権限を追加してください。

## 3. 受信 webhook を接続する

1. ボットの詳細ページで**連携**を開きます。
2. **受信 Webhook**の下で**Webhook を作成**を選びます。
3. **リリースパイプライン**など、呼び出し元に合わせた名前を付けます。
4. **送信先ルーム**にデプロイ更新用のルームを選びます。
5. webhook を作成し、完全な URL をツールの webhook 設定にコピーします。URL の `?room_id=…` 部分を残してください。

ツールが `Content-Type: application/json` と次の本文で HTTP **POST** を送信するように設定します。

```json
{
  "text": "デプロイが完了しました。バージョン **0.5** のテストを開始できます。"
}
```

選んだルームは URL に含まれているため、このリクエストに `channel` フィールドは不要です。代わりに**リクエストごとに選択**を選んだ場合は、JSON に `"channel": "YOUR_ROOM_ID"` を含めます。ルーム名ではなく ID を使ってください。

送信先を選ぶと、URL にルーム ID が追加されます。呼び出し元はその ID を変更し、ボットが投稿できる別のルームにも投稿できます。webhook を 1 つのルームに制限するには、そのルームだけにボットの投稿権限を付与してください。

## 4. テストを送信して結果を確認する

外部ツールのテスト機能を使います。受信リクエストが成功すると、HTTP `200` とテキスト `ok` が返ります。Chatto の選んだルームに、**リリース更新**からのメッセージが **BOT** ラベル付きで表示され、「0.5」が太字になっていることを確認します。

リクエストに失敗した場合は、応答を確認します。

- **`401 invalid_token`：**URL が不完全、無効、または取り消されています。完全な URL が手元にない場合は、新しい受信 webhook を作成してください。
- **`404 channel_not_found`：**ルーム ID、ボットの参加状態、`message.post` の付与、そのルームでの所有者の投稿権限を確認してください。
- **`400 invalid_payload`：**空でないメッセージ本文とルーム ID を含む有効な JSON を送ってください。URL と本文の両方にルーム ID がある場合、値は一致する必要があります。ルームのポリシーとメッセージサイズの制限も適用されます。
- **メッセージが 2 回表示される：**再試行により別のメッセージが作成されることがあります。受信 webhook には、重複を防ぐための冪等性キーがありません。

テストに成功したら、デプロイの完了時に webhook を呼び出すようにツールを設定します。

## 人に返信するボットを作る

ボットプログラムに Chatto API キーを設定します。キーはプログラムのシークレット設定に保存してください。API リクエストは `Authorization: Bearer YOUR_API_KEY` ヘッダーで認証します。

ボットに必要な権限を選びます。

- **呼びかけられたときだけ返信する：**`message.read-interactions` と `message.post-in-interactions` を付与します。ボットは、自分が開始したスレッド、直接メンションされたスレッド、および自分の DM を全体にわたって読めます。そのため、ボットへのメンションにより、そのスレッドの以前のメッセージへのアクセスも与えられることがあります。
- **ルームを読むが、呼びかけられたときだけ返信する：**`message.read` と `message.post-in-interactions` を付与します。
- **全メッセージを読み、会話を始める：**`message.read` と `message.post` を付与します。

対象のルームに権限を適用します。ダイレクトメッセージには、権限表の**ダイレクトメッセージ**の範囲を使います。これらの権限も所有者の権限に制限されます。

### 返信するタイミングをプログラムに伝える

プログラムが Chatto webhook イベントを受け付ける場合は、次の手順を行います。

1. **連携 → 送信Webhook → Webhookを作成**を開きます。
2. 名前と、プログラムの公開 HTTPS エンドポイントを入力します。
3. 受信側が **Authorization ヘッダー**を必要とする場合は、`Bearer` などの接頭辞も含む、受信側が期待する完全な値を入力します。
4. 受信側で Chatto webhook の署名を検証する場合は、署名用シークレットを受信側の設定にコピーします。シークレットは一度だけ表示されます。
5. ボットが読めるルームでメンションするか、DM を送ります。受信側のログと Chatto でのボットの返信を確認します。

エンドポイントには、ボットを直接メンションした新しいメッセージ、またはボットへの DM が届きます。通常のルームメッセージ、編集、リアクション、ボット自身が送信したメッセージでは、これらの webhook は実行されません。ルームのスレッドに続く通常の返信も、再びボットをメンションしない限り実行のきっかけになりません。

受信側は HTTP 2xx でイベントを受け付け、その後 API でチャットへの返信を送ります。Chatto は HTTP 応答の本文を無視します。配信は繰り返されることがあるため、受信側は配信 ID を使い、同じ処理を 2 回行わないようにする必要があります。読み取り可能な全活動を必要とするプログラムでは、メンションと DM の webhook ではなく、Chatto のリアルタイム API を使ってください。

イベントのペイロード、署名検証、API 操作については、[ボット webhook リファレンス](https://docs.chatto.run/reference/bot-webhooks/)と [API リファレンス](https://docs.chatto.run/reference/connectrpc-api/)を参照してください。

送信 webhook は、メッセージ本文と、メッセージ、投稿者、ルーム、ボットの識別子を設定済みエンドポイントに送ります。受信側には Chatto サーバーの送信元 IP アドレスも見えます。ボットが AI プロバイダーや別のサービスにメッセージを転送する場合は、メンバーの会話で使う前に、そのことを説明してください。

### ボットが返信しない場合

プログラムがイベントを受信したか確認します。送信 webhook の**最近の失敗**を開くと、記録された配信エラーを確認できます。エンドポイントが有効で到達可能か、設定した認証を受け付けるか、リダイレクトせずに 2xx を返すかを確認してください。失敗一覧が空でも、配信に成功した証拠にはなりません。

イベントは届いているのに返信が表示されない場合は、プログラムの API キー、返信操作、ボットの実効的な読み取り権限と投稿権限を確認してください。

## 連携を保守する

- **認証情報を交換する：**名前付きの新しいキーまたは webhook を作成し、呼び出し元を更新してテストした後、古いものを取り消します。API キーは自動では期限切れになりません。実際のキーや認証情報を含む URL を、チャットやソース管理に貼り付けないでください。
- **送信配信を一時停止する：**エンドポイントの**一時停止**を選びます。**再開**は新しいイベントを許可しますが、一時停止中のイベントを再送しません。
- **ボットを別の所有者に渡す：**`bot.manage` を持つアカウントは**所有者を再割り当て**を使えます。ボットの実効アクセス権は直ちに新しい所有者に従います。既存のキーは有効なままなので、以前の運用者のアクセスをなくす必要がある場合は認証情報を交換してください。
- **所有者アカウントを削除する：**継続利用するボットは先に別の所有者へ割り当てます。人間の所有者を削除すると、その所有者のボットも削除されます。
- **ボットにできることをメンバーに示す：**プロフィールを開き、**所有者**と**できること**を確認します。ルームや所有者を変えた後も、アクセス権を見直してください。
