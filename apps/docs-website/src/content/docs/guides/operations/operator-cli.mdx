`chatto operator` provides local, root-equivalent account administration, channel room management, and attachment upload. Use it to create the first account on a server, recover access, or manage channels and files from a script.

The CLI talks to the running Chatto server over a Unix socket. It does not connect directly to NATS and does not use a Chatto login, bearer token, cookie, or RBAC role.

## Enable the Operator API

The Operator API is disabled by default. Enable it in `chatto.toml`, then start or restart Chatto:

```toml
[operator_api]
enabled = true
socket_path = "/tmp/chatto/operator.sock"
```

The socket mode is always `0600`. Its parent directory must be owned by the Chatto process user and must not be accessible to other users. Chatto refuses to start if these checks fail.

<Aside type="danger" title="Socket access is root-equivalent">
  Anyone who can access the operator socket can create accounts, set passwords, assign roles, and delete accounts. Never publish the socket over TCP or mount it into an untrusted container.
</Aside>

## Create a user

<Steps>
1. Create the account with a unique login:

   ```sh
   chatto operator user create \
     --login alice \
     --display-name "Alice" \
     --verified-email alice@example.com
   ```

   In an interactive terminal, Chatto prompts for a password. Leave it empty to create a passwordless account. If you omit `--display-name`, it defaults to the login.

2. Copy the user ID from the output. Commands that change an existing account use this stable ID rather than its login or email address.

3. If the account should have an explicit role, assign one at creation time or afterwards:

   ```sh
   chatto operator user create \
     --login alice \
     --role admin \
     --role moderator

   chatto operator user role add USER_ID admin
   ```
</Steps>

`--verified-email` adds the address as already verified; Chatto does not send a verification email. Only use it when you trust the address. `--role` accepts a configured role name and can be repeated.

### Create a user non-interactively

Read passwords from standard input or a restricted file for automation:

```sh
printf '%s\n' "$CHATTO_USER_PASSWORD" | \
  chatto operator user create \
    --login alice \
    --display-name "Alice" \
    --password-stdin

chatto operator user create \
  --login alice \
  --password-file /run/secrets/alice-password
```

When the command is not attached to a terminal and you provide no password option, it creates a passwordless account. You can later add a password with `user set-password`.

<Aside type="caution">
  The `--password` option is available, but it can expose the password in shell history and process listings. Prefer `--password-stdin` or `--password-file`. Supply only one password option.
</Aside>

## Find and inspect users

List users or inspect one account:

```sh
chatto operator user list
chatto operator user list --search alice
chatto operator user list --search alice@example.com
chatto operator user get USER_ID
chatto operator user get --login alice
chatto operator user get --email alice@example.com
```

Use `user get --login` or `user get --email` to find one account by its exact login or verified email address. A script can use either command to recover a user ID after an interrupted run. Supply exactly one selector: `USER_ID`, `--login`, or `--email`.

Search matches logins and display names, or an exact verified email address. `list` returns 20 users by default and supports offset pagination:

```sh
chatto operator user list --limit 100 --offset 0
chatto operator user list --limit 100 --offset 100
```

The maximum limit is 100. Human-readable output ends with `total` and `has_more` values so you can tell whether another page exists.

## Find channel rooms

List channel rooms, including archived rooms:

```sh
chatto operator room list
chatto operator room list --name general
chatto operator room list --name general --json
```

`--name` matches the exact stored channel name. If more than one room has that name, the command returns each room with its own ID. Results include the room ID, name, group ID, description, and archived state. Use the ID to identify a room in later commands.

The command returns 20 rooms by default. Use `--limit` and `--offset` to read more, up to 100 rooms per page:

```sh
chatto operator room list --limit 100 --offset 0
chatto operator room list --limit 100 --offset 100
```

Rooms appear in room ID order. Human-readable output ends with `total` and `has_more`. Pages are live reads, so room changes between requests can shift offsets. You can repeat the command safely.

## Create a channel room

Create a channel in the first room group, or select a group by ID:

```sh
chatto operator room create --name "project-chat" --description "Project discussion"
chatto operator room create --name "team-chat" --group-id GROUP_ID
```

The command returns the room ID, name, group ID, archived state, and description. Use `--json` when a script needs the full response. Chatto checks the name and description as it does for rooms created in the app.

An import script can save the returned Chatto room ID alongside its source room ID. If the response is lost, use `room list --name` to find the room before creating it again. A repeated create request with the same name returns a conflict.

## Add a channel room member

Add an existing user to a channel room by Chatto ID:

```sh
chatto operator room member add --room-id ROOM_ID --user-id USER_ID
```

The command returns both IDs. Use `--json` to get the member record. Repeating the command for a current member succeeds without adding a second membership. Chatto rejects missing users or rooms, DM rooms, archived rooms, universal rooms, and users with an active room ban.

## Upload a local attachment

Upload a file for an existing Chatto user and channel room:

```sh
chatto operator asset upload \
  --room-id ROOM_ID \
  --author-id USER_ID \
  --file /path/to/exported-image.png
```

The command prints the completed asset ID. Add `--json` to get an `assetId` field for a script. The file basename becomes the stored filename. Chatto infers the MIME type from that name. Use `--filename NAME` or `--content-type TYPE` to override either value. If you run the CLI inside Docker, `--file` must name a file inside that container.

The command reads only the local file. It does not fetch a URL from the export. Chatto applies its normal attachment size limits and media processing. It stores the bytes in its configured NATS or S3 asset backend. If you use S3, the storage provider receives the file bytes and the server's IP address. The asset belongs to the selected author; the upload action is recorded as a system action. The author does not need a session or file-attachment permission for this operator command. The room must be an active channel.

If an upload command returns an error, it attempts to cancel the incomplete upload. If the process stops or cannot reach the server, server cleanup removes abandoned chunks after expiry. A completed asset remains pending until a message attaches it; Chatto removes an unattached pending asset after 24 hours. Running the command again can create a different asset ID, so an import script should save each returned ID. The CLI reports only an asset ID; a later message command attaches it.

## Import a historical message

Import one message for an existing Chatto user and channel room:

```sh
chatto operator message import \
  --room-id ROOM_ID --author-id USER_ID \
  --created-at 2022-08-18T11:11:11.147Z \
  --body-file /path/to/exported-message.txt
```

The command prints the new Chatto message ID. Use `--json` to read `messageId` in a script. Supply text with `--body`, `--body-file`, or `--body-stdin`. Use only one of these flags. A message can omit text when it has at least one `--attachment-asset-id ASSET_ID` flag. Repeat that flag for more attachments.

Use `--edited-at RFC3339` to preserve the last edit time. Use `--in-reply-to CHATTO_MESSAGE_ID` to refer to an existing message in the same room. A reply reference does not create a Chatto thread. To preserve an exported preview, use `--preview-url URL` with optional `--preview-title`, `--preview-description`, and `--preview-type` fields. The URL must use HTTP or HTTPS. Chatto stores these values without fetching the URL.

The room must be an active channel, and the author must exist. Attached assets must belong to that author and room. Chatto encrypts the body and applies its normal message and attachment limits. Historical imports do not notify users, mark messages unread, follow threads, or send bot webhooks. Update all server replicas before you start an import so each replica recognizes historical messages. The command does not require a user session or room membership. Each successful call creates a new message. Save the returned ID in your import script so a retry does not create a duplicate.

## Update a user

Change a login, a display name, or both:

```sh
chatto operator user update USER_ID --new-login alice-renamed
chatto operator user update USER_ID --display-name "Alice Example"
chatto operator user update USER_ID \
  --new-login alice-renamed \
  --display-name "Alice Example"
```

Add an email address that Chatto should treat as already verified:

```sh
chatto operator user add-email USER_ID --email alice@example.com
```

The operator CLI can add a verified email address, but it cannot remove one.

## Set a password

Run the command without a password option to enter the new password at an interactive prompt:

```sh
chatto operator user set-password USER_ID
```

For automation, use standard input or a restricted file:

```sh
printf '%s\n' "$CHATTO_USER_PASSWORD" | \
  chatto operator user set-password USER_ID --password-stdin

chatto operator user set-password USER_ID \
  --password-file /run/secrets/alice-password
```

The new password cannot be empty. Setting a password does not require the previous password.

## Clear a username-change cooldown

Allow a user to change their username again after a recent self-service change:

```sh
chatto operator user clear-username-cooldown USER_ID
```

The command does not change the user's current username. It clears the 30-day wait before the user's next self-service change. Use `--json` to get a `cleared` result for a script.

## Manage roles

Assign or revoke a configured server role by name:

```sh
chatto operator user role add USER_ID moderator
chatto operator user role remove USER_ID moderator
```

Use `user list --json` or `user get USER_ID --json` to inspect the roles currently assigned to an account. Role changes take effect through the running server's normal domain services.

## Delete a user

```sh
chatto operator user delete USER_ID
```

In an interactive terminal, Chatto asks you to type a confirmation containing the user ID. Non-interactive scripts must explicitly confirm deletion:

```sh
chatto operator user delete USER_ID --yes
```

<Aside type="danger">
  Account deletion is irreversible in the live server. Confirm the stable user ID with `user get` before using `--yes`. Existing backups are not modified by account deletion.
</Aside>

## Run commands in Docker Compose

Run the CLI inside the app container as the same `chatto` OS user that owns the socket:

```sh
docker compose exec -u chatto chatto /chatto operator user list

docker compose exec -u chatto chatto /chatto operator user create \
  --login alice \
  --display-name "Alice"
```

For password input from your terminal, keep the default pseudo-terminal allocated by `docker compose exec`. For scripted input, use `--password-stdin`:

```sh
printf '%s\n' "$CHATTO_USER_PASSWORD" | \
  docker compose exec -T -u chatto chatto \
    /chatto operator user create --login alice --password-stdin
```

## Global options and JSON output

The following options apply to every `chatto operator` subcommand:

| Option | Purpose |
| --- | --- |
| `-c, --config PATH` | Read configuration from `PATH` instead of `chatto.toml`. |
| `--operator-socket PATH` | Connect to a specific Operator API socket. |
| `--json` | Print the protobuf response as JSON for scripts. |

The socket path is resolved in this order:

1. `--operator-socket`
2. `CHATTO_OPERATOR_API_SOCKET_PATH`
3. `operator_api.socket_path` in the selected configuration file
4. `/tmp/chatto/operator.sock`

For example:

```sh
chatto operator user list --json
chatto operator user get USER_ID --json
chatto operator --operator-socket /run/chatto/operator.sock user list
chatto operator --config /etc/chatto/chatto.toml user list
```

## Troubleshooting

If a command cannot connect to the socket, check that:

- the running server has `operator_api.enabled = true`;
- the CLI and server resolve the same socket path;
- you run the CLI as the OS user that owns the socket;
- the Chatto server is running; and
- in containers, you execute the command in the container that owns the socket rather than on the host.

Use `chatto operator --help`, `chatto operator user --help`, or a command's `--help` output for the exact options supported by your installed Chatto version.
